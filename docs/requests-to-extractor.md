## 왜 이 문서가 기획 레포 요청과 따로 있나

**검사기와 규격의 원본이 추출기에 있다.** 기획 레포는 그 사본을 받을 뿐이고,

그래서 **검사기·규격에 관한 것은 기획팀에 물어도 못 고친다.** 전에 그 넷(검사기 관련 요청)이
기획 레포 요청 문서에 섞여 있었고, 이번에 여기로 옮겼다.

**아래 열넷은 빌더가 지어내면 안 되는 것이거나, 추출기만 고칠 수 있는 것이다.**

② 레포 전체가 돌기 때문에 **남이 만든 red 가 내 초안 판정에 섞여 나온다.**

## C. 어휘와 표기 — 둘

### 6. 나가는 규격이 「과업」을 쓴다 ★

> ⚠️ **2026-08-15 재실측 — 나빠졌다. 그리고 성격이 달라졌다.**
> **여덟 자리가 열한 자리**이고 파일이 둘에서 **셋**(`reqs.md` 5 · `layout.md` 3 · **`page.md` 3**)이 됐다.
> ⛔ **늘어난 자리가 산문이 아니다** — `page.md:111` 의 **`과업` 은 화면 md 꼬리표의 슬롯 이름**이다
> (`id: … / 기능: … / 과업: []`). **화면 263장에 박히는 값**이라 나중에 바꾸면 전수 재작업이다.
> **급이 「부딪힌다」에서 올라간다** — 다만 ⛔ **여전히 대응표가 먼저다**(아래).

`assets/spec/reqs.md` 와 `assets/spec/layout.md` 여덟 자리다 —
`# 요구사항 — reqs/<과업ID>.md` · "과업 1개 = 파일 1개" · 예시 본문 `# 과업` ·
"`reqs/` 는 과업 축이다" · "`tasks/`(과업 산출물)" 등.

**빌더는 「과업」을 쓰지 않기로 했다.** 작업 단위는 **BRD** 이고, 일반 명사로는 **「작업」**이다.

그 규격이 **기획 레포로 그대로 복사돼 나가므로**, 빌더가 클론한 레포 안 규격이 금지어로 말을 건다.
기획자가 빌더 화면에서는 「작업」을 보고, 레포 규격에서는 「과업」을 본다.

⛔ **다만 낱말부터 바꾸지 마라 — 그게 더 위험하다.**

`reqs/<과업ID>.md` 가 **빌더의 무엇에 해당하는지가 아직 안 정해졌다.** 빌더의 층은 다섯이다 —
요구사항(`REQ`) · 요구사항정의서(`RD`) · BRD · 작업목업 · 개발요청서(`DR`).
규격상 `reqs/` 는 「있어야 할 것을 적고 화면·도메인 앵커로 가리키는 것」이라 `REQ` 같기도 `RD` 같기도 하다.

**「과업」을 「작업」으로 바꾸면 BRD 와 같은 것처럼 읽힌다.** 빌더에서 「작업」은 BRD 하나를 뜻하기 때문이다.
그러면 어휘는 맞춰졌는데 **뜻이 어긋난 채로 굳는다** — 지금보다 나쁘다.

**순서**: ① 먼저 **대응표**를 정한다 — `reqs/<...>.md` 한 장이 빌더의 어느 층인가.
② 그 다음에 낱말을 맞춘다. **어느 쪽이든 세 저장소가 같은 말을 쓰면 된다** — 빌더가 그 말로 오는 것도 답이다.

| | `facet` | `variants` |

| 뜻 | **그 기관에만 있다** | **그 기관 목업이 있다** |
| 값 | 문자열 **하나** | 정렬 **배열**(여럿) |
| 어디서 오나 | 사람이 적은 꼬리표 | **폴더 실물에서 계산** — 사람이 적는 값이 아니다 |
| 둘 다 있으면 | **`FACET-6` red** — 한 기관 전용이면 갈릴 상대가 없다 | |

⚠️ **색인은 판정하지 않는다** — 그런 레포에서는 두 곳에 다 실린다. **그건 이미 red 인 레포라는 뜻이다.**

⭐ **등식은 안 깨졌다** — 칸이 늘어도 `iaScreens = Σ iaIndex + Σ iaShared + (자리 못 얻은 것)` 그대로다
(**251 + 2 + 3 = 256**, 재검산했다). ⛔ **`counts` 를 키 개수나 완전일치로 검산하면 그날 깨진다** —
그쪽 경고다. **우리는 `counts` 를 코드에서 아예 안 읽어 해당이 없다.**

```
화면형   : { 경로, 종류, 상위화면? }
팝업·모달: { 경로?, 종류, 여는화면: [정렬된 화면ID…], 여는곳? }
```

| 읽을 때 | |
|---|---|
| `상위화면` 대 `여는화면` | **앞엣것은 사람이 적은 값 · 뒤엣것은 실물에서 파생된 값**이다. 한 칸에 섞지 않은 이유가 그것이다 — 섞으면 「이 값이 어디서 왔나」를 아무도 못 묻는다 |
| `여는화면: []` | 팝업·모달이면 **비어 있어도 싣는다.** 0장(IA-9 red)과 **「파생을 모르는 옛 색인」**이 구별돼야 한다 |
| ⛔ **`경로` 없음이 두 가지다** | **`iaShared` 등재 여부로 가른다** — 등재됐으면 **공용(정상)**, 안 됐으면 **자리를 못 얻었다(red)**. 뭉치면 **정상인 공용 팝업과 결함을 같은 것으로 그린다** |
| `iaIndex` 는 **파티션**이다 | 한 화면은 **최대 한 자리.** 공용을 여러 경로에 실으면 「이 메뉴 아래 화면 몇 장」이 부풀고 「공용 한 장」과 「자리마다 한 장씩」이 구별되지 않는다 |
| `counts.iaShared` | **`iaScreens = Σ iaIndex + Σ iaShared + (자리 못 얻은 것)`** 으로 색인을 검산할 수 있다. **우리가 실제로 검산했다 — 251 + 2 + 3 = 256.** 앞 판에서는 `iaIndex` 가 곧 파티션이라 `iaScreens` 하나로 닫혔다 |

**빌더에 이것을 읽는 코드는 아직 없다** — 계획 2 가 IA 를 안 건드렸다. **때가 좋았다.**
새로 쓸 때 **`/3`** 으로 쓰면 된다.

#### 제안과 달라진 두 곳 — 둘 다 받는다

| | 제안 | 실제 | 왜 그쪽이 낫나 |
|---|---|---|---|
| 블록 이름 | `--- 메뉴 ---` | **`--- 배치 ---`** | 표에 **메뉴 아닌 행**(무소속 뿌리 화면)도 오른다. 「메뉴」면 이름이 거짓이 되는 행이 생긴다 |
| 경로 구분자 | `bizcard > delivery` | **`bizcard/delivery`** | 표의 경로 = 이름표 키 = 색인 키 꼬리로 **문법이 하나**가 된다 |

**이름표 절도 하나로 합쳐졌다** — `## 대분류`·`## 업무` 두 절이 **`## 이름표`** 한 절이 됐다.
전체 경로 키를 쓴다(`customer/usag: 이용기관`). 깊이가 가변이면 「업무」라는 절 이름이
셋째 단에서 거짓이 되기 때문이고, **맞는 판단이다.**

#### 표에는 메뉴 행만 오른다 — 하위는 사슬로 파생된다

**행에 오르는 것은 `종류: 화면` 이고 `상위화면` 이 없는 것뿐**이다(IA-7 red).
상세·등록·팝업의 소속은 **파생**된다.

> **소속 = ① 자신이 배치 행에 오른 화면이면 그 행의 `경로` ② 화면형이면 `상위화면` 사슬을 따라
> 처음 만나는 「행에 오른 화면」의 `경로` ③ 팝업·모달이면 그 화면을 같은 시스템에서
> `이동`·`이동modal` 로 지목한 화면들의 소속** (③ 은 **2026-08-15 신설**)

⛔ **③ 이 2026-08-15 에 바뀐 자리다 — 팝업·모달은 더 이상 `상위화면` 을 안 쓴다.**

| 지목한 화면들이 닿는 **자리**가 | 결과 |
|---|---|
| 한 곳 | 그 자리를 받는다 — 배치 행에 오른 화면과 똑같이 트리에 걸린다 |
| 두 곳 이상 | **공용** — 자리를 안 준다. 색인의 `iaShared` 로 빠진다 |
| 지목이 **0장** | **red**(IA-9). 단 `여는곳: 셸` 을 선언했으면 면제하고 공용으로 본다 |

★ **판정은 「부모가 몇 장이냐」가 아니라 「그 부모들이 몇 갈래 자리에 있냐」다.** 실측이 시킨 것이다 —
백오피스 팝업 46장 중 부모가 여럿인 5장 가운데 **3장은 자리가 하나**였다(같은 목록과 상세가 같은 팝업을 연다).
**부모 수로 판정했으면 자리가 멀쩡한 화면 셋을 트리에서 잃었다.**

⛔ **회신에 안 적힌 것 셋 — 규격 원문(`spec/ia.md`)에서 우리가 더 건졌다. 빌더 화면이 이것에 걸린다.**

| 무엇 | 빌더가 걸리는 자리 |
|---|---|
| **`여는곳: 셸`** — 팝업·모달 전용 예외 선언(어휘는 `셸` 하나). 「화면이 아니라 전 화면 공통 헤더에서 열린다」 | 이걸 선언하면 IA-9 red 가 **면제되고 공용으로 간다.** 다만 **`IA-9 review` 가 대신 뜬다** — 기계가 확인할 수 없는 주장이라 사람이 본다. ⚠️ **래칫이 review 총수를 기준선으로 잡으므로 이 도피구가 조용히 늘지 못한다.** 규격이 스스로 *"부모를 못 찾을 때 쓰는 도피구로 쓰지 마라"* 고 적었다(v1 웹뷰 부모 0장 29장 중 진짜는 2장) |
| **파생은 대상키 이름이 아니라 「지목당한 화면의 종류」에 건다** | 시스템마다 같은 일을 다른 키로 한다 — **백오피스는 팝업을 전부 평범한 `이동:` 으로 가리키고 `이동modal` 을 아예 안 쓴다.** 웹뷰는 `이동modal` 을 쓴다. **키 이름으로 걸면 한쪽이 통째로 red 다** |
| **`이동cross` 는 안 센다** | 다른 시스템을 가리키는 자리라 같은 시스템 소속의 근거가 될 수 없다. 자기 자신을 가리키는 이동도 부모가 아니다 |

**팝업 안에서 또 팝업이 뜨는 2단 사슬**(g2c 실측 2건 · v1 웹뷰는 최대 4단)은 **파생 간선으로 이어진다** —
파생 부모가 팝업이면 그 팝업의 소속을 다시 따라간다. **순환 검사는 `상위화면` 간선과 파생 간선 전부에 전역으로** 한다.

**그래서 메뉴를 옮기면 행 하나만 고치면 되고 하위가 자동으로 따라온다.**
화면형 전부를 행으로 실었다면 **「한 값을 두 곳에」 금지를 표 안에서 어기게 된다** — 그쪽 판단이 옳다.
(사슬 파생값과 기록값이 **159/159 일치**한다고 검증까지 했다.)

**여기 적어 두는 이유는 하나다** — `reqs/` 에 실물이 쌓이면 이게 필요해질 수 있고,
그때 새 규격을 급히 만들지 않도록 **자리 이름만 미리 예약해 두자**는 것이다.

**제안**: `index.json` 의 `screens[].domains[]` 로 예약하고 지금은 안 낸다.
`domain-index.json` 을 예약해 둔 것과 같은 방식이다.

### 14. 판이 올랐을 때 **`--json` 계약이 바뀐 것인지 알 길이 없다** — ✅ **섰다 (회신 #3)**

> **「있음」일 때는 무엇이 바뀌었나를 같은 줄에 적게** 했다 —

|---|---|
| 모르는 판을 **막는다** | 평범한 판올림 하나에 **그 사업 저장이 통째로 언다** |

**「`--json` 계약 영향: 있음 / 없음」** 한 줄. 그 문서가 기획 레포로 나가므로 빌더가 클론 안에서 읽는다.

⛔ **처음에 「출력에 계약 판을 따로 실어 달라」(`"contract": "we-adk-verify-json/1"`)로 적으려다 물렀다.**

## I. 역류가 as-is 를 갱신한다 — 둘 (2026-08-24 신설)

**무슨 일이 있었나.** 빌더가 **역류(개발 → 빌더)에 as-is 갱신 재료를 실어 오기로** 정했다
(2026-08-24 병주 확정 · 정본 `docs/superpowers/specs/2026-08-07-dev-feedback-design.md`).
개발이 구현을 끝내면 운영 화면이 바뀌는데 클론의 `pages/`·화면 md·`index.json`·도메인 md 가 낡고,
**다음 FRD 가 그 낡은 것을 as-is 로 읽어 확신에 찬 답을 낸다.**

**갱신할 길을 셋으로 세어 봤고 둘이 닫혀 있었다.**

| 길 | 상태 |
|---|---|
| 빌더가 운영 소스를 읽어 갱신 | ⛔ 경계다. 「빌더는 g2c 를 모른다」가 무너진다 |
| 추출기가 다시 굽는다 | ⛔ **그쪽 `CLAUDE.md` 의 「508화면은 재추출하지 않는다」** |
| 역류가 실어 온다 | 여기밖에 없다 |

⭐ **그래서 재료를 쥔 개발이 굽는 쪽이 된다.** 그리고 **기획 레포가 추출기 스킬 사본을 품고 나가므로**
규격에 맞게 굽는 도구가 개발 손의 클론에 이미 있다 — 개발이 손으로 md 를 쓰는 것이 아니다.
**이 그림이 그쪽 전제와 맞는지가 아래 둘이다.**

### 15. 부분 재추출을 지원하나 — 「508화면은 재추출하지 않는다」의 범위

**우리 해석**: 그 금지는 **전체를 다시 굽는 것**을 막은 것이고, **DR 이 건드린 화면·모듈만** 굽는 것은
그 금지 밖이다. ⛔ **이 해석은 우리 것이다** — 그쪽 문서에 「부분」이라는 말이 없다.

**물을 것 셋.**

1. **부분 재추출이 성립하나.** 스킬을 「화면ID 목록 / 모듈 목록」으로 좁혀 돌릴 길이 있나,
   아니면 전체를 돌려야만 규격에 맞는 출력이 나오나.
2. **「508화면은 재추출하지 않는다」가 무엇을 막으려던 것인가.** 값(시간·토큰)인가,
   **사람 손질이 덮이는 것**인가. 후자면 부분 재추출도 같은 위험을 갖는다 —
   우리가 이미 `ia.md` 를 역류 목록에서 뺀 것이 그 까닭이다.
3. **개발이 그 스킬을 돌리는 것을 그쪽이 허용하나.** 지금 지형표는 「사업 착수 때만 도는 스킬」이고
   **누가 돌리나가 안 적혀 있다.** 운영 소스를 쥔 쪽은 개발이라 기획자는 애초에 못 돌린다.

⛔ **기다리지 않는다.** 답이 「부분은 안 된다」여도 길이 있다 — 그때는 개발이 **운영 html 원본만** 밀고
규격 변환을 우리가 못 하니 **그 화면은 「as-is 낡음」 표시만 세운 채 남긴다.** 나쁘지만 조용하지는 않다.

### 16. 부분 출력을 `index.json` 에 어떻게 합치나

**여기가 진짜 어려운 자리다.** 화면 파일 한 장은 갈아끼우면 되는데,
**`index.json` 은 전체를 한 번에 쓰는 파일**이다.

**우리가 잰 것** (프로젝트 `0000001` · 색인 `we-adk-index/6`): 화면 하나의 색인 행이 나르는 것은
`경로` · `상위화면` · `여는화면` · (요청한) `화면명` · `기능` 이고, **표준 화면ID 채번이 그 중 `경로` 앞 두 마디에 매달려 있다**
— 색인에 행이 없으면 그 화면은 번호를 못 받는다(640장 중 26장이 그 자리다).

**그래서 부분 출력이 이 셋 중 무엇인지가 갈린다.**

| 모양 | 우리가 할 일 | 위험 |
|---|---|---|
| ㉠ **색인 조각**(그 화면들의 행만) | 우리가 기존 `index.json` 에 행을 갈아끼운다 | ⛔ **`counts`·`schema`·집계 칸이 안 맞게 된다** — 조각이 그것을 모른다 |
| ㉡ **색인 전문**(전체를 다시 굽는다) | 통째로 갈아끼운다 | 15번의 「전체 재추출 금지」와 부딪힌다 |
| ㉢ **합치는 도구를 그쪽이 준다** | 부르기만 한다 | 없으면 만들어야 한다 |

**물을 것 둘.**

1. **부분 출력이 ㉠·㉡·㉢ 중 무엇인가.** ㉠ 이면 **집계 칸을 누가 다시 세나.**
2. **새로 생긴 화면은 어떻게 오나.** 갱신은 행을 갈아끼우면 되는데 **신규는 행이 없다** —
   그 화면은 `경로` 가 없어 **표준 화면ID 도 안 붙고 메뉴구조도에도 안 잡힌다.**
   ⚠ 우리 실측으로 **색인에 경로가 있는데 번호가 안 붙은 것은 0장**이다 — 즉 이 자리의 결함은 전부 재료 쪽이다.

⛳ **도메인은 사정이 다르다.** 그쪽에 **병합기(`scan/lib/domain-merge.mjs`)가 이미 있고** 사람 문장 보존을
실측해 둔 코드라, 도메인은 ㉢ 이 이미 서 있는 것으로 읽었다. **맞나 확인만 해 주면 된다.**

## 2026-08-25 요청 — 디자인 시스템용 Layouts·Templates 계약

> 이 절이 디자인 가이드에 관한 최신 요청이다. 이전 HTML 가이드의 탭 구성 요청보다 우선한다.

### 목표

BZP의 메뉴 구성을 복제하지 않는다. BZP는 시각적 완성도와 정돈 수준의 참고 기준이다.
우리 디자인 가이드는 실제 추출 근거를 사용하면서 신규 화면 설계와 FRD 작업에 재사용할 수 있는
`Foundations / Components / Layouts / Templates` 네 영역으로 구성한다.

### Builder와 추출기의 책임

- 추출기는 근거가 확인된 디자인 값, 의미 단위 컴포넌트, 공통 레이아웃, 업무 화면 템플릿의 구조화 데이터와 렌더 재료를 제공한다.
- Builder는 시스템 선택, 탭, 카드, 상태 비교, 설명, 근거 펼치기를 네이티브 UI로 렌더한다.
- `index.html`은 추출기 독립 검수용이며 Builder 최종 사용자 화면의 정본이 아니다.
- iframe, 화면 캡처 이미지, 전체 운영 화면 덤프를 Builder의 기본 프리뷰로 사용하지 않는다.

### 사용자에게 보일 네 영역

1. `Foundations`
   - 확정된 색상 역할, 타이포그래피, 간격, 라운딩, 그림자만 제공한다.
   - 역할 미상 값과 추출 진단은 기본 콘텐츠에 노출하지 않는다.
2. `Components`
   - 원시 CSS class가 아니라 버튼, 입력, 선택, 탭, 표, 페이지네이션, 상태 표시, 모달 등 사용 목적 기준으로 분류한다.
   - 실제 근거가 있는 기본·선택·비활성·오류 상태를 같은 문맥에서 비교할 수 있어야 한다.
   - 독립 렌더가 의미 없거나 숨겨진 원자 요소는 기본 목록에서 제외한다.
3. `Layouts`
   - 사이드바와 헤더를 따로 쪼개지 않고 `사이드바 + 헤더 + 콘텐츠`의 시스템 공통 골격으로 제공한다.
   - 전체 운영 화면 복사본이 아니라 공통 영역과 관계를 이해할 수 있는 완결된 대표 fragment여야 한다.
   - 영역 이름, 필수 여부, 크기·고정 여부와 실제 사용 근거를 구조화한다.
4. `Templates`
   - 조회 목록, 상세, 등록·수정, 승인·처리, 대시보드 등 업무 화면의 재사용 가능한 출발점이다.
   - Layout 안에 실제 Components가 배치된 완결된 화면 구성을 제공한다.
   - `templateId → layoutId + componentIds` 관계를 제공해 FRD 캔버스 추천에서 그대로 사용할 수 있어야 한다.

### JSON 요청 계약

현재 `/5`의 격리 CSS, HTML fragment, render-check와 원본 근거는 유지하되 다음 사용자 의미 계약을 추가하거나 정리해 달라.

```text
foundations
components[]
  id, category, label, description
  states[]
  render
  usage
  evidence
layouts[]
  id, label, description
  regions[] { id, label, required, behavior }
  render
  usage
  evidence
templates[]
  id, label, purpose
  layoutId
  componentIds[]
  regions[]
  render
  representativeScreens[]
  evidence
```

- 기존 `screenPatterns`와 `recommendations`는 기계 데이터로 유지할 수 있지만 Builder 디자인 가이드의 독립 탭으로 가정하지 않는다.
- 동일 개념을 `screenPatterns`, `recommendations`, `화면 사례`, `templates`로 중복 제공하지 말고 사용자 노출 단위는 `templates`로 정리한다.
- `componentIds`와 `layoutId`는 반드시 같은 JSON 안의 실제 ID를 참조해야 한다.
- 원시 class, 파일 수, 줄 번호, 진단 내용은 접힌 근거 정보에서만 사용할 수 있도록 분리한다.

### 렌더 완료 조건

- 각 렌더 대상은 Builder 카드의 격리 scope 안에서 실제 CSS가 적용되어 보여야 한다.
- 빈 fragment, 숨김 DOM, 카드 밖으로 밀린 요소, 의미를 잃을 정도로 축소된 요소는 `visible`로 내보내지 않는다.
- 고정폭 원본을 그대로 잘라 가로 스크롤만 제공하지 않는다. 가이드에서 구조와 상태를 이해할 수 있는 대표 구성이어야 한다.
- Layout은 사이드바·헤더·콘텐츠 관계가 한눈에 보여야 한다.
- Template은 주요 영역과 사용 컴포넌트를 한눈에 구분할 수 있어야 한다.
- 1440px에서 전 항목을 검증하고, 375px에서는 반응형이 실제로 존재하는 항목만 검증 결과를 제공한다.
