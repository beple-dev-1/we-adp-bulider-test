# FRD 워크트리는 언제 만들고 언제 없애는가

> **이 문서가 답하는 질문 하나: FRD 작업의 워크트리는 언제 만들고 어떻게 다시 사용하는가.**

**2026-08-20 확정.** 받은 문서·요구사항·요구사항정의서·BRD는 현재 Builder의 작업 흐름에서 제거됐다.
현재 작업 단위는 FRD다.

## 결론

```text
요구사항 입력·AI 인터뷰
  → 분석 결과 확인(PICKED)
  → 개발 범위 확인(SCOPE_REVIEW)
  → 사용자가 [FRD 작업하기]를 누름
  → FRD 전용 브랜치·워크트리 생성 또는 기존 것 재사용
  → 생성 성공
  → 수정 중(DRAFTING)으로 전환하고 작업대 진입
```

**`FRD 1개 = 작업 1개 = 워크트리 1개 = 한 사람`**이다.

분석과 인터뷰는 기획 저장소를 읽어 범위를 정하는 단계이므로 워크트리가 필요 없다. 사용자가 개발 범위를
확인하고 실제 산출물을 고치기로 결정하는 `FRD 작업하기`가 최초 쓰기 시점이며, 이때 워크트리를 만든다.

## 이름과 기준점

| 항목 | 규칙 |
|---|---|
| 브랜치 | `frd/{FRD DB ID}`. 예: `frd/0000025` |
| 폴더 | `{ProjectPaths.worktreeRoot(projectId)}/frd-{FRD DB ID}` |
| 분기 기준 | 버튼을 누른 시점의 프로젝트 클론 `HEAD` |
| 소유자 | FRD의 `owner_account_id` |

화면용 번호 `FRD-025`가 아니라 변경되지 않는 DB ID를 쓴다. 화면 번호는 표시용이고, DB ID는 주소·브랜치·폴더를
같은 값으로 다시 계산하는 복구 열쇠다.

## 생성 계약

1. FRD가 `SCOPE_REVIEW`인지 확인한다.
2. 프로젝트 클론과 기본 브랜치가 정상인지 확인한다.
3. 같은 FRD의 생성 요청을 한 번에 하나만 처리한다.
4. 정해진 브랜치와 워크트리가 없으면 새로 만든다.
5. 이미 같은 짝으로 존재하면 새로 만들지 않고 재사용한다.
6. 워크트리 확인이 끝난 뒤에만 FRD를 `DRAFTING`으로 바꾼다.
7. 생성에 실패하면 FRD는 `SCOPE_REVIEW`에 남기고, 이유와 다시 시도할 행동을 화면에 알린다.

Git 파일 작업과 DB 상태 변경은 하나의 트랜잭션이 될 수 없다. 따라서 **워크트리 성공 → 상태 전환** 순서를
지킨다. 새 워크트리를 만든 뒤 상태 전환이 실패하면 방금 만든 빈 워크트리만 보상 정리한다. 기존 워크트리는
사용자 변경이 있을 수 있으므로 자동으로 지우지 않는다.

## 다시 열기와 예외

- 목록에서 `DRAFTING` FRD를 다시 열면 같은 워크트리를 사용한다.
- 브라우저나 서버를 다시 시작해도 DB ID로 브랜치와 폴더를 다시 계산한다. 별도 워크트리 경로 열은 두지 않는다.
- 브랜치만 있고 워크트리가 없으면 그 브랜치로 워크트리를 다시 연결한다.
- 폴더가 Git에 등록되지 않았거나 다른 브랜치를 가리키면 덮어쓰거나 삭제하지 않고 복구가 필요하다고 알린다.
- 이 기능 도입 전에 이미 `DRAFTING`이 된 FRD만 작업대 최초 진입에서 같은 생성 계약으로 보완한다.
- 화면을 선택하지 않은 FRD도 문서·API·권한·배치 작업을 할 수 있으므로 워크트리를 만든다.
- `다시 인터뷰하기`는 범위를 다시 정하는 행동이다. `FRD 작업하기` 전에는 워크트리를 만들지 않는다.

## 종료 계약

워크트리는 `REVIEW` 동안에도 유지한다. `DONE` 표시만으로 지우지 않는다. 기획 저장소 커밋과 원격 반영이
성공한 뒤에만 워크트리를 제거하며, 제거 전에 미커밋 변경이 없는지 확인한다. 원격 반영 기능이 아직 없다면
워크트리를 보존한다.

⛔ **워크트리 제거는 브랜치 삭제가 아니다 (2026-08-24 병주 확정).** 작업을 닫을 때 **브랜치는 남긴다** —
그것이 「무엇을 왜 그렇게 바꿨나」를 되짚을 유일한 근거다. 「닫는다 = 밀고 · 워크트리를 지우고 · 잠금을 푼다」는
옛 관용구가 이 문서 밖에 여럿 남아 있는데, **그 관용구에 브랜치 삭제를 얹지 마라.**

⛔ **그리고 작업을 닫을 때 to-be 를 기본 브랜치의 `core/<시스템>/pages/` 로 병합하지 않는다.**
그 폴더는 **as-is(사실)** 를 담는 자리이고, 사실을 실어 오는 것은 개발의 역류다
(→ `docs/superpowers/specs/2026-08-07-dev-feedback-design.md`). 병합하면 `pages/` 가 **기획이 그린 것**을
담게 되고 **다음 FRD 가 그것을 as-is 로 읽는다.**
⚠ **워크트리 브랜치 안에서 `pages/<화면ID>.html` 을 쓰는 것은 금지가 아니다** — `ScreenMockupWorker` 가
그렇게 하고 있고 꾸러미가 그 자리에서 재료를 뽑는다. **막는 것은 기본 브랜치로 넘어가는 것 하나다.**

즉 **「FRD 작업 완료」가 하는 일은 「작업 닫기 + 브랜치 보존」까지다.**

개발요청서를 보낸 뒤에는 GitLab 이슈의 개발 상태를 별도로 확인한다. `done` 라벨을 확인하면
개발요청서에 `DONE`만 기록한다. 외부 개발 상태는 병합 승인과 같지 않으므로 자동으로 병합하지 않는다.
사용자가 개발요청서 상세에서 `개발 결과 반영`을 명시적으로 선택하면 전송할 때 굳힌 FRD 커밋을
기획 저장소 기본 브랜치에 병합한다. 병합이 실패하면 `DONE`은 유지하며 사용자가 원인을 확인한 뒤
다시 병합할 수 있다.
