# FRD 요구사항 분석을 인터뷰로 어떻게 진행할 것인가

## 결론

FRD 작업 만들기는 요구사항을 한 번에 분석해 화면 후보를 내는 기능이 아니라, **AI가 근거를 조사하고 불명확한 판단만 한 질문씩 확인한 뒤 분석 결과를 확정하는 인터뷰**로 바꾼다.

```text
요구사항 입력
  → AI 조사
  → 답이 필요한 판단이 있나?
      ├─ 있음: 질문 1개 → 사용자 답변 → AI 조사 계속
      └─ 없음: 분석 결과 정리
  → 사용자가 프론트·백엔드 범위와 화면을 확인
  → 분석 결과 확정
  → 개발 범위 확인
      ├─ 백엔드 변경만: [개발요청서 바로 만들기] → 개발요청서 검토
      └─ 화면 작업 있음: [FRD 작업하기] → 워크트리 생성 → FRD 작업대
```

AI가 다음 판단을 확신할 근거가 부족하면 질문한다. 질문은 한 번에 하나씩 기본 최대 5개까지 할 수 있고, 사용자는 언제든 `현재 내용으로 범위 정리`를 선택해 인터뷰를 끝낼 수 있다.

- 기존 화면 변경인지 신규 화면 추가인지
- 화면 변경과 함께 API·배치·권한·데이터 변경이 필요한지
- 이미 있는 기능을 운영하는 일인지 새 개발인지
- 여러 시스템 가운데 어느 시스템까지 작업 범위인지
- 오류·권한·보관 기간처럼 완료 기준에 영향을 주는 조건

## 기술 검토

### 지금 되는 것

- `ScreenPickWorker`가 Claude Code를 비동기로 실행한다.
- `CliClaudeRunner`는 `--output-format stream-json`을 읽어 도구 호출과 AI 설명을 실행 중에 전달한다.
- `AiProgress`는 최근 실행 내용 20건을 메모리에 보관한다.
- FRD 마법사 화면은 5초마다 새로고침해 실행 내용을 보여 준다.
- 설치된 Claude Code 2.1.234는 `--input-format stream-json`, `--resume`, `--session-id`, `--brief`를 지원한다.

따라서 채팅 모양의 실시간 분석 과정과 사용자 질문을 만드는 것은 가능하다.

### 구현 전 구조에서 그대로는 안 됐던 것

- `CliClaudeRunner`는 stdin을 `NUL`로 연결하므로 실행 중 사용자 답변을 보낼 수 없다.
- Claude 실행이 끝날 때까지 한 메서드가 기다리며 계정별 실행 잠금을 잡는다.
- `AiProgress`는 서버 메모리에만 있고 실행이 끝나면 지워진다.
- 구현 전 FRD 상태에는 `답변 필요`가 없었다.
- 질문·답변·판단 변경 이력을 저장하는 데이터가 없다.

### 선택한 구현 방향

첫 구현은 **실행을 오래 붙잡는 양방향 프로세스가 아니라 턴 단위 실행**으로 한다.

1. AI가 요구사항과 기획 저장소를 조사한다.
2. 답이 필요하면 최종 결과 대신 질문 하나를 구조화된 JSON으로 반환하고 실행을 끝낸다.
3. 서버가 질문과 조사 요약을 DB에 저장하고 FRD를 `답변 필요`로 바꾼다.
4. 사용자가 답하면 답변을 DB에 저장하고 다음 AI 실행을 시작한다.
5. 다음 실행에는 요구사항 원문과 지금까지의 질문·답변을 함께 제공한다.
6. 질문이 없으면 분석 결과를 저장하고 `분석 결과 확인`으로 넘긴다.

이 방식은 사용자가 브라우저를 닫거나 서버가 재시작되어도 질문과 답변이 남는다. 사용자가 답을 기다리는 동안 Claude 프로세스·자격 파일·계정 잠금도 유지하지 않는다.

Claude 세션 재개는 첫 구현에 넣지 않는다. 매 턴 필요한 맥락을 명시적으로 다시 제공한다. 비용이 늘 수 있지만 실행 복구와 자격 파일 삭제 규칙이 단순하다. 이후 실측에서 비용이 문제가 되면 `--session-id`와 `--resume`을 붙인다.

## 사용자 화면

### 1. 요구사항 입력

- 요구사항 내용
- 가져온 출처가 있으면 출처 표시
- 분석이 확인할 항목 안내
- 주요 행동 `요구사항 분석 시작`

버튼을 누르면 FRD 줄을 먼저 만들고 분석 화면으로 이동한다. 분석 중 브라우저를 닫아도 목록에서 다시 열 수 있다.

### 2. 분석 중

화면은 자유 채팅창이 아니라 현재 질문에 집중하는 구조로 표시한다.

- 왼쪽: 요구사항 원문, AI 질문, 질문 이유, 선택지와 직접 입력
- 오른쪽: 진행 상황, 관련 화면, 지금까지 확인한 범위

항상 열려 있는 자유 대화 입력창은 두지 않는다. 분석 결과를 고칠 때만 `내용 보완하기`로 입력창을 연다. 파일 경로와 도구 호출은 사용자 화면에 섞지 않고 진행 상황으로 요약한다.

### 3. 답변 필요

질문은 한 번에 하나만 한다. 질문에는 세 요소가 필요하다.

1. 무엇을 결정해야 하는지
2. 왜 묻는지와 찾은 근거
3. 서로 겹치지 않는 선택지와 직접 입력

예시:

> 현재 운영 화면에는 결재 문서 작성 화면이 있습니다. 임시 저장은 이 화면에 기능을 추가하는 것인가요, 별도 작성 화면을 새로 만드는 것인가요?

- 기존 작성 화면에 추가
- 새 작성 화면 추가
- 아직 결정하지 않음
- 직접 입력

사용자가 `아직 결정하지 않음`을 고르면 AI가 사실을 만들어 확정하지 않는다. 분석 결과의 `확인 필요`에 남긴다.

### 4. 분석 결과 확인

결과는 다음 순서로 보여 준다.

1. 사용자 목표
2. 요구사항 항목별 성격: 개발·운영·외부
3. **수정할 프론트**: 기존 화면 변경·신규 화면과 화면별 변경 내용
4. **수정할 백엔드**: API·데이터·권한·배치·알림과 변경 여부
5. 요구사항 항목별 프론트·백엔드 구현 연결
6. 완료 기준
7. 확인 필요
8. 근거가 된 인터뷰 답변

사용자는 프론트 영역에서 AI가 놓친 현재 운영 화면이나 신규 화면을 직접 추가할 수 있다. 추가할 때 화면과 수정할 내용을 함께 적는다. 화면 확인을 별도 단계로 다시 반복하지 않는다.

사용자는 `다시 인터뷰하기` 또는 분석 결과 확정을 선택한다. 결과를 확정하면 `개발 범위 확인` 상태로 이동한다.
화면·흐름·API 계약·DB·권한처럼 별도 설계가 필요한 변경은 `FRD 작업하기`로 전용 워크트리를 만들거나 기존 워크트리를 재사용하고, 성공한 뒤에만 작업대를 연다.
**백엔드만 변경하는 요청**은 AI가 빠른 진행(FAST_TRACK)을 권장할 수 있다. 화면 작업이 하나도 없고 미결 사항이 없을 때만 `개발요청서 바로 만들기`를 제공하며, FRD 기록과 분석 근거는 유지하되 워크트리와 FRD 작업대는 생략한다. 사용자는 권장과 무관하게 FRD 작업으로 진행할 수 있다.

> **2026-09-02 개정 (병주 확정).** 종전에는 「기존 화면 한 곳의 단순 문구·노출·링크·스타일」
> 간단 변경도 빠른 진행 대상이었다. 그 몫은 FRD 밖의 **SRT(빠른 개발요청)** 메뉴가 받는다 —
> FRD 인터뷰의 빠른 진행은 **백엔드 변경만 있을 때 하나**이고, 화면이 하나라도 있으면
> `FrdCompletionService.completeFastTrack` 이 거절한다. 화면 변경 기준을 되살리지 마라.
정본은 `docs/frd-worktree-lifecycle-design.md`다.

## 상태

FRD 상태는 화면에 다음 말로 보인다.

| 코드 제안 | 화면 문구 | 뜻 |
|---|---|---|
| `ANALYZING` | 요구사항 분석 중 | Claude가 저장소와 요구사항을 조사하고 있다 |
| `WAITING_ANSWER` | 답변 필요 | 질문이 저장됐고 사용자 답변을 기다린다 |
| `ANALYSIS_FAILED` | 요구사항 분석 오류 | 실행이 끝나지 못해 다시 분석해야 한다 |
| `PICKED` | 분석 결과 확인 | 인터뷰가 끝났고 결과 확정을 기다린다 |
| `SCOPE_REVIEW` | 개발 범위 확인 | 분석 결과를 확정했고 FRD 작업 시작을 기다린다 |
| `DRAFTING` | 수정 중 | 워크트리를 준비하고 FRD 작업을 시작했다 |
| `REVIEW` | 검토 필요 | 작업 결과를 검토하고 있다 |
| `DONE` | 완료 | 기획 저장소 반영까지 끝났다 |

`답변 필요`는 단순한 다음 행동이 아니라 AI 실행이 멈춘 작업 상태이므로 별도 상태가 필요하다.

## 저장할 정보

질문·답변은 실행 로그와 다르므로 DB에 보관한다.

### 인터뷰

- FRD ID
- 현재 상태
- 현재 질문 번호
- 분석 시작·마지막 활동 시각
- 오류 내용

### 인터뷰 메시지

- 메시지 ID와 순서
- 역할: 사용자·AI·시스템
- 종류: 분석 요약·질문·답변·결과 안내
- 본문
- 질문 선택지
- 질문이 근거로 삼은 화면·업무 규칙
- 만든 시각

도구 호출과 파일 경로는 영구 메시지로 저장하지 않는다. 지금처럼 `AiProgress`에 일시적으로 둔다.

## 서버 동작 제안

```text
POST /projects/{p}/artifacts/frds
  요구사항 저장 + FRD 생성 + 첫 분석 시작

GET /projects/{p}/artifacts/frds/{f}/interview
  인터뷰 전체 화면

GET /projects/{p}/artifacts/frds/{f}/interview/feed
  채팅·실행 상태 조각

POST /projects/{p}/artifacts/frds/{f}/interview/answers
  현재 질문 답변 저장 + 다음 분석 시작

POST /projects/{p}/artifacts/frds/{f}/interview/finish
  현재까지 확인한 내용으로 결과 정리 요청

POST /projects/{p}/artifacts/frds/{f}/interview/continue
  분석 결과에서 추가 질문 요청

POST /projects/{p}/artifacts/frds/{f}/interview/confirm
  프론트·백엔드 분석 결과 확정 + 개발 범위 확인으로 이동

POST /projects/{p}/artifacts/frds/{f}/start
  워크트리 생성·재사용 + 성공 후 FRD 작업 열기

POST /projects/{p}/artifacts/frds/{f}/fast-track
  워크트리 없이 개발요청서 생성 + 검토 화면 열기
```

화면 갱신은 기존 기술에 맞춰 HTMX 조각 폴링을 우선한다. 분석 중에는 1초, 변화가 없으면 3초로 늦춘다. 질문이 도착하면 폴링을 멈춘다. WebSocket은 여러 서버 사이의 연결 공유가 필요해지는 시점까지 도입하지 않는다.

## AI 출력 계약

AI는 매 턴 다음 둘 중 하나만 반환한다.

```json
{
  "type": "QUESTION",
  "analysisSummary": "현재 운영 화면과 저장 API 존재 여부를 확인했다.",
  "question": {
    "topic": "신규 화면 여부",
    "text": "기존 작성 화면에 추가하는 기능인가요?",
    "reason": "현재 운영 화면에서 작성 화면을 찾았지만 별도 화면 요청인지 원문만으로 확정할 수 없다.",
    "options": ["기존 화면에 추가", "새 화면 추가", "아직 결정하지 않음"]
  }
}
```

```json
{
  "type": "RESULT",
  "title": "결재 문서 임시 저장",
  "items": [],
  "implementationScopes": ["SCREEN", "API", "DATA"],
  "acceptanceCriteria": [],
  "openIssues": [],
  "workMode": "FRD",
  "workModeReason": "API와 데이터 계약을 함께 설계해야 한다."
}
```

AI가 질문을 너무 많이 하지 않도록 다음 규칙을 둔다.

- 저장소 근거로 답할 수 있으면 묻지 않는다.
- 화면명·버튼명처럼 결과에 영향이 작은 표현은 묻지 않는다.
- 작업 범위·완료 기준·신규 화면 여부를 바꾸는 판단만 묻는다.
- 같은 질문을 표현만 바꿔 다시 묻지 않는다.
- 인터뷰는 기본 5문 이내이며, 더 필요하면 이유를 표시한다.

## 오류와 복구

- 분석 실패: 마지막 사용자 답변은 유지하고 `다시 분석하기`를 제공한다.
- 브라우저 종료: 목록의 `답변 필요` 상태에서 인터뷰로 돌아온다.
- 서버 재시작: DB 메시지에서 이어가며 실행 중이던 턴만 다시 실행한다.
- 사용자가 장시간 답하지 않음: 프로세스가 없으므로 자원을 점유하지 않는다.
- 중복 답변 제출: 질문 ID와 상태를 함께 검사해 첫 답변만 받는다.
- 요구사항 수정: 기존 인터뷰 답변을 자동 재사용하지 않고 새 분석으로 시작한다.

## 구현 상태

- 요구사항 입력과 단위 실행형 인터뷰
- 분석 과정과 질문을 함께 보는 `답변 필요` 상태
- 선택지와 `직접 입력` 답변
- 프론트·백엔드로 분리한 분석 결과와 요구사항별 구현 연결
- 현재 운영 화면과 신규 화면 추가
- 질문·답변·백엔드 변경·완료 기준·확인 필요 항목의 DB 저장
- 서버 재시작 뒤 `ANALYZING` 상태의 단위 실행 재제출
- Opus·high 추론으로 최대 5개의 구조화 질문 진행과 사용자 조기 종료
- 단순 변경의 개발요청서 빠른 진행과 FRD 기록 유지

구현 정본은 `V23__frd_requirement_interview.sql`, `FrdInterviewService`,
`ScreenPickWorker`, `frd-wizard.html`이다.
