# 개발 결과 받기 — 시험용 회신 만드는 법 (FRD · SRT)

> **읽는 사람: 테스터를 돕는 Claude.** 테스터가 빌더에서 「개발에 넘기기」를 누른 뒤,
> 개발팀 대신 **시험용 회신**을 만들어 기획 저장소에 올리고 「개발 결과 받기」를 시험하게 돕는다.
> 실제 개발을 하는 것이 아니다 — 빌더가 받는 모양을 갖춘 회신을 만드는 것이다.

> ⚠ **기획 저장소 `dev-requests` 브랜치의 `TESTING.md` 는 이 문서의 사본이다.** 고치면 그쪽도 같이 올린다.

⛔ **기획 저장소에 브랜치를 올리는 일이다.** 올리기 전에 테스터에게 브랜치 이름과 무엇을 담는지
말하고 확인을 받는다. 토큰·비밀번호를 파일이나 명령에 적지 않는다 — 올리기는 테스터 PC 의 git 자격 증명으로 한다.

## 0. 먼저 알 것

- 빌더가 넘긴 것은 기획 저장소의 **전달 브랜치** `dr/<시스템>/DR-nnn` 에 있다. 그 안의
  `DR-nnn/expected-back.md` 가 **이 요청의 회신 규칙 원문**이다. 이 문서보다 그것이 우선이다.
- 돌려보낼 브랜치 이름 · 갈라 올 기준 커밋 · 화면 목록 · TC 번호는 **`expected-back.md` 에서 그대로 옮긴다.**
  ⛔ 이름을 짐작해 짓지 않는다 (예: 시스템 자리가 `SRT` 로 나간 요청서도 있다 — 적힌 대로 쓴다).
- 빌더는 `expected-back.md` 를 읽지 않는다. **회신 브랜치의 정해진 자리에 놓인 파일만** 읽는다.

## 1. 전달 꾸러미 읽기

```bash
git clone https://github.com/beple-dev-1/we-adp-repository-test.git planrepo   # 이미 있으면 git fetch origin
cd planrepo
git fetch origin
git branch -r | grep "dr/"                       # 넘겨진 전달 브랜치 목록
git show origin/dr/<시스템>/DR-nnn:DR-nnn/expected-back.md
git show origin/dr/<시스템>/DR-nnn:DR-nnn/manifest.json
```

`expected-back.md` 에서 다음을 옮겨 적는다.

| 무엇 | 어디 |
|---|---|
| 돌려보낼 브랜치 | 머리 표 「돌려보낼 브랜치」 — `feedback/<시스템>/DR-nnn` |
| 기준 커밋 | 머리 표 「갈라 올 기준 커밋」 |
| 화면과 필수 구성요소 | 1절 표 — 화면ID 마다 `pages` · `screen-md` · `index` |
| 통합테스트 TC | 4절 표 — 완료 조건마다 `TC-nnn` |
| 단위테스트 TC | 3절 표 — 화면 외 구현마다. 「아직 시나리오가 없습니다」면 보낸 번호가 없다 |

## 2. 회신 브랜치 따기 — 기준 커밋에서

```bash
git switch -c feedback/<시스템>/DR-nnn <기준 커밋>
```

⛔ **전달 브랜치(`dr/...`) 위에서 따지 않는다.** 거기엔 기획이 그린 to-be 가 있어, 빌더가
「갈라 온 기준이 기본 브랜치 이력에 없습니다」로 통째로 거절한다.

## 3. 화면 파일 놓기

1절 표의 화면마다, 바꾼 구성요소만 제자리에 놓는다.

| 구성요소 | 자리 | 시험용으로 만드는 법 |
|---|---|---|
| `pages` | `core/<시스템>/pages/<화면ID>.html` | 아래 참고 |
| `screen-md` | `core/<시스템>/pages/<화면ID>.md` | 바뀐 동작 한두 줄을 해당 항목에 적는다 |
| `index` | `index.json` 의 그 화면 줄 | 화면 이름·종류·메뉴가 안 바뀌었으면 건드리지 말고 `unchanged` |

**화면 html 을 만드는 법은 요청서 종류마다 다르다.**

- **FRD 요청서** — 전달 꾸러미에 기획이 그린 to-be 가 있다. 그것을 「개발이 구현한 결과」로 쓴다.
  ```bash
  git show origin/dr/<시스템>/DR-nnn:DR-nnn/screens/<시스템>/<화면ID>/to-be.html > core/<시스템>/pages/<화면ID>.html
  git show origin/dr/<시스템>/DR-nnn:DR-nnn/screens/<시스템>/<화면ID>/to-be.md   > core/<시스템>/pages/<화면ID>.md
  ```
- **SRT 요청서** — to-be 가 없다(`as-is.html` · `as-is.md` · `changes.md` 만 있다). 기준 커밋의 화면 html 을
  `changes.md` 와 요구사항대로 **작게 직접 고친다.** 그 화면의 기존 CSS 클래스만 쓰고 `style` 속성·`<style>` 을 새로 넣지 않는다.

⛔ 1절 표에 없는 화면은 놓지 않는다 — 「돌려받을 목록에 없는 화면입니다」로 거절된다.
⛔ `ia.md`(메뉴구조도)는 받지 않는다.

## 4. 회신서 `DR-nnn/return.json`

`expected-back.md` 의 견본을 그대로 옮기고, 칸마다 `changed` 또는 `unchanged` **하나**로 바꾼다.
`base` 는 2절의 기준 커밋이다.

```json
{
  "dr" : "DR-014",
  "base" : "<기준 커밋>",
  "screens" : [
    { "screenId" : "EXW-UWV-70-30-10-C", "pages" : "changed", "screen-md" : "changed", "index" : "unchanged" }
  ]
}
```

- `changed` 로 적은 구성요소는 3절의 자리에 파일이 **실제로 바뀌어 있어야** 한다.
- `unchanged` 는 「보았고 바꿀 것이 없었다」는 뜻이다.
- 1절 표의 화면은 **하나도 빠짐없이** 적는다 — 빠지면 「돌려받아야 할 화면이 안 왔습니다」.

## 5. 테스트 결과 `DR-nnn/return/integration-tests.md` · `unit-tests.md`

`expected-back.md` 4절(통합)·3절(단위) 표를 **그대로 복사**하고, 줄마다 **마지막 세 칸만** 채운다.

| 칸 | 채우는 것 |
|---|---|
| 실제 결과 | 시험해서 본 것 한 문장 |
| 판정 | `통과` · `PASS` · `OK` 또는 `실패` · `FAIL` · `NG` — ⚠ 다른 말은 「모름」으로 센다 |
| 근거 | 무엇으로 확인했나 (예: 「로컬 시험 서버 화면 확인」) |

- 표는 **9칸**이다 (TC · 무엇을 보나 · 의존 · 조건 · 행위 · 기대 결과 · 실제 결과 · 판정 · 근거).
  칸을 빼거나 합치면 그 줄을 못 읽는다. 칸 안에 `|` 를 쓰려면 `\|` 로 적는다.
- ⛔ **앞의 여섯 칸은 고치지 않는다.** ⛔ **보낸 적 없는 TC 번호를 더하지 않는다** — 통째로 거절된다.
- 시험용이라도 일부를 `실패` 로 적어 보면 빌더 화면이 통과·실패를 가르는지까지 볼 수 있다.
- 3절이 「아직 시나리오가 없습니다」면 `unit-tests.md` 는 없어도 되고, 같은 9칸 서식으로 적으면 그대로 받는다.

⚠ `return.json` 과 `return/` 은 기본 브랜치로 합쳐지지 않는다 — 빌더가 읽어 판정하고 테스트 결과를 담을 뿐이다.

## 6. 올리기

```bash
git add core/<시스템>/pages/ DR-nnn/return.json DR-nnn/return/
git commit -m "DR-nnn 시험용 개발 결과"
git push origin feedback/<시스템>/DR-nnn      # ⛔ 테스터 확인을 받은 뒤
```

그다음 테스터에게 「빌더의 DR-nnn 상세에서 **개발 결과 받기**를 누르세요」라고 알린다.

## 7. 빌더가 거절하는 경우 — 받은 사유와 고치는 법

빌더에는 「개발 결과를 받지 못했습니다 — 사유 · 사유」로 뜬다. 거절이면 기획 저장소도 빌더 DB 도 **아무것도 안 바뀐다.** 고쳐서 같은 브랜치에 다시 올리고 다시 누르면 된다.

| 빌더에 뜨는 사유 (앞부분) | 고치는 법 |
|---|---|
| 회신서를 읽지 못했습니다 | `DR-nnn/return.json` 자리 · JSON 문법을 본다 |
| 회신서에 갈라 온 기준(base)이 없습니다 | `base` 를 채운다 |
| 갈라 온 기준이 기본 브랜치 이력에 없습니다 | 전달 브랜치가 아니라 기본 브랜치의 기준 커밋에서 다시 딴다 |
| 돌려받을 목록에 없는 화면입니다 | 1절 표에 없는 화면을 뺀다 |
| 필수 구성요소가 안 왔습니다 | 그 화면의 `pages` · `screen-md` · `index` 를 모두 적는다 |
| 모르는 상태값입니다 | `changed 또는 unchanged` 를 하나로 바꾼다 |
| 돌려받아야 할 화면이 안 왔습니다 | 1절 표의 화면을 회신서에 모두 적는다 |
| 갈라 온 뒤 기본 브랜치에서 이 파일이 바뀌었습니다 | 그 파일을 지금 기본 브랜치 것과 합치고 `base` 를 기본 브랜치의 지금 머리로 고친다 |
| 보낸 적 없는 … TC 입니다 | 표에 없는 TC 줄을 지운다 |

## 8. 받은 뒤 확인

- 빌더 DR-nnn 상세에 「개발 결과를 반영했습니다. 테스트 결과 N줄을 담았습니다.」가 뜬다.
  화면 파일을 모두 `unchanged` 로 보냈으면 「받을 변경이 없었습니다」, 같은 회신을 다시 받으면 「이미 받은 판입니다」 — 둘 다 거절이 아니다.
- 기획 저장소 기본 브랜치에 `chore: DR-nnn 개발 결과 반영` 커밋이 생기고, `changed` 로 적은 화면 파일만 들어가 있다.
  ```bash
  git fetch origin && git log --oneline -3 origin/main
  git show --stat origin/main
  ```
- 채운 테스트 결과는 빌더 DB 에 TC 한 줄씩 담긴다 — 메시지의 「테스트 결과 N줄」이 그 수다. (그린존의 단위·통합테스트 화면은 아직 없다.)
