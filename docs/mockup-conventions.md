# 목업을 어떻게 만드나 — 화면 규칙

> **이 문서가 답하는 질문 하나: 화면을 만들거나 고칠 때 무엇을 지키나.**
> **목업(`docs/mockups/`)과 템플릿(`templates/`) 둘 다다** — 둘은 같은 스타일시트를 함께 쓴다.
> 어떤 화면이 있나는 여기 없다 — `docs/mockups/_README.md` 다.
> 데이터 구조는 `docs/data-model.md`, 코드 이름 규칙은 `docs/coding-conventions.md` 다.

**목업이 화면의 정본이다.** 설계 문서와 어긋나면 목업이 이긴다. 그래서 목업을 고치는 것은
문서를 고치는 것이 아니라 제품을 정하는 것이다.

## 제품 맥락

- 왼쪽 메뉴는 현재 산출물의 진입점이며 **실제 화면 수와 같지 않다.** 산출물 하나가
  목록·상세·작업대 화면을 따로 가질 수 있다.
- **메뉴 열쇠·순서·표시 이름의 정본은 `ShellContract.java` 와 `fragments/parts.html` 이다.**
  목업의 `_shell.js` 는 그 사본이다. ⛔ **순서를 손으로 외워 적지 마라 — `parts.html` 의
  `nav` 조각에서 확인한다.**
- FRD 요구사항은 사용자가 직접 입력하며, 접수처의 적용 구분을 함께 고를 수 있다.
- 수정할 솔루션 목업 화면 선택은 **선택 사항**이다. 화면을 고르지 않아도 백엔드·권한·배치·문서
  범위로 FRD 작업을 시작할 수 있다.

## 화면 구성

- **한 HTML 에는 한 시점의 실제 제품 상태만 렌더한다.**
  채워진 상태·빈 상태·오류 상태·로딩 상태를 한 화면에 동시에 놓지 않는다.
- **설계 메모를 제품 화면에 보이는 요소로 넣지 않는다.** 결정 근거는 이 문서, 설계 문서,
  또는 HTML 주석에 남긴다.
- **목록과 작업대를 한 화면에 섞지 않는다.** 간단 확인만 레이어를 고려하고, 입력 항목이 많거나
  원문 대조가 필요한 등록·수정은 독립 화면을 쓴다.
- 기본 위계는 `제목과 주요 행동 → 목적 한 문장 → 검색·필터 → 표 또는 본문` 이다.
- 판단 축이 있는 목록에는 필요한 검색과 필터를 둔다.
- **목록이 아닌 산출물(표 한 장 · 문서 한 장)을 억지로 일반 목록 틀에 맞추지 않는다.**
- 데스크톱 정보 밀도는 6을 기준으로 한다. 모바일에서는 **페이지 전체가 아니라 표 컨테이너만**
  가로로 스크롤한다.

## 무엇으로 만드나 — 새 클래스를 짓기 전에

`coding-conventions.md` 의 **「같은 것을 두 이름으로 부르지 않는다」가 CSS 에도 그대로 걸린다.**
목업과 템플릿은 같은 스타일시트를 함께 쓴다 — 한쪽에서 지은 이름이 다른 쪽의 짐이 된다.

- ⛔ **새 클래스를 짓기 전에, 만들려는 것이 이미 있나 스타일시트에서 찾는다.**
  ⚠ **화면 이름으로 찾으면 안 나온다** — 만들려는 **물건**이 무엇인지로 찾아야 나온다.
- **있으면 그것을 쓴다.** 모양이 조금 다른 것은 새 클래스를 지을 이유가 아니다 —
  **그 클래스에 변형을 더한다.** 변형 짓는 법은 **그 클래스가 이미 쓰는 방식**을 따른다.
- **없을 때만 새로 짓는다.** 짓기 전에 **두 화면 이상이 쓸 것인가**를 자문한다.
  그렇다면 화면 전용 자리가 아니라 **공용 자리**에 둔다.
- ⛔ **색·간격·모서리·그림자를 숫자로 박지 않는다.** 토큰이 `tokens.css` 의 `:root` 에 있다.
  토큰에 없는 값이 필요하면 **그것이 정말 새 값인지** 먼저 묻는다 — 대개는 옆 화면과
  1px·한 톤 어긋난 것이지 새 값이 아니다.
- 쓰지 않게 된 클래스는 **그 자리에서 지운다.** 안 지우면 다음 사람이 그것을 살아 있는 본으로 읽는다.

⛔ **이 문서에 클래스 이름을 적지 마라.** 「무엇무엇이 있다」는 목록은 낡고,
**낡은 목록은 「없구나」 하고 새로 짓게 만든다** — 고치려는 원인 그대로다.
**무엇이 있는지는 문서가 아니라 스타일시트를 열어서 안다.**
이 절이 정하는 것은 목록이 아니라 **순서**다 — 찾기 → 쓰기 → (없으면) 짓기.

> 왜 이 규칙이 있나 (2026-08-27 실측). 화면 36개가 클래스 672개를 지었고 공용 층은 104줄이었다.
> 글자까지 똑같은 것이 나란히 있었고, 어느 화면도 안 쓰는 죽은 것이 89개였다.
> 아무도 마음대로 한 것이 아니다 — **찾아볼 자리를 안 정해 둬서 매번 처음부터 지은 것이다.**

## UX 카피

- 사용자가 이해할 수 있는 **표준 업무 한국어**를 쓴다.
- 버튼과 링크는 결과를 예상할 수 있는 **`목적어 + 행동`** 으로 쓴다.
- 상태는 `내용 추출 중` · `정리 내용 확인` · `요구사항 추출 중` · `검토 필요` · `완료` ·
  `문서 처리 오류` 처럼 **구체적으로** 쓴다.
- **FRD 분석 상태와 작업 상태를 섞지 않는다.** 상태 정본은
  `docs/frd-requirement-interview-design.md` 다.
- **상태와 다음 작업을 같은 말로 뭉개지 않는다.**
- 비유·의인화·훈계·혼잣말을 쓰지 않는다.
- 말 바꾸기: `레포` → **`저장소`**, `as-is` → **`현재 운영 화면`**,
  `재생성물` → 실제 산출물 이름이나 **`자동 생성 문서`**.
- 오류는 **`무슨 일 + 이유 + 다음 행동`** 순서로 쓰며 사용자 탓으로 말하지 않는다.
- 확정되지 않은 파일 형식·용량·자동 처리 기능을 **지원한다고 약속하지 않는다.**

## 접근성과 상호작용

- 모든 입력에는 연결된 `label` 을 둔다.
- 주요 버튼과 링크는 키보드로 접근 가능해야 하며 충분한 조작 영역을 둔다.
- **색만으로 상태를 전달하지 않는다.**
- 표 머리에는 `scope="col"` 을 쓴다.
- 페이지는 하나의 `h1` 로 시작하고 절은 `h2` 순서를 지킨다.

## 공통 셸과 검증

- 제품 목업은 `<template id="본문">` 과 `_shell.js` 를 사용한다.
- ⛔ **Thymeleaf 셸과 목업 셸을 함께 갱신한다. 둘 중 하나만 바꾸지 않는다.**
- ⛔ **메뉴를 바꾸면 `ShellContract.java` · `fragments/parts.html` · `_shell.js` 셋의
  열쇠·순서·이름을 함께 맞춘다.** 하나만 바꾸면 조용히 갈린다.
- 변경 뒤 `python docs/mockups/check_mockups.py` 를 실행한다.
- 제품 목업을 **데스크톱과 375px 너비**에서 확인한다.
  볼 것: 페이지 전체 가로 넘침 · 제목과 주요 행동이 첫 화면에 보이나 · 표 읽기 · 폼 오류.
- `_README.md` 의 화면 목록과 실제 목업 파일을 일치시킨다.
