# 개발과 합의할 것 — 두 가지

> **이 문서가 답하는 질문 하나: 빌더와 개발이 무엇을 주고받기로 하나.**
>
> **받는 사람**: 개발팀.
> **보내는 쪽**: `we-adk-builder` — 기획자가 브라우저로 붙어 현재 산출물을 관리하는 서버.
> **날짜**: 2026-08-10. **2026-08-09 자를 고쳐 다시 보낸다** — **응답에 관한 질문 둘이 늘었다**
> (상태코드표 · 전송 키 되울림). 그 앞 판(8/9)은 나가는 것이 PRD 에서 개발요청서로 바뀐 것이었다.

## 무슨 사이인가

기획이 업무 하나를 다 정리하면 **개발요청서 한 장이 개발로 나가고**, 개발이 끝나면
**두 가지가 그 번호를 달고 돌아온다.** 창구가 둘이고, 둘 다 형식을 합의해야 선다.

```
빌더 ──[① 나가는 창구]──▶ 개발      개발요청서 한 장 (DR-003)
빌더 ◀──[② 돌아오는 창구]── 개발      ㉮ 테스트 결과 md 둘 → 개발요청서 자리에 앉는다
                                     ㉯ as-is 재동기      → 원자리에 앉는다 (2026-08-24 추가 · 1순위)
```

⚠ **㉯ 는 2026-08-24 에 늘어난 것이다.** 개발이 구현을 끝내면 운영 화면이 바뀌는데
**그것을 기획 레포에 반영할 길이 역류밖에 없다** — 빌더는 운영 소스를 안 읽고, 추출기는
「508화면은 재추출하지 않는다」로 전체 재추출을 닫아 뒀다. 재료를 쥔 쪽이 개발이다.
정본은 `docs/superpowers/specs/2026-08-07-dev-feedback-design.md` 다.

⚠️ **8/8 자와 달라진 것 둘.**

| 8/8 | 지금 |
|---|---|
| **프로젝트 전체 PRD 를 매번 통째로** 보낸다 | **업무 하나분(BRD 하나) = 개발요청서 한 장**을 보낸다 |
| 역류가 **항목 ID** 로 돌아온다 | 역류가 **개발요청서 번호**로 돌아온다 |

**왜 바꿨나**: 개발도 업무 단위로 받아 만든다. 전체를 보내면 「이번에 뭐가 새로 왔나」를
개발이 매번 비교해 찾아야 했고, 회의 하나분을 다 모아 보내면 **업무 셋 중 하나가 늦어서
다 끝난 둘도 못 나간다.**

**빌더 쪽은 잠정안을 다 잡아 놨다.** 아래는 그 잠정안이고, 합의되면 **구현 한 군데만** 고치면 되게 인터페이스 뒤에 가둬 뒀다.

## 1. 나가는 창구 — 개발요청서를 개발에 보내는 형식

기획자가 「개발에 넘기기」를 누르면 빌더가 개발 쪽 주소로 한 번 쏜다.

**빌더의 잠정안:**

| 무엇 | 잠정값 |
|---|---|
| 방식 | `POST {개발이 알려준 주소}` |
| 신원 | 머리 `X-Builder-Key: {개발이 발급한 키}` |
| 몸 | `{"deliveryKey": "01J...", "devRequestId": "DR-003", "businessName": "전자결재", "body": "...", "comment": "...", "previousDevRequestId": "DR-001"}` |
| 성공 | 200·201 **+ 몸에 `deliveryKey` 되울림** |

**정해줄 것**: 실제 주소 · 인증 방식 · 몸의 모양. **개발요청서를 통짜 글로 받나, 구조화해서 받나.**

⭐ **2026-08-24 — 빌더 쪽은 다 서 있다.** 「개발요청 전송」을 누르면 **꾸러미 한 채**가 실제로
만들어지고, 검증을 통과한 것만 나간다. 지금 막힌 것은 **어디로 어떻게 실어보내나** 하나뿐이다.

```
DR-003/
├─ dev-request.md      요청 원문 · 요구사항 전체 · 개발 범위 · 제외 범위 · 완료 조건
│                    · 확인 필요 · 화면 외 구현(API·데이터·권한·배치·알림·기타)
│                    · 화면별 산출물 목록 · 전송 정보 · 첨부 목록
│                    · **개발 완료 후 반환** — `expected-back.md`와 `manifest.json` 안내
├─ expected-back.md   이 DR의 예상 반환 대상과 개발자가 채울 상세 회신 양식의 사람용 정본
├─ manifest.json     규격 판 · DR번호 · 전송 키 · 전송 시각 · 기획레포 커밋SHA
│                    · 앞 DR번호 · **계약 파일**의 경로·크기·SHA-256
│                    · **자산 요약** — 개수·전체 크기·묶음 해시 (낱개로 안 담는다)
│                    · **돌려받을 것** — 표다: 시스템+화면ID · 필수 구성요소
│                      · 화면 md 를 받나 · 도메인+모듈
├─ attachments/
└─ screens/<시스템>/
   ├─ assets/                    목업이 부르는 css·js·이미지
   └─ <화면ID>/
      ├─ as-is.html   to-be.html    현재 운영 화면 / 이렇게 바꿔 주세요
      ├─ as-is.md     to-be.md      현재 기능정의서 / 바뀐 기능정의서
      └─ changes.md                변경 목록 + 화면에 표시한 지시 + 메모
```

`expected-back.md`는 대상 목록에서 끝나지 않는다. 화면 외 구현 항목마다 개발자가 실제 구현 결과와
구현 저장소·모듈·커밋·검증 근거를 채우고, 도메인 반영을 `changed` 또는 `unchanged`로 선언하는
회신 양식을 함께 싣는다. `changed`면 `domains/<도메인>/<모듈>.md`의 변경 후 전체 파일과 기준 커밋,
SHA-256, 바이트 크기를 반환한다. `unchanged`면 파일 대신 변경 없음의 근거와 확인한 코드 위치를 적는다.
도메인 문서에는 책임·업무 규칙·API·데이터·적용 범위·외부 연동·구현 근거를 남기며 비밀값과 실제
개인정보는 넣지 않는다. 화면 외 구현이 0건이어도 실제 도메인 변경과 요청 외 구현 변경 여부를 반드시
확인하게 하고, `changed`·`unchanged` 작성 예시를 한 번씩 싣는다. 요청 당시 특정되지 않은 도메인 변경은
변경 후 전체 문서를 별도 검토용 파일로 받되 `manifest.json`의 자동 수신 대상을 늘리지 않는다. 개발요청서 11절은 상세를 복제하지
않고 `expected-back.md`를 작성해 반환하며 자동 수신 대상으로 처리할 파일과 항목은 `manifest.json`에
맞추라는 안내만 둔다.

- **목업은 혼자 선다.** 화면 폴더에서 `../assets/…` 로 그대로 열린다 — 파일 안을 한 글자도 안 고쳤다
- ⚠ **그래서 자산이 많다** — 실측으로 한 시스템에 **514장**(svg·png·css·woff2·js)이다.
  **`core/<시스템>/assets/` 를 통째로 붓는다** — 그 화면이 무엇을 부르는지 골라내면 **놓치는 순간 목업이 깨진다.**
  ⭐ **다만 `manifest.json` 은 자산을 낱개로 담지 않는다** — 개수·전체 크기·**묶음 해시** 하나다.
  자산은 추출기 원본 그대로라 낱개 검증이 값을 안 한다(그러지 않았을 때 지문이 **121KB** 였다)
- **as-is 를 같이 보낸다.** 계약은 「무엇을 → 무엇으로」라서, 나중에 「원래 그랬다/아니다」를 가릴 근거를 남긴다
- **`manifest.json` 에 규격 판 번호가 있다.** 배치가 바뀌면 그 값이 오른다 — **사람이 읽는 안내문 대신 기계가 갈래를 타면 된다**
- ⚠ **`manifest.json` 은 자기 자신을 목록에 담지 않는다** (자기 해시를 자기 안에 넣을 길이 없다)
- **`manifest.json` 에 「돌려받을 것」 표가 있다.** 대상마다 **시스템+화면ID · 어느 구성요소가 필수인가 ·
  화면 md 를 받는지**, 그리고 도메인+모듈 —
  **㉯ 로 무엇이 돌아와야 하는지가 나갈 때 이미 적혀 있다.** 같은 내용의 사람이 읽는 문서는
  `expected-back.md`로 함께 싣는다. 백엔드 대상이 자연어라 도메인 파일 경로를 확정할 수 없어도
  `expectedBack.backendChanges`에 구현 결과 회신 대상으로 남긴다. 처리 규약과 빌더의 실제 수신·반영은
  이 꾸러미의 범위가 아니다.

**그래서 정해줄 것 하나가 더 있다: 이 꾸러미를 어떻게 받나.**
zip 한 덩어리로 받나 · 파일 여럿을 multipart 로 받나 · 우리가 GitLab 에 올린 뒤 커밋 SHA 와 경로만 받나.
⚠ 셋 중 **마지막은 개발이 기획 저장소를 볼 수 있을 때만** 되는 길이다.

### ⭐ 알아 둘 것 — 전송을 철회할 수 있다 (2026-08-25)

기획자가 보낸 뒤 무를 수 있게 했다. **다만 요구가 아니라 고지다 — 그쪽이 할 일이 없다.**

- **라벨이 `intake` 그대로일 때만** 철회된다. 그쪽이 집어가서 라벨을 바꿨으면 **빌더가 거절한다**
- 철회하면 **`intake` 를 빼고 `withdrawn` 을 붙이고 이슈를 닫는다.** 까닭은 댓글로 남는다
- ⛔ **라벨을 통째로 비우지 않는다** — 그쪽이 붙인 라벨은 그대로 둔다
- 철회한 것은 **고쳐서 다시 보낼 수 있다.** 그때는 **새 이슈**가 열린다(닫힌 이슈를 재활용하지 않는다)

⭐ **이 판정에 합의가 필요 없는 까닭**: `intake` 는 우리가 붙인 「인수 전」 표시이고,
**그쪽이 집어가면 그쪽 워크플로가 라벨을 바꾼다.** 라벨이 그대로인지 보는 것만으로
「아직 아무도 손 안 댔다」가 판정된다 — **그쪽 시스템이 스스로 답을 준다.**

⚠ **그쪽이 `intake` 를 안 떼고 작업을 시작한다면 알려 달라.** 그러면 이 판정이 헛돈다.

**함께 정해줄 것 둘 — 응답에 관한 것이다. 8/8 에도 8/9 에도 없었다.**

- ⭐ **상태코드표.** 어떤 코드를 언제 주나 — 특히 **`202` 를 쓰나**(쓴다면 그건 「접수」인가 「처리 끝」인가),
  그리고 **`409` 를 「이미 받은 것」이라는 뜻으로 쓰나.** 이 둘의 답에 따라 빌더가 「전송완료」로 볼지
  「전송중」으로 볼지가 갈리고, **잘못 읽으면 같은 개발요청서가 두 번 간다.**
- ⭐ **응답 몸에 `deliveryKey` 를 그대로 되울려 줄 수 있나.** 사내 프록시나 로그인 페이지도 `200` 을 주기 때문에,
  **되울림이 없으면 「2xx = 받았다」를 우리가 확인할 길이 없다.** 한 줄이면 된다.

⭐ **`deliveryKey` 는 새 요구가 아니라 고지다.** 세상에 하나뿐인 값이고, **같은 키가 두 번 오면 그건 재시도이지
새 요청이 아니다.** 그쪽이 아무것도 안 해도 우리는 상관없다 — 다만 거를 생각이면 이 키로 걸러 달라.
⚠️ **`devRequestId` 로 거르면 안 된다** — 번호는 **사업마다 1번부터**라 서로 다른 사업의 `DR-001` 이 여럿이다.

**함께 정해줄 것 둘 — 8/8 에는 없던 것이다.**

- **화면별 목업을 어떻게 받나.** 개발요청서에는 화면 여럿의 목업이 실린다.
  HTML 을 몸에 통째로 담나, 파일로 따로 보내나, 기획 레포 링크만 주나.
- **앞 개발요청서를 이어 읽어 주나.** 같은 업무를 두 번 손대면 `DR-003` 뒤에 `DR-009` 가 나간다.
  **전체를 안 보내므로 뒤엣것이 앞엣것을 고치는 것임을 개발이 읽어야 한다.**
  빌더는 `previousDevRequestId` 를 넣어 주는 것으로 잡았다.

**빌더 쪽 준비**: 개발 창구의 주소와 키는 **관리 화면에서 사람이 넣는다.** 키는 봉인해 DB 에 둔다. 키를 바꾸면 사람이 다시 넣는다 — **기간 만료는 두지 않았다.**

**개발이 「요청 자체를 안 받았다」는 뜻의 4xx 를 주면**(400·401·403·404·413·415·422)
**아무것도 안 나간 것으로 둔다.** 빌더가 몰래 다시 쏘지 않는다. 사람이 다시 누른다.

⛔ **4xx 를 통째로 「안 나갔다」로 읽지 않는다.** `408`·`429` 는 「지금 말고 나중에」이고,
**`409` 는 오히려 「이미 받았다」일 수 있다** — 그래서 위에서 상태코드표를 물었다.
답이 오기 전까지 빌더는 그 셋을 **「전송중」**으로 둔다(다시 누르는 것을 막는 쪽이 안전하다).

⚠️ **답을 못 받은 것은 「안 나갔다」가 아니다.** 시간 상한이나 연결 끊김은 **개발이 이미 받았을 수 있다.**
그건 빌더가 **「전송중」**으로 남겨 두고 **다시 누르는 것을 막는다** — 그래서 두 번 갈 일이 아주 드물다.

⛔ **다만 0 은 아니다. 우리가 「빌더가 중복을 막아준다」고 말하지 않는 이유다.**
「전송중」에서 나오는 문은 사람이 여는데, **관리자가 물어본 시점과 그 답을 쓰는 시점 사이에
원 요청이 늦게 착지하면 두 번 간다.** 빌더는 그 문에 시계를 걸어 위험을 좁히지만 없애지는 못한다.
**그러니 그쪽 방어를 우리 말 믿고 빼지 마라** — 걸러 낼 생각이면 위의 `deliveryKey` 로 거르면 된다.

⚠️ **한 번 쏜 뒤의 일은 빌더가 안에서 감당한다 — 개발 API 에 새로 요구할 것이 없다.**
쏘고 나서 빌더가 기획 레포에 저장하는 단계가 남는데, 그것만 실패하면
빌더는 **「이미 쐈다」를 기록해 두고 다시 누를 때 저장만 다시 한다.**
⛔ **개발 쪽에 「같은 번호가 두 번 오면 걸러 달라」고 요구하지 않는다.**

**다만 사람 손이 드는 자리 하나가 남는다** — 위의 「전송중」이다. 빌더는 그것이 갔는지 **끝내 모른다.**
그때는 **빌더 관리자가 개발팀에 「DR-003 받았나」를 물어보고**, 받은 답을 관리 화면에서 골라 넣는다
(「받았다」면 저장만 다시 하고, 「못 받았다」면 처음부터 다시 보낸다). 드물지만 실재하는 자리다.
**API 를 새로 만들어 달라는 요청은 아니다** — 사람끼리 확인하면 된다.
⚠️ 만약 개발 쪽에 **「그 번호를 받았는지 조회하는 길」**이 이미 있으면 알려주면 좋다. 그러면 그 손이 없어진다.

## 2. 돌아오는 창구 — 개발이 빌더에 미는 형식

개발이 만든 것이 **개발요청서 번호를 달고** 빌더로 온다. 빌더가 받아서 기획 레포에 커밋한다.

**그 번호는 우리가 적어 보낸 것이라 개발이 새로 알아낼 것이 없다.**

**돌려받을 것이 두 갈래다** (2026-08-24 개정 — ㉯ 가 늘었다 · **2026-08-25 개정 — ㉮ 가 다섯에서 둘로 줄었다**).

| 갈래 | 무엇 | 앉는 자리 |
|---|---|---|
| **㉮ 테스트 결과** | **단위테스트 결과 md** · **통합테스트 시나리오 md** — 둘뿐이다. 아래 「㉮ 의 구조」 | 개발요청서 자리 |
| **㉯ as-is 재동기** | `pages/<화면ID>.html` · 화면 md · `index.json` 의 그 화면 조각 · 도메인 md · **「확인했고 변경 없음」** — **1순위다** | 원자리 (`core/<시스템>/` · `domains/` · 색인) |

**㉮ 가 줄어든 까닭 셋** (병주 확정 2026-08-25):

- **기능명세서는 따로 받지 않는다.** ㉯ 로 갱신된 화면 html·md·메뉴구조도에서 **Builder가 공식
  기능명세서를 자동으로 만든다.** 화면 md는 제출 문서가 아니라 사실을 확인하는 입력 자료다.
- **화면설계서·사용자 매뉴얼도 보내지 마라.** ㉯ 로 갱신된 화면 html·md·메뉴구조도에서 **빌더가 만든다.**
  그래서 ㉯ 가 먼저 와야 한다.
- **테스트는 코드가 아니라 결과 문서다.** 빌더는 개발 소스를 못 읽는다.

### ㉮ 의 구조 — 개발요청서의 무엇에 대응하나

| 무엇 | 대응하는 개발요청서 항목 | 줄마다 적을 것 |
|---|---|---|
| **단위테스트 결과 md** | 「화면 외 구현」 **항목마다 1줄** | 무엇을 어떻게 검증했나 · 결과. 우리가 보낸 **「판정 방법」** 칸이 기준이다 |
| **통합테스트 시나리오 md** | 「완료 조건」 **마다** | 시나리오 · 단계 · 기대 결과 · 결과 |

이렇게 하면 **요구사항 → 완료 조건 → 시나리오** 추적표가 저절로 난다. 대응할 항목과 완료 조건은
`expected-back.md`에 **그 DR의 값으로 미리 채워** 보낸다 — 개발자는 각 값 아래의 수행 결과와 근거만 작성한다.

⛔ **㉯ 로 `core/<시스템>/ia.md` 는 보내지 마라.** 그 파일은 「추출기가 초안을 내고 **사람이 고치는 문서**」이고
기계가 덮으면 기획자 손질이 조용히 사라진다. **`422` 로 거절한다** — 조용히 버리지 않는다.

⛔ **화면 md 도 전부는 아니다.** `⚑ 보정됨` · `⬛ 네이티브` 표시가 붙은 화면은 **사람이 정의 블록을 손댔고**
그 안의 `--- 원본 글 ---` 은 자유 산문이라 **검사기가 안을 안 본다** — 규격 검사가 손실을 못 잡는다.
**그 화면들의 화면 md 는 `422` 로 거절한다.** 어느 화면이 그런지는 **`manifest.json` 의 「돌려받을 것」에 적어 보낸다.**

⛔ **㉯ 는 파일 하나씩 보내지 마라 — 한 DR 의 회신을 배치로 묶어 보낸다.** 아래 몸 표.

⛔ **㉯ 의 도메인 md 는 「병합기를 지난 결과」여야 한다** — 기획 레포 `spec/domain.md` 가 사유 줄을
「사람이 적는다」로 정했고, 통째 덮기가 그 문장을 잃는 것이 병합기에 실측돼 있다.

⭐ **㉯ 는 규격에 맞게 굽는 도구를 이미 개발이 쥐고 있다** — 기획 레포가 품고 나간 추출기 스킬 사본.
**손으로 md 를 쓰는 것이 아니다.** DR 이 건드린 화면·모듈에만 돌려 그 출력을 밀면 된다.

**빌더의 잠정안:**

| 무엇 | 잠정값 |
|---|---|
| 방식 | 빌더가 여는 수신 API 로 `POST` |
| 신원 | **프로젝트 키** — 빌더가 발급해 개발에 건넨다. 새면 다시 발급해 갈아끼운다 (기간 만료 없음) |
| 몸 (㉮) | 프로젝트 번호 · 개발요청서 번호 · 종류(단위테스트 결과 · 통합테스트 시나리오) · md 파일 |
| 몸 (㉯) | 프로젝트 번호 · 개발요청서 번호 · **배치 번호** · **기준 커밋SHA** · 항목 여럿. 항목마다 **갈래**(`pages`·`screen-md`·`index`·`domain`) · **시스템+화면ID 또는 도메인+모듈** · **`changed` 냐 `unchanged` 냐** · (`changed` 면) 파일 |
| 배치 완결 | **필수 구성요소마다 `changed`·`unchanged` 가 정확히 하나** 와야 받는다. 무엇이 필수인지는 `manifest.json` 의 「돌려받을 것」에 적어 보낸다. ⭐ **보호 화면(`⚑`·`⬛`)은 `screen-md` 가 필수에서 아예 빠진다** — 그 화면에서 「새 html + 옛 md」는 **의도된 정상 상태**다 |
| 규격 위반 | `422` 로 거절 — **규격 판정은 기획 레포의 검사기가 한다.** ⛔ **배치 통째로 거절하고 아무것도 안 놓는다** |
| **목록 밖 · `ia.md` · 보정/네이티브 화면 md** | **`422` 로 거절 — 이 셋은 빌더가 판정한다** |
| **기준 어긋남** | **`409`** — 기준 커밋이 우리 기본 브랜치 HEAD 와 다르면 받지 않는다 |
| 밀다 부딪힘 | `409` + **부딪힌 파일 목록** |
| 커밋 | **배치당 하나.** author 「빌더 수신」 · 메시지에 **키 식별자·배치 번호·시각**(⛔ 키 원문·해시는 안 넣는다) |

⛔ **㉯ 를 파일 하나씩 즉시 반영하지 않는 까닭** — html · 화면 md · 색인은 **서로 파생 관계**다.
하나씩 놓으면 앞은 성공하고 뒤가 `422`·`409` 로 떨어져 **기본 브랜치가 서로 다른 시점의 혼합물**이 된다.
그리고 「회신이 끝났다」는 신호가 없으면 **아무것도 안 보낸 것과 다 봤는데 안 바뀐 것이 같아 보인다.**

⚠ **「빌더가 판정하지 않는다」에 예외 하나가 생겼다** (2026-08-24). 규격은 여전히 검사기 몫인데,
**「이 화면ID 가 이 DR 의 대상인가」는 검사기가 알 수 없다** — 그건 우리가 `manifest.json` 의
「돌려받을 것」으로 보낸 목록이다. **그 목록에 없는 화면ID·모듈은 빌더가 거절한다.**
⭐ 이것이 **내용을 대조하지 않고도 자리를 지키는** 유일한 문 지킴이다.

⛔ **그 밖에는 대조하지 않는다.** 개발이 준 것을 믿는다 — 옛 파일과 내용을 견주지 않는다.
받쳐 주는 것 둘: **「같은 것이 또 오면 덮어쓰고 옛것은 git 이력에 남는다」**와
**커밋 author 「빌더 수신」 + 커밋 메시지의 키·시각.** 되돌릴 길이 있으니 대조가 문 지킴이일 필요가 없다.

⚠ **㉯ 는 `409` 가 ㉮ 보다 훨씬 잦다.** ㉮ 는 DR 폴더라 남과 겹칠 것이 없는데
㉯ 는 **공유 폴더 `core/` 와 색인**이다. 아래 `409` 규약이 여기서 진짜로 값을 한다.

**정해줄 것 — 이것 하나가 핵심이다:**

> **`409` 를 받으면 개발은 무엇을 하나?**

빌더 쪽은 답이 났다 — **워크트리를 지우고 `409` 와 부딪힌 파일 목록을 돌려준다. 몰래 다시 밀지 않는다.** 남은 것은 **개발 쪽 재시도 규약**이다.

- 곧바로 다시 미나 (그러면 또 부딪힐 수 있다)
- 얼마 뒤에 다시 미나
- 사람에게 알리고 멈추나

**`422` 와 `409` 는 다른 것이다.** `422` 는 「규격에 안 맞는다 — 고쳐서 다시 와라」이고,
`409` 는 「보낸 것은 멀쩡한데 그 사이 기획 레포가 바뀌었다」이다.

⛔ **다만 `409` 를 「그냥 다시 보내면 된다」로 읽지 마라 (2026-08-24 정정).** ㉮ 는 DR 폴더라 그래도 되는데,
**㉯ 는 같은 파일을 그대로 재전송하면 그 사이 남이 고친 것을 다시 덮는다.**
㉯ 의 `409` 뒤에 할 일은 **최신 기준에서 다시 굽고 새 배치 번호로 보내는 것**이다.

## 이것이 안 정해지면

| 안 정해진 것 | 무슨 일이 나나 |
|---|---|
| 1 | 「개발에 넘기기」 버튼이 **아무 데도 못 쏜다** |
| 2 (㉮) | 단위·통합 테스트 결과가 **개발요청서에 안 매달린다.** 「판정 방법」·「완료 조건」이 검증됐는지 아무도 모르고, 요구사항 → 완료 조건 → 시나리오 추적표가 안 난다 |
| **2 (㉯)** | **기획 레포의 as-is 가 영원히 낡는다.** 갱신할 다른 길이 닫혀 있다 — 빌더는 운영 소스를 안 읽고 전체 재추출은 금지돼 있다. ⛔ **다음 FRD 가 낡은 화면을 as-is 로 읽고 확신에 찬 답을 낸다** |
| 앞 개발요청서 | 같은 업무를 두 번 손댈 때 개발이 **무엇이 새 요청인지 못 짚는다** |
| `409` 규약 | 부딪힐 때마다 **산출물이 조용히 사라진다.** 개발은 보냈다고 알고 빌더에는 없다. ⚠ **㉯ 가 공유 폴더를 쓰므로 이제 자주 터진다** |
| **㉯ 를 개발이 구울 수 있나** | 기획 레포의 추출기 스킬 사본으로 **DR 이 건드린 것만** 구울 수 있는지가 미확인이다. 못 구우면 ㉯ 는 **손으로 쓴 md** 가 되어 규격 위반이 상시가 된다 (→ `docs/requests-to-extractor.md` 15·16번) |

**빌더는 둘 다 잠정안으로 계획을 다 썼다.** 합의가 되면 `DevHandoffGateway`(나가는 쪽) 구현 하나와 수신 API 한 자리만 고치면 된다 — 그러려고 인터페이스 뒤에 가둬 뒀다.
