# 빌더가 다루는 현재 산출물 9종

> **이 문서가 답하는 질문 하나: 현재 Builder는 무엇을 다루나.**
> *어떻게* 다루는지(UI·AI 실행·워크트리)는 각각의 설계 문서가 답한다.

**2026-08-20 개정.** 받은 문서·요구사항·요구사항정의서·BRD는 현재 Builder 작업 흐름에서 제거됐다.
과거 데이터와 화면 주소가 남아 있더라도 새 작업의 산출물이나 선행 단계가 아니다.

현재 흐름은 다음과 같다.

```text
솔루션 목업 + 메뉴구조도
          ↓ AI 조사
요구사항 직접 입력 → 인터뷰 → 개발 범위 확인 → FRD 작업 → 개발요청서
                                                        ↓ 개발
                    as-is 재동기(기획 레포 갱신) · 단위테스트 결과 · 통합테스트 시나리오
                                                        ↓ 빌더가 만든다
                                 기능명세서 · 화면설계서 · 사용자 매뉴얼
```

## A. Builder가 만들고 관리한다 — 2종

| 산출물 | 번호 | 책임 |
|---|---|---|
| **FRD 작업** | `FRD-` | 입력 요구사항을 AI 인터뷰로 개발 가능하게 정리하고 화면·백엔드 범위를 작업한다. 화면 0장도 정상이다 |
| **개발요청서** | `DR-` | 완료한 FRD를 개발 조직에 전달한다. **문서 한 장이 아니라 꾸러미 한 채**다 — `dev-request.md`(절 열하나 — 마지막은 반환 계약 파일 안내) · `expected-back.md`(이 DR의 예상 반환 대상 + 개발자가 채울 상세 회신 양식) · `manifest.json`(지문 + 기계가 검사할 반환 대상 표) · 화면마다 현재 운영 화면·변경 화면·변경내용 · 자산. 배치의 정본은 `superpowers/specs/2026-08-22-dev-request-package-design.md` |

**`FRD 1개 = 작업 1개 = 워크트리 1개 = 한 사람`**이다. 분석 중에는 워크트리를 만들지 않는다.
`개발 범위 확인(SCOPE_REVIEW)`에서 `FRD 작업하기`를 누르면 워크트리를 만들고, 성공한 뒤
`수정 중(DRAFTING)`으로 바꾼다. 정본은 `frd-worktree-lifecycle-design.md`다.

FRD 요구사항은 사용자가 직접 입력한다. 수정할 솔루션 목업 화면은 선택 사항이며, 화면을 선택하지 않은
백엔드·권한·배치·정책 작업도 같은 FRD와 워크트리에서 진행한다.

## B. 기획자가 관리한다 — 1종

| 산출물 | 책임 |
|---|---|
| **메뉴구조도(IA)** | 시스템마다 한 장. AI가 대상 화면과 메뉴 영향을 판단하는 지도다 |

최초 `core/<시스템>/ia.md`는 추출기가 만들고, Builder가 한 번 가져온 뒤 DB에서 편집한다. 확정할 때
기획 저장소의 `ia.md`를 읽기용 스냅샷으로 갱신한다.

## C. 현재 운영 화면을 보여 준다 — 1종

| 산출물 | 책임 |
|---|---|
| **솔루션 목업** | 운영 소스에서 추출한 현재 화면. FRD가 수정할 화면을 고르고 시작점을 얻는 자료다 |

솔루션 목업은 `we-adk-builder-extractor`가 만들며 Builder는 운영 소스를 직접 읽지 않는다. 모든 연결은
기획 저장소의 화면 ID(`wv-card-list` 꼴)를 사용한다. FRD는 직전 FRD 결과가 아니라 현재 솔루션 목업에서
시작한다.

## D. 개발 결과를 받아 생긴다 — 5종

**2026-08-27 병주 확정 — 갈래가 셋이다.** 단위·통합테스트는 개발이 보내고, 기능명세서·화면설계서·
사용자 매뉴얼은 갱신된 화면 자료에서 Builder가 만든다. 개수를 세는 것은 이 절이 유일하다 — 다른 문서에
다시 적지 않는다. 기능명세서 자동 생성의 정본은
`superpowers/specs/2026-08-27-feature-spec-generation-design.md`다.

### 개발이 돌려보낸다

| 무엇 | 연결 기준 | 어떤 모양으로 |
|---|---|---|
| **as-is 재동기** | 개발요청서 · 화면ID · 도메인 모듈 | 화면 html · 화면 md · `index.json` 조각 · 도메인 md · 「확인했고 변경 없음」. **1순위**다 — 기획 레포를 갱신할 유일한 재료다. ⚠ **산출물로 세지 않는다** — 이미 있는 것의 갱신이다 |
| **단위테스트** | 개발요청서 | **코드가 아니라 결과 문서(md)**다. 개발요청서 「화면 외 구현」 항목마다 한 줄 — 무엇을 어떻게 검증했나 · 결과. 우리가 보낸 「판정 방법」 칸에 대응한다 |
| **통합테스트** | 개발요청서 | **시나리오 문서(md)**다. 개발요청서 「완료 조건」마다 — 시나리오 · 단계 · 기대 결과 · 결과. 요구사항 → 완료 조건 → 시나리오 추적표가 저절로 난다 |

빌더는 개발 소스를 못 읽는다(g2c 를 모른다). 그래서 테스트는 코드로 받지 않는다.
**둘 다 「무엇을 검증하나」(TC 번호·조건·행위·결과)는 빌더가 개발요청서 꾸러미의 `expected-back.md` 에 먼저 적어 보낸다
(2026-08-27)** — 개발은 실제 결과·판정·근거만 채운다. 그래야 돌아온 md 를 화면이 TC 단위로 셀 수 있다.

### 빌더가 만든다 — 개발이 보내지 않는다

| 무엇 | 재료 |
|---|---|
| **기능명세서** | 솔루션 템플릿 — as-is 재동기로 갱신된 화면 html · 화면 md · 메뉴구조도. 화면 상세 진입 시 현재 문서가 없거나 입력이 바뀐 경우에만 자동으로 만든다 |
| **화면설계서** | 솔루션 템플릿 — as-is 재동기로 갱신된 화면 html · 화면 md · 메뉴구조도 |
| **사용자 매뉴얼** | 같은 재료 |

as-is 재동기가 먼저 와야 만들 값이 있다. **셋은 그린존이다.** 화면 md는 기능명세서 자체가 아니라 AI가
공식 기능명세서를 만들고 사실을 검증하는 입력 자료다. 기능명세서는 구조화된 DB 문서와 성공 개정판으로
관리하며, 사용자 화면에는 md 원문·추출 위치·생성 방식을 노출하지 않는다.

돌아온 것은 원본과 가공본을 구분하고 개발요청서 단위로 묶는다.

## E. 삭제됐다 — 요구사항 추적 매트릭스

**2026-08-27 병주 결정으로 산출물에서 뺐다.** 종전에는 「FRD·화면·개발요청서·개발 결과의 연결을 열 때마다 계산해 보여 주는
표」였다. 그 설계 문서는 이 저장소에 없다 — 폐기 문서는 팀 사본에서 뺐다.
⛔ **메뉴 열쇠 `matrix` · 목업 `09-matrix.html` · 로드맵 단계 6 을 되살리지 마라.**

## Builder의 일이 아닌 것

| 무엇 | 누구 일인가 |
|---|---|
| 운영 소스에서 화면을 추출하는 것 | `we-adk-builder-extractor`를 사람이 별도 Claude Code 세션에서 실행한다 |
| 기획 저장소 규격을 판정하는 것 | 기획 저장소가 품은 검사기 |
| g2c와 원본 시스템을 아는 것 | `we-adk-builder-extractor` |

## 폐기된 체인

`받은 문서 → 요구사항(REQ) → 요구사항정의서(RD) → BRD` 체인은 2026-08-20 폐기됐다.
당시 판단을 보존하는 이력 문서가 있었으나 이 저장소에 없다 — 폐기 문서는 팀 사본에서 뺐다.
⛔ 폐기된 체인을 새 코드·화면·DB 설계의 근거로 삼지 않는다.
