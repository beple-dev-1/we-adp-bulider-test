# 표준 화면ID 를 언제 어떻게 짓고 무엇에 쓰나

> **이 문서가 답하는 질문 하나: `PS-WB-MRC-010-L01-S` 꼴 표준 화면ID 를 누가 · 언제 짓고,
> 빌더 안에서 무엇에 쓰나.**
>
> **날짜**: 2026-08-20. **지시는 보스, 결정은 병주 확정.**
>
> **무엇을 보고 썼나**: 이 저장소의 코드와 문서를 **읽기만** 하고 썼다 —
> `SolutionScreenReader`(레포 3소스 읽기) · `IaScreenProfile` · `IdSequence` ·
> `docs/data-model.md` §4 · `docs/requests-to-planning-repo.md` §5 · `docs/extractor-measured-facts.md` §1~3.
> **추출기와 기획 레포는 안 건드렸다** — 아래 결정이 그 둘에 아무것도 요구하지 않는다.

## 답하는 것과 안 답하는 것

**답한다** — 표준 ID 가 기존 화면ID 를 대체하나 · 언제 짓나 · 여섯 마디를 각각 무엇에서 뽑나 ·
AI 가 어디까지 하나 · 무엇을 저장하고 무엇을 계산하나 · 빌더 코드가 이것으로 무엇을 하면 안 되나.

**안 답한다** —

- **신규 화면의 「열쇠」(`bo-usag-list` 꼴 화면ID)를 누가 짓나.** 이건 표준 ID 와 **별개 숙제**이고
  `docs/requests-to-planning-repo.md` §5 에 미결로 열려 있다. 아래 「⛔ 이 문서가 안 닫는 것」 참조
- **`C`(변경) 마디의 규칙.** 2026-08-20 병주 지시로 미룬다. 아래 설계가 나중에 한 줄로 받는다
- **표준 ID 로 화면을 검색하는 UI.** 어느 화면에 검색창을 다나는 목업이 정한다
- **다음 사업에서 `N` 으로 난 화면이 무엇이 되나.** 사업 하나를 다 돌려 보고 정한다

## 1. 대체가 아니라 매핑이다 — 확정

**표준 ID 는 기존 화면ID 를 대체하지 않는다.** 옆에 하나 더 선다.

| | 열쇠 | 라벨 |
|---|---|---|
| 값 | `bo-usag-list` · `wv-card-list` | `PS-WB-MRC-010-L01-S` |
| 정본 | **기획 레포** (`index.json` · `pages/<화면ID>.html`·`.md`) | **빌더 DB** (매핑표) |
| 쓰는 자리 | 파일 경로 · 동시편집 잠금 · BRD 대상화면 · 작업목업 경로 · FRD · IA 연결 | 화면 목록 표시 · 보고서 · 개발요청서 |
| 성질 | 밖에서 온 것. 빌더가 못 바꾼다 | 빌더가 지은 것. 5마디는 불변 |

**왜 대체가 아닌가.** 대체하려면 추출기가 508장을 일괄 재채번해야 하고, 검사기·규격·기존 문서가
전부 따라 움직여야 한다. 매핑이면 **추출기에 아무것도 요구하지 않는다.**

### ⛔ 못 둘 — 이름이 둘이 되는 값을 여기서 막는다

`SolutionScreen` javadoc 이 2026-08-13 에 *"`SOL-W-014` 꼴 자기 이름을 짓지 마라 —
이름이 둘이 되면 BRD 의 자동 복사가 거기서 깨진다"* 로 못을 박았다. 매핑은 그 못을 **어기는 것이
아니라 조건부로 푸는 것**이다. 조건이 이 둘이고, 둘 다 깨지면 그 javadoc 의 경고가 그대로 현실이 된다.

| # | 못 | 왜 |
|---|---|---|
| **못 1** | **빌더 코드가 표준 ID 로 화면을 찾지 않는다.** 조회 · 잠금 · 경로 · 조인은 언제나 열쇠(`screenId`)로 한다. 표준 ID → 화면의 역방향은 **사람이 검색창에 칠 때만** | 두 이름으로 같은 것을 찾기 시작하면 한쪽이 낡았을 때 **조용히 다른 화면을 집는다** |
| **못 2** | **표준 ID 를 파싱해서 업무영역·기능그룹·유형을 알아내지 않는다.** 분류 · 필터 · 집계는 언제나 IA 와 `IaScreenProfile` 을 본다 | 아래 §3 의 대가(IA 가 바뀌면 ID 가 어긋난 채 굳는다)를 **표시 문제로 가둬 두는 장치**다. 이 못이 없으면 어긋난 ID 를 파싱하는 코드가 생겨 그때부터 진짜 버그가 된다 |

**표준 ID 는 이름일 뿐 분류가 아니다.** 이 한 줄이 §1 의 전부다.

## 2. 여섯 마디를 각각 무엇에서 뽑나

```
PS  -  WV  -  MRC  -  010  -  L01  -  S
 │      │      │       │       │      │
 │      │      │       │       │      └ 상태  — 저장 안 한다. 조립할 때 계산 (§4)
 │      │      │       │       └ 유형+번호 — IaScreenProfile + 결정적 정렬
 │      │      │       └ 기능그룹 — IA 경로 둘째 마디 slug 의 순번
 │      │      └ 업무영역 — AI 가 IA 경로 첫 마디 slug 에서 1회 생성
 │      └ 시스템 — manifest.json 의 systems[].prefix 대문자
 └ 플랫폼 — 프로젝트 열 platform_code
```

| 마디 | 재료 | 누가 | 결정적인가 |
|---|---|---|---|
| **플랫폼** `PS` | **프로젝트 열** `platform_code` | 사람 (프로젝트 등록) | ✅ |
| **시스템** `WV` | **`manifest.json` 의 `systems[].prefix` 를 대문자로** (`wv` → `WV`) | 레포 (읽기만) | ✅ |
| **업무영역** `MRC` | IA `경로` **첫 마디 slug**(`merchant`) + 이름표의 한글(「가맹점」) | **AI 가 1회 생성 → 코드표에 고정** | ⚠ §5 |
| **기능그룹** `010` | IA `경로` **둘째 마디 slug** 의 순번 | 결정적 정렬 → 코드표에 고정 | ✅ |
| **유형** `L` | `IaScreenProfile` 의 `ScreenKind` + `ScreenType` | 규칙표 (§2.1) | ✅ |
| **일련번호** `01` | 같은 (업무영역·기능그룹·유형) 안의 순번 | **결정적 정렬** (§2.2) | ✅ |
| **상태** `S` | 태생(저장) + 계산 | §4 | ✅ |

⛔ **설치 설정(yml)에 두지 마라 — 2026-08-20 에 한 번 그렇게 짰다가 걷어냈다.** 시스템 목록은 **사업마다 다르다**. yml 에 세 줄(`backoffice`·`webview`·`online-pg`)을 박아 뒀더니 실물 레포의 시스템이 **여섯**(`saleoffice`·`lspnoffice`·`portal` 이 더 있다)이라 **나머지 세 시스템의 화면이 조용히 번호를 못 받는 상태**였다. 「코드에 박지 마라」를 yml 로 옮긴 것일 뿐이었다.

⭐ **시스템 두 글자는 지어내는 것이 아니라 이미 클론에 있다 (2026-08-20 실측).** `manifest.json` 의 `systems[]` 가 시스템마다 `prefix` 를 갖는다 — `bo`·`wv`·`pg`·`so`·`lo`·`pt`. **화면ID 앞머리와 같은 값**이라(`bo-usag-list`·`wv-card-list`) 사람이 대조하기도 쉽다. **대문자로 올려 쓴다.**

⚠ **그래서 웹뷰가 `WV` 다 — 보스 예시의 `WB` 가 아니다** (2026-08-20 병주 확정). 레포가 정본이고, 새 시스템이 늘어도 자동으로 따라온다.

⚠ **플랫폼만 클론에 없다.** `manifest.json` 최상위에 플랫폼도 회사도 없다(실측). 그래서 **플랫폼만 프로젝트 등록에서 사람이 넣고 `adk_builder_project.platform_code` 에 산다** (2026-08-20 병주 확정). ⚠ **등록 시점에 받는 까닭**은 클론이 끝나면 바로 채번이 도는데 **박힌 ID 는 안 바꾸는 규칙**이라, 나중에 고쳐도 이미 붙은 번호엔 안 먹기 때문이다.

### 2.1 유형 한 글자 — 축이 둘이라 우선순위를 둔다

보스 예시의 `L01`·`D01`·`P01` 은 **한 글자에 축 둘을 섞었다.** `L`(목록)·`D`(상세)는 화면유형이고
`P`(팝업)는 화면 종류다. `IaScreenProfile` 은 그 둘을 이미 갈라 갖고 있다 —
`ScreenKind`(화면·팝업·모달) 와 `ScreenType`(목록·상세·등록·수정·안내·미분류).

**규칙: 종류가 먼저다.**

| 조건 | 글자 |
|---|---|
| `ScreenKind` = 팝업 | `P` |
| `ScreenKind` = 모달 | `M` |
| `ScreenKind` = 화면 → `ScreenType` = 목록 | `L` |
| 〃 상세 | `D` |
| 〃 등록 | `R` |
| 〃 수정 | `U` |
| 〃 안내 | `G` |
| 〃 미분류 | `X` |

⚠ **등록이 `C`(Create) 가 아니라 `R`(Register), 수정이 `E` 가 아니라 `U`(Update) 다.**
`C` 와 `E` 를 피한 것은 일부러다 — 여섯째 마디가 `S`/`N`/`C` 라서 **`C` 가 두 자리에서 다른 뜻으로
쓰이면 사람이 반드시 헷갈린다.** 자리가 달라 기계는 안 헷갈리지만 이 ID 를 읽는 것은 사람이다.

⚠ **`X`(미분류)가 실제로 나온다.** `IaScreenProfile.typeNeedsReview()` 가
*"이름으로 추정한 유형은 사람이 본다"* 로 이미 서 있다. **`X` 화면 목록을 보여주는 자리가 필요하다** —
사람이 유형을 고치면 그 화면의 표준 ID 를 **한 번만** 다시 짓는다(§3 의 예외).

### 2.2 일련번호 — 카운터가 아니라 함수다

⛔ **「먼저 색인된 순」으로 주지 마라.** 그러면 재클론·재색인 때 번호가 갈린다.

**정렬 규칙**: 같은 `(업무영역, 기능그룹, 유형글자)` 묶음 안에서
**① IA 경로 사전순 → ② 화면ID 사전순** 으로 세우고 1번부터 매긴다.
같은 레포를 열 번 색인해도 **같은 표가 나온다.**

⚠ **`ia.md` 의 `순서` 92행이 전부 비어 있다**(기획팀이 채울 몫 · `requests-to-planning-repo.md` §6).
그래서 「IA 가 정한 차례」를 쓸 수 없고 **경로 사전순으로 대신 뽑는다.** 나중에 `순서` 가 채워져도
**이미 박힌 번호는 안 바꾼다**(§3).

⚠ **2자리 0채움이고, 100장을 넘으면 3자리로 늘어난다.** `data-model` §4 규칙 5 와 같은 성격이다 —
**이 문자열로 정렬하지 않는다.** 정렬은 별도 순번 열로 한다.

### 2.3 IA 경로가 없는 화면은 번호를 안 받는다

**모든 화면이 번호를 받지는 못한다.** 업무영역·기능그룹의 재료가 IA 경로인데, 그것이 없는 화면이 있다.

| 경우 | 실측 | 어떻게 |
|---|---|---|
| **시스템에 `ia.md` 가 아직 없다** | **웹뷰가 그렇다** (`extractor-measured-facts` §13) | 그 시스템 전체를 **건너뛴다** |
| 공용 팝업 — `iaShared` 에 있고 `경로` 가 없다 | 백오피스 **2장** | 건너뛴다 |
| 자리를 못 얻었다 (검사기 IA-9 red) | 백오피스 **3장** | 건너뛴다. 기획 레포가 고칠 일이다 |
| **경로를 얻었다** | 백오피스 **251장 / 256장** | 번호를 받는다 |

⛔ **번호가 없는 화면에 억지 코드(`XXX-000`)를 지어 붙이지 마라.** 그것은 「모른다」가 아니라
**틀린 정보**이고, 나중에 진짜 경로가 와도 §3.2 의 「없는 것만 채운다」에 걸려 **안 고쳐진다.**

**화면 목록에 「번호 없음」으로 그대로 보인다.** 웹뷰 `ia.md` 가 오거나 red 3장이 고쳐지면
**다음 저장소 업데이트에서 자동으로 채워진다**(§3.1) — 그때 그 화면들이 `max + 1` 로 뒤에 붙는다.

## 3. 언제 짓나 — 클론·셋업 직후 일괄 (병주 확정)

**프로젝트의 기획 레포 클론이 앉는 순간, 색인과 함께 매핑표를 일괄로 박는다.**

**왜 IA 확정 시점이 아닌가** — 최초 274장(v1 기준 508장)에 사람이 먼저 손대게 하면
**시작을 못 한다**(2026-08-20 병주 판단). 레포가 보이는 순간 모든 화면이 번호를 갖는 편이 낫다.

### 3.1 붙는 자리는 둘이다 — 하는 일이 다르다

**클론 한 번으로 끝나지 않는다.** 기획 레포는 계속 자란다 — `git pull` 로 화면이 들어오면
그 화면도 번호를 가져야 한다. 그래서 채번은 **두 자리**에 붙는다.

| | `CloneWorker.clone()` | `RepositoryUpdateWorker.update()` |
|---|---|---|
| 언제 | 프로젝트 설정에서 Git 정보를 넣고 **최초 클론** | 「저장소 업데이트」 (`fetch` 뒤) |
| 대상 | **전 화면** | **매핑표에 없는 화면만** |
| 업무영역 코드표 | AI 가 **전체 목록을 한 번에** 보고 생성 (§5) | 코드표에 **없는 업무영역만** 추가 생성 |
| 일련번호 | **결정적 정렬로 1..N** (§2.2) | ⚠ **그 묶음의 `max + 1`** |
| 기존 행 | — | **절대 안 건드린다** |

⛔ **업데이트에서 §2.2 의 정렬을 다시 돌리지 마라.** 사전순 중간에 화면이 끼면 **그 뒤 번호가
전부 한 칸씩 밀린다.**

```
최초:  ...-L01  가맹점 목록
       ...-L02  가맹점 이력 목록

업데이트로 「가맹점 승인 목록」이 들어왔다 — 사전순으로는 L02 자리다
  ❌ 정렬을 다시 돌리면 → L02 가 둘이 되고 기존 L02 가 L03 으로 밀린다
  ✅ 뒤에 붙인다        → L03. 사전순과 어긋나지만 기존 번호가 안 움직인다
```

**번호가 밀리면 이미 개발요청서에 찍혀 나간 번호가 다른 화면을 가리킨다** —
`data-model` §4 규칙 4 와 같은 자리다. **최초만 정렬, 이후는 뒤에 붙이기.**

⚠ **사라진 화면의 행은 남긴다.** 업데이트로 화면이 레포에서 없어져도 매핑표 행을 지우지 않는다.
지우면 그 번호가 **재사용**되어 다음 화면에 붙는다 — 같은 까닭이다.

### 3.2 재색인 규칙 — 없는 것만 채운다

`IaScreenProfile` 의 *"최초 색인에서 가져온 화면 분류. 이후 색인이 바뀌어도 DB 값을 덮어쓰지 않는다"*
를 **그대로 베낀다.** 재색인은 **매핑표에 없는 화면에만** 번호를 준다.

**예외 하나** — §2.1 의 `X`(미분류)를 사람이 실제 유형으로 고쳤을 때. 그때는 그 화면의 표준 ID 를
**한 번만** 다시 짓는다. `X` 는 「아직 안 정해졌다」는 표시이지 확정된 유형이 아니다.

### 3.3 이 시점을 택한 대가 — 받아들이고 가둔다

`MRC-010` 은 클론 직후의 IA(추출기가 준 원본 배치)로 박힌다. **기획자가 그 뒤 메뉴구조도를
정리하면 ID 의 업무영역·기능그룹이 어긋난 채로 굳는다.**

이 대가를 **없애지 않고 가둔다** — §1 의 **못 2**(ID 를 파싱해 분류를 알아내지 않는다)가 그 장치다.
어긋나도 **기능이 안 깨진다.** 사람 눈에 「옛날 번호」로 보일 뿐이다.

⛔ **어긋났다고 나중에 일괄 재채번하지 마라.** 개발요청서에 이미 찍혀 나간 번호가 다른 화면을
가리키게 된다 — `data-model` §4 규칙 4 가 산출물 ID 에 대해 못 박은 것과 같은 까닭이다.

## 4. 무엇을 저장하고 무엇을 계산하나

**5마디를 저장하고, 상태 마디는 볼 때 조립한다.**

| | 무엇 | 어디 |
|---|---|---|
| **불변 ID** | `PS-WB-MRC-010-L01` (5마디) | 매핑표에 **저장**. 절대 안 변한다 |
| **태생** | `S`(색인에서 왔다) · `N`(빌더에서 새로 났다) | 매핑표에 **저장**. 화면 속성이라 불변 |
| **상태 마디** | `-S` / `-N` / (뒤에 `-C`) | **저장 안 한다. 조립할 때 계산** |

**지금의 조립 규칙** (2026-08-20):

```
태생이 N 이면  →  N
그 외          →  S
```

**왜 이렇게 갈랐나.** `S`/`N`/`C` 는 **화면의 속성이 아니다.** 「이번 사업에서 이 화면에 무슨 일이
있었나」이고, 그건 **작업(BRD) × 화면** 축이다. 추출기 규격이 *"축이 셋 다 다르므로 섞지 않는다"*
고 못 박은 것과 같은 종류다. 이것을 5마디에 붙여 **저장**하면 답이 없는 질문이 셋 생긴다 —

- 두 번 고치면? (`C` 로 간 뒤엔 계속 `C`. 담는 정보가 「한 번이라도 고쳤나」뿐이다 — ID 가 아니라 플래그다)
- 작업목업은 BRD 마다 사본으로 남는데 8/5 판본과 8/12 판본이 둘 다 `C` 면 무엇으로 가르나
- 다음 사업에서 `N` 으로 난 화면은 이미 운영 화면인데 여전히 `N` 인가

**계산값으로 두면 이 셋이 질문 자체로 사라진다.** 그리고 **보스가 보는 글자는 한 자도 안 바뀐다** —
표시·보고서·개발요청서에는 그 시점에 6마디가 조립돼 나간다.

⛳ **`C` 는 밖에 걸어 뒀다** (2026-08-20 병주 지시). 나중에 규칙을 이렇게 한 줄 늘리면 된다 —
`태생이 S 인데 이번 사업에서 BRD/FRD 가 이 화면을 잡았으면 → C`.
**5마디 저장 구조라서 그때 마이그레이션이 없다.**

## 5. AI 가 어디까지 하나

⛔ **「AI 가 알아서 채번한다」는 아니다.** AI 가 손대는 자리는 **하나뿐**이고, 나머지는 상속·조회·정렬이다.

| 마디 | AI 인가 | 왜 |
|---|---|---|
| 플랫폼 · 시스템 | ❌ 상수·조회 | 판단할 것이 없다 |
| **업무영역 `MRC`** | ✅ **AI 1회 생성** | slug(`merchant`)를 3글자로 줄이는 것은 규칙으로 못 짠다. 앞 3글자(`MER`)는 보스 예시(`MRC`)와 다르고, 두 업무영역이 앞 3글자를 나눠 가지면 부딪힌다 |
| 기능그룹 `010` | ❌ 정렬 | 판단이 아니라 순번이다 |
| 유형 `L` | ❌ 규칙표 | `IaScreenProfile` 이 이미 분류를 갖고 있다 (그 분류를 만드는 자리에 AI 가 이미 있다) |
| **일련번호 `01`** | ⛔ **금지** | 두 사람이 같은 시각에 같은 번호를 받는다. 원자적 채번의 일이지 AI 의 일이 아니다 |
| 상태 `S` | ❌ 계산 | §4 |

### 업무영역 코드표 — AI 가 짓고, 사람이 고칠 수 있다

**클론 직후 AI 가 업무영역 목록을 한 번에 보고 3글자 코드를 짓는다.** 결과는
**프로젝트별 코드표로 DB 에 고정**되고, 재색인이 덮지 않는다.

**AI 에게 주는 입력은 짝이다** — IA `경로` 첫 마디 slug 와 `## 이름표` 의 한글:

```
merchant : 가맹점
approval : 결재
customer : 고객관리
```

AI 에게 주는 제약:

- **한 프로젝트 안에서 코드가 겹치지 않게** 목록 전체를 한 번에 보고 짓는다 (화면마다 따로 묻지 않는다)
- 대문자 영문 3글자 고정. 뜻이 통하는 축약을 고른다 (`merchant`/「가맹점」 → `MRC`)
- 못 짓겠으면 **지어내지 말고 `XXX`** 를 낸다 — 사람이 볼 목록에 남는다

**어느 AI 가 짓나 — 기본은 Gemini 다 (2026-08-20 개정).**

| | 재료 | 못 지을 때 |
|---|---|---|
| **`GeminiBusinessAreaCoder`** (기본) | 서버 API 키 (`builder.document-understanding.api-key`) | 전부 `XXX` |
| `ClaudeBusinessAreaCoder` (되돌릴 길) | **클론을 돌린 사람의 Claude 연결** | 전부 `XXX` |

⭐ **Claude 에서 옮긴 까닭은 자격 관문이다.** 클론은 관리자가 돌리는데 그 계정에 Claude 연결이
없거나 만료면 업무영역이 전부 `XXX` 로 박히고, **코드표에 행이 생겨 다시 묻는 길이 없다**
(코드가 있으면 AI 를 다시 안 부른다). 복구가 `adk_builder_screen_id_group` 행을 지우고
재실행하는 것뿐이라 **조용히 굳는 고장**이었다. 서버 API 키는 사람의 계정과 무관하다.

⛔ **Claude 구현을 지우지 않았다 (병주 지시).** `builder.screen-id.business-area-coder=claude`
한 줄로 되돌아간다. 설정이 정확히 하나만 띄우는 것을 `BusinessAreaCoderWiringTest` 가 잰다 —
둘이 뜨면 주입이 애매해져 **앱이 아예 안 뜬다.**

⚠ **Gemini 에는 `--json-schema` 가 없다.** Claude 쪽은 출력 모양을 강제했지만 이쪽은 못 한다 —
그래서 답에서 **코드 울타리(```json)와 앞뒤 인사말을 걷어내고** 가장 바깥 중괄호 한 쌍을 집는다.
안 걷으면 업무영역이 통째로 `XXX` 가 된다. 걷어내는 규칙 자체는 두 구현이 **한 자리**
(`BusinessAreaCodes`)를 같이 쓴다 — 갈라 두면 공급자를 바꾼 날 규칙도 같이 갈린다.

⛔ **코드표의 열쇠는 slug 이지 한글 이름이 아니다.** 이름표는 기획자가 IA 작업대에서 고칠 수 있고
(`IaDocumentCodec.serialize` 가 확정할 때 이름표를 다시 쓴다), 이름이 바뀌면 한글을 열쇠로 잡은
코드표가 **자기 행을 못 찾아 같은 업무영역에 코드를 하나 더 짓는다.** slug 는 안 바뀐다 —
`data-model` 이 그것을 「안정적인 경로 식별자」로 적어 뒀다.

**사람이 코드표를 고칠 수 있다.** 다만 ⛔ **이미 박힌 표준 ID 는 안 바뀐다**(§3).
코드표 수정은 **그 뒤에 나는 신규 화면부터** 먹는다. 이것을 화면에 글로 적어 둔다 —
안 적으면 「고쳤는데 왜 안 바뀌냐」가 온다.

### 신규 화면의 표준 ID

BRD/FRD 가 신규 화면을 만들면:

1. **업무영역·기능그룹은 상속한다** — 신규 화면은 언제나 어떤 메뉴 아래 난다. 부모 IA 노드에서 가져온다
2. **유형 글자는 AI 가 제안하고 사람이 확정한다** — `IaScreenProfile` 의 `typeSource`(ID·이름) 패턴 그대로
3. **일련번호는 원자적 채번** — 그 묶음의 max + 1. 빌더는 서버 1대라 DB 카운터로 직렬화된다
4. **태생 = `N`**

## 6. DB — 표 둘

`data-model` §0 을 따른다 — PK 는 7자리 0채움 글자, `IdSequence.Kind` 에 줄을 늘린다.

### `adk_builder_screen_standard_id` — 매핑표

| 열 | 뜻 |
|---|---|
| `id` | PK. `SCREEN_STANDARD_ID` 시퀀스 |
| `project_id` | 프로젝트 |
| `screen_id` | **열쇠** (`bo-usag-list`). 레포의 것 |
| `standard_id` | **5마디** (`PS-WB-MRC-010-L01`). 상태 마디 없음 |
| `origin` | 태생 `S` · `N` |
| `sort_no` | 정렬용 순번 (문자열 정렬 금지 · §2.2) |
| `created_at` | |

유일 제약 둘: `(project_id, screen_id)` · `(project_id, standard_id)`.
**둘째가 중복 채번을 DB 가 막는 자리다.**

### `adk_builder_screen_id_group` — 업무영역·기능그룹 코드표

| 열 | 뜻 |
|---|---|
| `id` | PK. `SCREEN_ID_GROUP` 시퀀스 |
| `project_id` | |
| `system_code` | `backoffice` · `webview` · `online-pg` |
| `area_key` | **IA `경로` 첫 마디 slug** (`merchant`) ← **열쇠** |
| `area_code` | AI 가 지은 3글자 (`MRC`) |
| `area_label` | 이름표의 한글 (「가맹점」). **표시용이고 열쇠가 아니다** |
| `group_key` | **IA `경로` 둘째 마디 slug** (`master`). 없으면 빈 문자열 |
| `group_no` | 3자리 (`010`) |
| `group_label` | 이름표의 한글. 표시용 |

유일 제약 둘: `(project_id, system_code, area_key, group_key)` · **`(project_id, system_code, area_code, group_no)`**(`area_code <> 'XXX'` 인 행만).
**둘째가 코드 충돌을 DB 가 막는 자리다** — 한 시스템 안에서 AI 가 두 업무영역에 같은 3글자를 내면 삽입이 깨진다.
**조용히 겹치는 것보다 시끄럽게 깨지는 편이 낫다.**

⚠ **`XXX` 는 제약에서 빠진다.** 「못 지었다」는 표시라 여럿이 정상이다 — 그것까지 막으면 AI 가 실패한 날 채번이 통째로 깨진다.

⚠ **`system_code` 가 제약에 들어 있는 것은 일부러다 (2026-08-20 구현 중 잡았다).** 백오피스와 웹뷰가 같은 업무영역(`merchant`)을 갖는 것은 정상이고, **그 둘은 `area_code` 를 일부러 나눠 쓴다** — 같은 업무니까. 갈라 주는 것은 표준 ID 의 시스템 마디다(`PS-BO-MRC-010` ≠ `PS-WV-MRC-010`). ⛔ **`system_code` 를 다시 빼지 마라** — 빼면 웹뷰 `ia.md` 가 오는 날 두 시스템의 행이 부딪혀 채번이 통째로 죽는다.

⚠ **기능그룹 번호는 시스템마다 010 부터 다시 센다.** 백오피스의 `MRC-010` 옆에 웹뷰의 `MRC-010` 이 선다 — ID 가 시스템을 이미 적고 있으므로 그편이 읽힌다.

⚠ **업무영역=경로 1마디 · 기능그룹=경로 2마디로 고정 가정한다.** `ia.md` 의 `경로` 는
**1~5단계 가변**이다(`IaDocumentCodec.PATH`). 마디가 하나뿐인 가지는 기능그룹이 없다 —
그때 `group_key` 는 빈 문자열이고 `group_no` 는 `000` 이다. 3마디 아래는 표준 ID 에 안 들어간다.

## ⛔ 이 문서가 안 닫는 것 — 보스에게 미리 말할 것

**표준 화면ID 채번은 `docs/requests-to-planning-repo.md` §5 의 미결을 닫지 않는다.**

매핑이라서, 신규 화면은 표준 ID(라벨) 말고도 **`bo-usag-list` 꼴 열쇠**를 여전히 새로 지어야 한다.
그리고 **동시편집 잠금과 파일 경로를 쥔 것은 그 열쇠다** — 표준 ID 가 아니다.

> 두 사람이 같은 새 화면을 조금 다르게 적으면 **열쇠가 갈려서 안 막힌다.**
> 그러면 같은 화면의 상충하는 판본 둘이 개발로 나간다.

**둘은 별개 숙제다.** 섞으면 「표준화 했는데 왜 두 사람이 같은 화면을 고쳤냐」가 온다.
