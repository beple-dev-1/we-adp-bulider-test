# 목업 구조·UX 카피 재설계

## 배경

현재 `docs/mockups`는 산출물 메뉴 10개를 모두 목록 한 장씩으로 해석했다. 그 결과 새 접수를 시작하는 화면이 없고, 받은 문서 화면에는 업로드·목록·오류가 섞였다. 여러 파일은 채워진 상태와 빈 상태, 설계 메모까지 한 화면에 동시에 렌더한다. 버튼과 상태 문구도 `올린다`, `연다`, `낳는다`, `역류`처럼 제품 언어보다 설명자의 혼잣말에 가깝다.

정본 IA의 10개는 메뉴 수이지 화면 수가 아니다. 산출물은 목록·상세·작업대라는 서로 다른 화면 상태를 가질 수 있다. 이번 재설계는 메뉴 계약을 유지하면서 현재 목업군을 실제 사용 가능한 제품 화면으로 바로잡는다.

## 목표

- 모든 화면의 문구를 자연스러운 한국어 업무 언어로 바꾼다.
- 받은 문서 목록과 문서 등록·AI 정리본 수정을 분리한다. 등록과 수정은 입력량과 원문 대조가 필요하므로 독립 화면으로 연다.
- 등록 때 사용자가 문서 종류를 반드시 선택하게 한다.
- 한 HTML에는 한 시점의 제품 상태만 보이게 한다.
- 산출물 성격에 맞는 정보 위계와 다음 행동을 보여준다.
- 현재의 높은 정보 밀도와 공통 셸은 유지한다.

## 범위

이번에 포함한다.

- `docs/mockups/AGENTS.md`: 지속적으로 적용할 카피·구성 규칙
- `01-received-docs.html`: 받은 문서 목록 전용 화면
- `01a-received-document-register.html`: 받은 문서의 하위 등록 화면
- `02`~`10`: 문구, 정보 위계, 필터, 상태, 행동 재구성
- `_style-guide.html`, `_README.md`, 공통 CSS/셸의 필요한 수정
- 문서 종류 속성에 대한 IA·데이터 모델 정본 보완

이번에 포함하지 않는다.

- Spring 업로드 기능 구현
- 모든 산출물의 상세·작업대 목업 제작
- 문서 종류별 추출 알고리즘 차등 처리
- 다중 파일 등록과 부분 성공 정책
- 개발 전송 관리 화면 설계

## 선택한 접근

세 대안을 비교했다.

1. 문구만 교체: 빠르지만 상태 동시 렌더와 업무 혼합이 남아 제외한다.
2. 현재 목업군의 구조적 재설계: 목록·등록 경계를 세우고 각 산출물의 성격을 반영한다. 이번 안으로 선택한다.
3. 상세·작업대 전체 확장: 필요한 도메인 결정이 많아 별도 작업으로 남긴다.

이 결정은 캡틴이 사용자의 전면 재검토 위임, 프로젝트 정본, 제품 IA·UX 카피·구현 계약 전문가의 독립 검토를 근거로 내렸다.

## 정보 구조

### 받은 문서

```text
받은 문서 목록
  └─ 문서 등록
       └─ 등록 완료
            └─ 받은 문서 목록(요구사항 추출 중인 새 행)
```

- 목록 주소와 메뉴는 기존 `received-docs`를 유지한다.
- 등록은 받은 문서 아래의 자식 화면이다. 왼쪽 메뉴에 새 항목을 만들지 않는다.
- 실제 구현 시 권장 주소는 목록 `GET /projects/{id}/artifacts/received-docs`, 등록 `GET /projects/{id}/artifacts/received-docs/new`, 제출 `POST /projects/{id}/artifacts/received-docs`다.
- 상세는 후속 화면이지만 목록의 문서명과 행 작업은 상세 확장을 막지 않게 설계한다.

### 등록 계약

- 한 번에 문서 1건을 등록한다. 첨부파일은 선택이며 파일과 직접 입력 중 하나 이상을 받는다.
- 필수 입력은 문서 종류와 파일이다.
- 문서 종류는 `회의록`, `과업요청서`, `제안서`, `기타`다.
- 문서명은 파일명으로 자동 입력되는 값을 수정할 수 있다.
- 프로젝트, 등록자, 등록일시는 현재 문맥에서 자동 기록하므로 입력받지 않는다.
- 문서 종류는 우선 분류·표시용 메타데이터다. 종류에 따라 AI 처리 방식이 달라진다고 약속하지 않는다.
- 허용 확장자와 용량은 실제 처리 계약이 정해지지 않았으므로 목업에서 단정하지 않는다.

### 산출물별 화면 성격

- 받은 문서: 목록에서 등록 문서와 처리 상태, 다음 작업을 찾는다.
- 요구사항: 출처, 생성·확정 상태, 정의서 생성 요청 여부를 비교하고 상세에서 AI와 구체화한다. 관련 화면은 후보로 확인한다.
- 요구사항정의서: 요구사항에서 생성된 상세 요건과 연결 BRD를 확인한다.
- BRD: 시스템, 작업 상태, 확인 필요 여부와 작업 진입점을 확인한다.
- 작업 목업: 화면별 현재 버전과 수정 상태를 확인한다.
- 개발요청서: 전달 상태와 개발 산출물 수신 현황을 확인한다.
- 메뉴구조도: 시스템 단위 목록을 보여주고 편집은 별도 작업 화면으로 보낸다.
- 솔루션 목업: 현재 운영 화면에서 수집된 읽기 전용 자료를 확인한다.
- 추적 매트릭스: 일반 목록이 아니라 요구사항별 단계 연결을 계산한 표로 보여준다.
- 기타 산출물: 개발요청서별 후속 산출물 수신 현황과 문서 접근점을 보여준다.

## 화면 구성 원칙

모든 목록형 화면은 다음 순서를 기본으로 한다.

1. 페이지 제목과 한 문장 목적
2. 핵심 건수 또는 현재 상태 요약
3. 필요한 경우 검색·필터
4. 비교 가능한 표
5. 행 단위의 구체적인 다음 행동

채워진 상태, 빈 상태, 오류 상태, 로딩 상태는 동시에 렌더하지 않는다. 설계 설명은 실제 화면 아래의 보이는 메모로 붙이지 않고 README나 HTML 주석에 남긴다. 검색과 필터는 데이터가 많거나 판단 축이 있는 화면에만 둔다.

## 카피 원칙

- 제목과 설명은 사용자가 이 화면에서 할 일을 먼저 말한다.
- 버튼은 `목적어 + 행동`으로 쓴다: `문서 등록`, `요구사항 검토`, `BRD 작업 시작`, `저장소 반영 재시도`, `로그아웃`.
- 상태는 처리 구분과 현재 단계를 나눠 보여준다. 처리 구분은 `처리 대기`·`요구사항 대상`·`참고 문서`다. 문서 준비 단계는 `내용 추출 중`·`내용 정리 중`·`정리 내용 확인`·`준비 완료`·`문서 처리 오류`이며 요구사항 단계와 섞지 않는다.
- 요구사항 상태는 `생성 완료`·`확정 완료`로 표시하고, 정의서 생성 요청 여부는 `요청 전`·`요청 완료`로 분리한다.
- 비유, 의인화, 훈계, 혼잣말을 쓰지 않는다.
- 내부 구현어는 사용자 언어로 바꾼다: `레포`는 `저장소`, `as-is`는 `현재 운영 화면`, `스킬`은 역할이 드러나는 도구 이름.
- 오류는 `무슨 일 + 이유 + 다음 행동` 순서로 쓴다.
- 설명하지 않아도 아는 조작을 장문으로 해설하지 않는다.

## 시각·상호작용 원칙

- 공통 셸, 표 중심 구성, 밀도 수준 6은 유지한다.
- 주요 버튼과 텍스트 링크는 키보드 초점과 최소 44px 조작 영역을 확보한다.
- 데스크톱에서는 표 비교성을 지키고, 좁은 화면에서는 페이지 전체가 가로로 넘치지 않게 표 컨테이너만 스크롤한다.
- 첫 화면에서 제목, 주요 행동, 검색·필터, 표 머리가 지나친 설명 없이 보여야 한다.
- 추적 매트릭스의 빈 칸은 `—` 하나로 모호하게 두지 않고 `요청 전`, `미생성`, `해당 없음`처럼 이유를 직접 쓴다.

## 데이터 모델 보완

`adk_builder_received_document`에 `document_type`과 파일/직접 입력 원문, AI 정리본, 문서 준비 상태를 둔다. 파일은 선택이며 파일 또는 직접 입력 중 하나 이상이어야 한다. 원문은 보존하고 정리본은 분리한다. 회의록의 회의 일시·참석자는 선택 입력이며 AI 제안을 사람이 확인한다. API 재시도 이력은 별도 `adk_builder_document_processing_run`에 둔다.

## 검증

- 금지한 인공 문구와 내부어가 남지 않았는지 정적 검사한다.
- 한 화면에 서로 배타적인 상태가 함께 렌더되지 않는지 확인한다.
- 모든 HTML의 공통 셸, 링크, 폼 라벨, 표 머리 구조를 검사한다.
- 전체 화면을 데스크톱과 모바일 너비에서 브라우저로 렌더한다.
- 받은 문서 목록, 문서 등록, BRD, 추적 매트릭스를 대표 화면으로 눈으로 확인한다.
- 페이지 전체 가로 넘침, 주요 행동 가시성, 표 읽기, 오류 안내를 점검한다.

## 후속 작업

- 받은 문서 상세/처리 진행 화면
- 요구사항·정의서·BRD 등 산출물별 상세와 작업대
- 개발 전송 관리 화면
- 다중 등록과 부분 성공 정책
- 파일 형식·용량·보안 검사 계약
- 대규모 솔루션 목업 탐색을 위한 검색·시스템 필터 상세
