# 개발요청서를 넘길 때 무엇을 어떤 배치로 보내나 — 전송 꾸러미

> **이 문서가 답하는 질문 하나: 「개발요청 전송」을 누르면 개발 손에 무엇이 어떤 배치로 놓이나.**
>
> 어디로 어떻게 쏘나(주소·인증·몸의 모양)는 여기 없다 — `2026-08-07-handoff-to-dev-design.md` 와
> `docs/requests-to-dev.md` 다. **그쪽 답이 안 왔어도 이 문서는 선다** — 꾸러미는 파일 트리로 못 박고,
> 실어보내는 방법은 `DevHandoffGateway` 뒤에 가둔다.
>
> ⭐ **이것은 디벨롭과의 계약서다.** 그래서 이 문서의 판정 기준은 「예쁘냐」가 아니라
> **「빠진 칸으로 나중에 다툴 자리가 있나」**다.

---

## 실측 — 재료가 어디까지 손에 있나

**잰 날 2026-08-22.** 코드로 쟀다.

| 꾸러미 칸 | 지금 어디에 있나 | 상태 |
|---|---|---|
| 본문 (요구사항·화면·백엔드·완료조건·확인필요) | `dev_request.content_json` 스냅샷 | 있다 |
| 개발 범위 / 운영 반영 / 범위 밖 | `content_json` 이 `DEVELOP`·`OPERATE`·`OUTSIDE` 로 이미 갈라 담는다 | 있다 |
| 전달사항 · 개발완료일 · 배포일 · 첨부 | `V44` · `V45` · `requestDelivery()` | 있다 |
| 목업 to-be | 완료한 FRD 워크트리의 `core/<시스템>/pages/<화면ID>.html` | 있다 |
| 목업 as-is · 기능정의서 as-is | 개발요청서에 고정한 `workspace_base_sha` 판 | 있다 |
| **기능정의서 to-be** | AI 결과를 전송 전에 FRD 워크트리의 `<화면ID>.md`로 쓰고 별도 커밋한다 | 있다. 생성 실패 시 전송 차단 |
| 마커 · 메모 · 코멘트 | `frd_screen_marker` · `_memo` · `_memo_comment` | ⛔ 계약에 안 실린다 |
| 메뉴(IA) 변경 | IA DB. `content_json` 에 칸이 없다 | ⛔ 없다 |
| 앞 개발요청서 번호 | 전송 설계가 요구하는데 DR 표에 열이 없다 | ⛔ 없다 |
| 백엔드의 근거 · 나온 요구사항 · 「변경 없음」 | FRD DB 에는 **있는데 스냅샷이 버린다** | ⛔ 버려진다 |
| 기획 레포 푸시 | FRD 워크트리는 **커밋만 한다.** `push` 는 `IaPublisher` 에만 있다 | ⛔ 미구현 |

⭐ **꾸러미를 만드는 재료는 워크트리다.** 완료할 때 `commitChanges` 가 돌고 **워크트리는 지워지지 않는다**
(`worktree remove` 는 `reset`·`rollback` 안에만 있다). 그래서 as-is(커밋 앞판)와 to-be(커밋 뒷판)를
같은 자리에서 뽑을 수 있다.
⛔ **전송이 끝나기 전에 워크트리를 지우는 코드를 넣지 마라** — 계약서를 만들 재료가 사라진다.

⚠ **화면 0장이 정상이다.** 간단 변경(`completeFastTrack`)·백엔드만인 FRD 는 **워크트리도 커밋도 없다.**
꾸러미가 `screens/` 없이도 성립해야 하고, 검증이 「화면 ≥ 1」을 요구하면 그 FRD 는 영영 못 나간다.

## 꾸러미 — 이 배치로 나간다

```
DR-003/
├─ dev-request.md
├─ expected-back.md
├─ manifest.json
├─ attachments/
│  └─ <기획자가 붙인 파일>
└─ screens/
   └─ <시스템>/
      ├─ assets/                  css · js · 이미지 한 벌
      └─ <화면ID>/
         ├─ as-is.html   to-be.html
         ├─ as-is.md     to-be.md
         └─ changes.md
```

### 시스템 층이 왜 있나 — 목업이 혼자 서게 하는 값이다

목업은 추출된 실물이라 **`../assets/css/style.css` 에 기대고 있다.** 그냥 `screens/<화면ID>/` 로 옮기면
개발이 열었을 때 **스타일이 다 깨진다.**

시스템 층을 하나 두면 `screens/<시스템>/<화면ID>/to-be.html` 의 `../assets/...` 가
**`screens/<시스템>/assets/...` 를 저절로 가리킨다 — 파일 안을 한 글자도 안 고친다.**

⛔ **`screens/assets/` 한 벌로 잡지 마라.** FRD 하나가 두 시스템 화면을 건드릴 수 있고
(`FrdScreen.systemCode` 가 화면마다 있다) 그때 자산이 부딪힌다.

⛔ **스킨을 고르지 않는다 — `core/<시스템>/assets/` 를 통째로 붓는다 (2026-08-24 구현이 뒤집었다).**

처음에는 「고른 스킨 한 벌만 붓고 무엇을 골랐는지 적는다」로 정했는데, 짜 보니 **그게 더 위험했다.**

- ⛔ **고르려면 링크를 갈아야 한다.** `SkinRewriter` 는 「저장본을 고치지 않는다 · 치환은 응답에서만」이
  자기 계약이다. 꾸러미는 저장본이라 그 길을 쓸 수 없고, 쓰면 **원본과 대조가 안 된다**
- ⛔ **고르는 코드는 스킨 폴더 이름을 쥐어야 한다.** 안 고르면 **그 질문 자체가 없어진다** —
  `iks`·`tnj` 꼴 글자가 코드에 들어올 자리가 사라진다
- ⭐ 기관 갈래 **어느 것을 열어도 그림이 뜬다**

`manifest.json` 에는 **어디서 떠 왔나**(`assetRoots`)를 적는다 — 무엇을 골랐나가 아니다.

### 이름은 폴더도 파일도 영문이다 — 2026-08-25 병주 지시로 넓혔다

화면 폴더는 **화면ID**(`wv-card-list` 꼴)다. 사람이 읽는 화면명은 md 안에 있다.
⛔ **한글 폴더명을 쓰지 마라** — zip 으로 실어보내면 인코딩에서 깨진다.

⭐ **파일 이름도 영문이다** — `dev-request.md` · `changes.md`.
종전에는 `개발요청서.md`·`변경내용.md` 였고 `java.util.zip` 의 UTF-8 이름 + 언어 인코딩 비트에 기댔다.
그 주석이 스스로 「**옛 도구에서 깨질 수 있다**」고 적어 뒀다 — 실물을 받아 보고 그 위험을 없앴다.
⛔ **한글 파일명으로 되돌리지 마라.** 이제 꾸러미에 한글 이름이 하나도 없다.
⚠ **뜻은 잃지 않았다** — 8절이 파일마다 「무엇인가」를 한 줄로 적는다(README 를 뺀 그 자리).

`expected-back.md`가 필수 계약 파일로 추가된 판의 `manifest.json.specVersion`은 **`2`**다.

### 화면마다 넷이 앉는 까닭

| 파일 | 무엇 | 왜 |
|---|---|---|
| `as-is.html` · `as-is.md` | 완료 커밋 **앞판** | ⭐ **계약은 「무엇을 → 무엇으로」다.** to-be 만 주면 개발이 diff 를 스스로 짜고, 뒤에 「원래 그랬다/아니다」를 가릴 근거가 없다. 워크트리에 이미 있어 거의 공짜다 |
| `to-be.html` | 완료 커밋 **뒷판** | 어떻게 보여야 하나 |
| `to-be.md` | **전송 전 AI가 만든다** (아래) | 계약서의 칸이 비지 않게 한다 |
| `changes.md` | 그 화면의 변경 목록 | 목업이 말 못 하는 것(까닭·주의)을 담는다 |

⛔ **화면 폴더에 「FRD 문서」를 넣지 마라.** FRD 는 작업 단위 하나당 하나(`FRD 1개 = 작업 1개`)라
화면마다 넣으면 **같은 문서가 N벌**이 되고 갈린다. FRD 본문은 `dev-request.md` 가 품는다.

### `to-be.md` 는 전송 전에 AI가 만든다 — 병주 확정 2026-08-22

지금은 **캔버스 AI가 건드린 화면만** `frd_screen_history.md` 를 갖는다. 목업만 만든 화면은 `null` 이라
제안했던 「변경 예정 기능정의서」 칸이 **대부분 빈다.**

**전송 전에 AI가 만든다.** 재료는 셋 다 손에 있다 — `as-is.md` · 목업 앞뒤판 · 그 화면의 변경 목록.

- ⚠ **이미 `md` 가 있는 화면은 그것을 쓴다.** 캔버스 AI가 쓴 것을 덮어쓰지 않는다 — 사람이 대화로 만든 것이 더 세다
- ⚠ **AI 실행 한 자리가 늘고, 사람이 검토할 것이 늘어난다.** 이것이 이 선택의 값이다
- ⭐ **시동은 FRD 작업 완료가 스스로 건다 (병주 확정 2026-08-25).** 개발요청서가 만들어지는 그 순간
  목업이 커밋되어 재료 셋이 확정되기 때문이다. 사람이 상세 화면에서 버튼을 찾아 누르게 하지 않는다 —
  버튼은 **실패한 화면을 다시 돌리는 용도**로만 남는다. 못 걸어도 완료는 성립하지만 기능정의서가 없으면 전송을 차단한다.
  ⚠ 간단 변경 FRD(작업대 없음)는 `frd_screen_history` 가 없어 만들 재료가 없다 — 거기선 비는 것이 정상이다
- ⛔ **화면 작업 중에 md 를 항상 같이 만들게 하는 쪽으로 되돌리지 마라** — 화면 작업이 무거워지고,
  **고칠 때마다 md 를 다시 맞춰야 해서** 목업과 md 가 갈리는 자리가 오히려 늘어난다

## `dev-request.md` 에 무엇이 들어가나

**본문은 재생성물이다** — AI가 쓰고 사람이 손으로 안 고친다(전송 설계). 그래서 **절마다 재료가
어디서 오는지 못 박는다.** ⛔ **재료 없는 절을 만들지 마라** — AI가 채우려고 지어낸다.

| 절 | 재료 |
|---|---|
| **표지** | `label()` · `title` · `systemCode` · `facetList()` · `frdLabel()` · `ownerLabel()` · 생성/전송 시각 · **전송키** |
| **1. 요청 내용** | 요청 원문 `content.summary()` = `frd.sourceText()` + 승인 전 확인한 인터뷰 요구사항 요약 `content.interviewSummary()` |
| **2. 요구사항 전체** | `content.requirements()` — 순번 · 요구사항 · **성격**(개발/운영/범위밖) · 비고 |
| **3. 개발 범위** | `developmentRequirements()` (`DEVELOP`) |
| **4. 제외 범위** | `operationRequirements()`(`OPERATE`) + `excludedRequirements()`(`OUTSIDE`) + 각 `note` |
| **5. 완료 조건** | `acceptanceCriteria()` |
| **6. 확인 필요** | `openIssues()` |
| **7. 화면 외 구현** | 백엔드 항목을 **갈래로 묶어** 보여 준다 (아래 절) |
| **8. 화면별 산출물 목록** | ⭐ **`manifest.json` 에서 생성한다** |
| **9. 전송 정보** | 개발 완료 희망일 · 배포일 · 전달사항(`planner_comment`) |
| **10. 첨부 목록** | `attachment_name` · `attachment_size` |

### 4절이 계약의 심장이다

다툼은 「했다/안 했다」보다 **「이건 범위였다/아니었다」**에서 난다. `OPERATE`·`OUTSIDE` 가 이미
갈려 있고 `note` 에 까닭까지 있다.

⛔ **화면(`dev-request.html`)의 배치를 그대로 옮기지 마라** — 거기서는 아래쪽 `<aside>`·`boundary-grid` 에
작게 앉아 있다. **md 에서는 개발 범위 바로 뒤 큰 절**이다.

### 8절은 손으로 적지 않는다

`manifest.json` 의 파일 목록에서 **생성한다.**
⛔ **손으로 적으면 `screens/` 폴더와 갈리고, 갈린 순간 어느 쪽이 맞는지 아무도 모른다** —
「산출물 12종 vs 14종」이 갈린 그 자리다.

⛔ **화면별 변경 내용을 md 에 다시 펼치지 마라.** 상세의 정본은
`screens/<시스템>/<화면ID>/changes.md` 이고 **8절은 색인만**이다. 둘 다 적으면 사본 둘이 된다.

### 꾸러미에 `README`와 처리 규약은 넣지 않고 돌려받을 대상만 넣는다 — 2026-08-25 교정

「개발이 배치를 읽고 처리해야 하니 README 가 있어야 하지 않나」를 검토하고 **뺐다.**
뻔한 생각이라 다시 올라온다 — 까닭을 적어 둔다.

**자리가 이미 셋 있다.** 어떤 파일이 무엇인가는 **8절**, 기계가 읽을 목록·해시·커밋SHA·스킨은
**`manifest.json`**, 이 DR에서 개발 완료 뒤 빌더에 돌려줄 대상은 **`expected-back.md`** 다.

- ⛔ **8절과 갈리는 셋째 사본이 된다.**
- ⛔ **README 는 DR마다 내용이 같다** — 재생성물이 아니라 정적 텍스트를 매 꾸러미에 N벌 복사하는 것이고,
  배치가 한 번 바뀌면 **이미 나간 N벌이 전부 거짓**이 된다. 되돌릴 길이 없다.
- ⭐ **`expected-back.md`는 꾸러미에 싣는다.** 이 DR의 화면·도메인·테스트 회신 대상과 개발자가
  실제 결과를 채울 상세 양식을 담는 사람용 정본이다. `manifest.expectedBack`과 같은 대상 자료에서
  생성하고, `dev-request.md` 11절은 두 계약 파일을 따르라는 안내만 둔다.
  백엔드 `target`이 `domains/<도메인>/<모듈>.md` 형태가 아니어도 `backendChanges`에 원래 대상과
  변경 내용을 남겨 구현 결과 회신 대상에서 사라지지 않게 한다.
  실제 수신 API·검증·목업 및 도메인 반영은 후속 단계가 맡는다.
- ⭐ **테스트 시나리오는 우리가 먼저 적어 보낸다 (2026-08-27 병주 확정).** `expected-back.md` 의
  단위·통합테스트 회신 양식은 종전에 시나리오·단계·기대 결과가 전부 `<…>` 빈 칸이었다 — 개발이 채우는
  구조라 돌아오는 것이 기계가 못 읽는 모양이 됐다. 이제 **빌더 AI 가 FRD 의 완료 조건마다 통합테스트 TC,
  화면 외 구현 항목마다 단위테스트 TC** 를 미리 쓴다(`DevRequestTestScenarioWorker` · 스냅샷의
  `testScenarios` 칸). 서식은 bzp 빌더 E2E 시나리오 TEMPLATE 을 빌렸다 — `TC-nnn` · 의존 · 조건(`(mock)` 표기) ·
  행위 · 결과. 개발은 **실제 결과 · 판정 · 근거만** 채운다. 완료 조건 ↔ TC 대응표가 통합테스트 절 머리에 앉는다.
  ⚠ **실행은 개발 몫이다** — 빌더는 대상 시스템을 띄울 수 없다(g2c 를 모른다). ⚠ **시나리오 없이도 계약은
  성립한다** — 안 만들어졌으면 종전 빈 양식이 그대로 나가고, 전송 전 검증은 차단이 아니라 경고로만 말한다.
  ⛔ **이미 있으면 덮지 않는다.** 만들기는 상세를 열거나 전송을 누를 때(`DevRequestPrecheck`) 없으면 청한다 —
  개발요청서 만들기 자리(`createFromFrd`)에 붙이지 않은 것은 2026-08-27 그 파일을 다른 세션이 고치고 있었기 때문이다.

**대신 둘을 한다.**

1. **8절을 「목록」이 아니라 「목록 + 각 파일이 무엇인가」로 만든다** — 한 줄씩. README 가 하려던 일 중
   실제로 필요한 것은 이것 하나다.
   ⭐ **파일 이름이 뜻을 담고 있는 것이 여기서 값을 한다** — `screen-1.html`·`screen-2.html` 로 지었으면
   README 가 필요했다.
2. **`manifest.json` 에 꾸러미 규격 판 번호 한 칸.** README 가 정당해지는 자리는 **배치가 판을 바꿀 때**
   하나뿐이고, 그건 사람이 읽는 글이 아니라 **기계가 갈래를 타는 값**이어야 한다.

### 1절은 원문과 승인된 인터뷰 요약을 구분한다 — 병주 변경 2026-08-26

요청 원문은 사람이 처음 입력한 말을 그대로 싣고, 인터뷰 요구사항 요약은 분석 결과 승인 전에 확인한
마지막 `SUMMARY`를 그대로 싣는다. 둘을 합쳐 「목적과 배경」 같은 새 문장으로 다시 쓰지 않는다.
원문은 최초 근거, 인터뷰 요약은 확정한 해석, 2절 요구사항 전체는 실행 항목이라는 역할을 유지한다.
이 필드가 생기기 전에 만든 개발요청서는 연결된 FRD의 마지막 `SUMMARY`를 상세 조회와 전송 꾸러미에서
보완해 사용한다. 요약 기록 자체가 없어도 두 구획은 숨기지 않고 기록이 없음을 명시한다.

### 「공통 정책과 예외」는 절을 따로 만들지 않는다 — 병주 확정 2026-08-22

응답속도 · 권한 · 정책처럼 **목업이 없는 요건**을 전송 설계가 요구했는데,
`FrdAnalysisNote.Kind` 는 `ACCEPTANCE_CRITERION`·`OPEN_ISSUE`·`WORK_MODE_FAST_TRACK` 셋뿐이라
대응하는 열이 없다.

**7절을 갈래로 묶어 그 자리를 삼는다.** `PERMISSION`·`OTHER` 가 이미 그 자리다 —
**새 열도 마이그레이션도 0이다.**

⛔ **`POLICY` 노트 종류를 새로 만들지 마라.** 그러면 같은 것(권한 변경)을 적을 자리가
백엔드 항목과 노트 둘이 되고, **기획자가 어디에 적었는지에 따라 계약서에서 사라진다.**
⚠ **남는 값**: 「정책」이 「구현」 목록에 섞여 눈에 덜 든다. **갈래로 묶어 보여 주는 것**으로 갚는다 —
7절을 `API` · `데이터` · `권한` · `배치` · `알림` · `기타` 소제목으로 갈라 찍는다.

## 백엔드 개발 사항 — 여기가 계약의 약한 쪽이다

**화면과 사정이 근본적으로 다르다.** 화면은 as-is 파일이 클론에 실재해서 대조가 공짜인데,
**백엔드의 as-is 는 빌더 손에 없다.** 운영 소스를 읽지 않기 때문이다.
⛔ **여기서 g2c 경계를 넘어 소스를 읽으려 하지 마라** — 재구성이 무의미해지는 자리다.

그래서 백엔드는 **「대조」로 계약을 만들 수 없고 「유일한 지목 + 근거 + 판정 방법」** 셋으로 만든다.

### 버리던 넷을 살린다 — 병주 확정 2026-08-22

**열은 이미 다 있다.** `DevelopmentRequestContent.BackendChange` 가 안 담아서 생긴 구멍이라 고치는 값이 거의 없다.

| 살리는 것 | 지금 | 왜 계약에 필요한가 |
|---|---|---|
| `evidence` | FRD DB 에 있는데 스냅샷이 안 담는다 | AI가 **왜 그렇게 판단했는지**가 사라진다. 개발이 되물을 데가 없다 |
| `requirementSeq` | 같이 버려진다 | 요구사항↔백엔드 추적이 끊긴다. 추적 매트릭스가 이걸 요구한다 |
| **`required = false`** (확인했고 변경 없음) | `.filter(change -> change.required())` 가 버린다 | ⭐ **이것이 백엔드의 as-is 대응물이다.** 「이건 안 봤나?」를 개발이 되묻지 않게 한다 |
| `category` 원값 | 라벨만 담고 있다 | 되울려 받을 때 갈래를 기계로 못 맞춘다 |

### 항목마다 「판정 방법」을 더한다 — 병주 확정 2026-08-22

화면은 **목업이 완료 조건 노릇을 한다.** 백엔드는 그것이 없어서, 항목마다
**「무엇으로 됐다고 하나」 한 줄**을 새로 받는다.

⛔ **전체 완료 조건(`ACCEPTANCE_CRITERION`)으로 갈음하지 마라.** 그건 FRD 하나에 걸린 것이고,
백엔드 항목 다섯 중 어느 것이 남았는지 못 가른다 — 검수가 통째로 되거나 통째로 안 된다.

⛔ **종류별로 다른 틀(API면 요청/응답, DATA면 테이블·열…)을 지금 짓지 않는다.**
그러면 기획자가 그것까지 정해야 하고 FRD 인터뷰·작업대가 통째 넣어진다.
**계약은 「무엇이 필요하다 + 무엇으로 됐다고 하나」까지 담고, 상세 설계는 개발이 한다.**

### `target` 이 자유 글자인 것은 남는 위험이다

`varchar(255)` 라 「결제 API」로 적히면 개발이 **어느 것인지 모른다.** 화면은 화면ID로 유일한데
백엔드는 그 자리가 비었다.

⭐ **백엔드에도 as-is 자리가 하나 있다.** 추출기가 `domains/<도메인>/<모듈>.md` 를
「화면 없는 업무 규칙·흐름」으로 내고, **검사기 A-3 가 앵커 실재를 이미 검사한다.**
백엔드 항목을 도메인 앵커로 걸면 그것이 대조 지점이 된다.

⚠ **다만 실측(2026-08-09)으로 `domains/` 는 `.gitkeep` 뿐이고 사람이 채운다.**
그래서 **필수 칸으로 잡으면 전송이 통째로 막힌다** — 아래 검증에서 **경고 층**에 둔다.

## 검증 — 차단과 경고 두 층이다 (병주 확정 2026-08-22)

### ⛔ 기획 저장소 검사는 기저를 상쇄한 뒤에 막는다 — 2026-08-25 실물에서 고쳤다

**무슨 일이 있었나.** `DR-003` 전송 화면에 **「막는 것 28건」**이 떴다. 같은 때 클론을 대상으로
검사기를 직접 돌리니 **red 가 정확히 28** 이었다 — **그 FRD 가 만든 위반은 0건**이고
전부 기획 레포에 원래 깔려 있던 것이었다(도메인 색인 · `ui-base-wrap` 의 `display:none` · 팝업 IA 구멍).

⭐ **이 저장소는 그 답을 이미 알고 있었다.** `DraftChecker` 가 2026-08-14 에 같은 벽을 만나 적어 뒀다 —
「실물 레포에 **이미 red 26 · review 17 이 깔려 있어** 「전체가 초록이어야 저장」은 **애초에 불가능**하다.
**남이 만든 빨강이 기획자를 영원히 막는다**」. 저장 전 검사는 그때 상쇄를 넣었는데
**전송 전 검증에만 안 들어와 있었다.**

**그래서 이렇게 한다.**

1. 워크트리를 검사한다 (지금까지 하던 것)
2. **클론(기저)을 한 번 더 검사한다** — 값은 검사 한 번(`DraftChecker` 실측 **~0.95초**)
3. **기저에 같은 것이 있는 red 는 막지 않는다.** 워크트리에만 새로 생긴 것만 차단이다

⛔ **기저 red 를 안 보이게 하지 마라.** 사라지는 게 아니라 **경고로 내려간다** —
「이 레포에 원래 N건이 있다」는 알려야 하고, **고칠 자리는 추출기와 기획팀**이지 이 개발요청서가 아니다.

**조심할 것 셋 — 시험으로 못 박았다.**

| 무엇 | 왜 |
|---|---|
| ⚠ **줄 번호를 열쇠에 넣지 않는다** | 워크트리가 파일 위에 줄을 더하면 기저 red 의 줄이 밀려 **「새로 생긴 것」으로 오인**된다. 열쇠는 `게이트\|파일\|내용` |
| ⚠ **개수로 센다** | 기저에 2건인데 워크트리에 3건이면 **1건만** 새것이다 |
| ⛔ **기저를 못 재면 막지 않는다** | 누구 탓인지 모르는데 막으면 **이 장치가 없애려는 상태(영영 못 나감)로 돌아간다.** 경고로 올려 사람이 본다 |

⚠ **red 가 0건이면 기저를 아예 안 잰다** — 값을 안 치른다.

⭐ **이미 있는 기계를 쓴다.** 기획 레포 검사기 `node verify/run.mjs <뿌리>` 는 레포 전집을 요구하는데
**워크트리가 바로 레포 전집이다.** A-2(`data-screen-id`↔파일명) · A-5(styleguide 허용 class) ·
A-1(html/md 짝)이 **AI가 만든 to-be 를 실제로 잡는다.** 새 검사기를 만들 것이 아니다.

⚠ **검사기는 워크트리에서 돌린다 — 꾸러미 배치와 무관하다.** 그래서 꾸러미를
「사람이 읽기 좋은 배치」로 골라도 검증이 약해지지 않는다.
(실측: 검사기는 **파일 한 장만 넘겨 판정받을 수 없고** 결과가 JSON 이 아니다 — 종료코드와 사람 읽는 글이다.)

| 차단 — 전송 버튼이 안 눌린다 | 경고 — 보고 넘긴다 |
|---|---|
| **검사기 red** | 검사기 「사람이 볼 것」이 늘었다 |
| 개발 범위(`DEVELOP`) 항목 0건 — 보낼 것이 없다 | 완료 조건 0건 |
| 화면이 미작업·실패로 남아 있다 | 「확인 필요」가 미결로 남아 있다 |
| **임시 화면ID 잔존 / 신규 화면 표준ID 미채번** | 백엔드 항목의 대상·판정 방법 빈칸 |
| to-be html·md 실파일 부재 | 백엔드 항목에 도메인 앵커가 없다 |
| 워크트리에 미커밋 변경 — DB와 파일이 갈린다 | 마커·메모에 미응답 코멘트 |
| 개발완료일 · 배포일 순서 (이미 있다) | 기능정의서 as-is 부재 (신규 화면은 정상) |

⛔ **「임시 화면ID 잔존」을 경고로 내리지 마라.** 표준 채번을 개발요청서 생성 시점으로 미뤘으므로
(`b91624d`), 임시ID가 새 나가면 **개발이 그 글자로 파일을 만든다.** 되돌리는 값이 가장 비싼 한 건이다.

⛔ **검사기를 경고로 내리지 마라.** 그러면 개발이 **못 쓰는 목업**이 계약에 실려 나간다.
AI 초안이 styleguide 를 자주 깨서 전송이 막히면, 고칠 자리는 초안 쪽이다.

## 정한 것과 그 이유

| 무엇 | 정한 것 | 왜 |
|---|---|---|
| 배치 | `screens/<시스템>/<화면ID>/` + `screens/<시스템>/assets/` | 목업의 `../assets/` 가 저절로 맞는다. 파일 안을 안 고친다. 시스템 둘일 때 자산이 안 부딪힌다 |
| 스킨 | ⛔ **고르지 않는다.** 자산을 통째로 붓고 `assetRoots` 만 적는다 | 고르려면 링크를 갈아야 하고(원본과 대조 불가) 코드가 스킨 폴더 이름을 쥐게 된다 |
| 폴더 이름 | 영문 화면ID | 한글은 zip 인코딩에서 깨진다 |
| as-is | **화면마다 같이 보낸다** | 계약은 「무엇을 → 무엇으로」다. 워크트리 커밋 앞판이라 거의 공짜다 |
| 화면별 FRD 문서 | **안 넣는다** | FRD 는 작업 단위당 하나다. 화면마다 넣으면 N벌이 되고 갈린다 |
| 기능정의서 to-be | **전송 전 AI가 만든다.** 이미 있으면 그것을 쓴다 | 목업만 만든 화면은 지금 `null` 이라 계약 칸이 빈다 |
| `dev-request.md` 1절 | **요청 원문과 인터뷰 요구사항 요약을 구분해 싣는다.** 둘을 합쳐 다시 쓰지 않는다 | 원문은 최초 근거이고, 요약은 사용자가 분석 결과 승인 전에 확인한 해석이다 |
| 「공통 정책과 예외」 | **절을 따로 안 만든다.** 백엔드 항목의 갈래가 그 자리다 | 적을 자리가 둘이면 기획자가 어디에 적었는지에 따라 계약서에서 사라진다. 새 열이 0이다 |
| 화면별 산출물 목록 | **`manifest.json` 에서 생성한다.** 목록 + 각 파일이 무엇인가까지 | 손으로 적으면 `screens/` 폴더와 갈리고, 갈린 순간 어느 쪽이 맞는지 아무도 모른다 |
| 꾸러미 `README` | ⛔ **안 넣는다.** 규격 판 번호는 `manifest.json` 의 칸으로 | 8절과 갈리는 셋째 사본이 된다. DR마다 같은 글을 N벌 복사하고, 배치가 바뀌면 나간 N벌이 전부 거짓이 된다 |
| 마커 · 메모 | **화면별 `changes.md` 에 싣는다** | 마커가 목업의 어느 지점인지까지 담는다. 이미 DB에 있어 새 열이 0이다 |
| 메뉴(IA) | **화면의 메뉴 경로만.** 빌더 DB(`IaScreenLink`)에서 읽는다. 델타는 안 싣는다 | FRD 흐름이 IA를 안 건드려 델타를 계산할 근거가 없다. 정본이 빌더 DB다 |
| 앞 개발요청서 | **화면 겹침으로 후보를 대고 사람이 고른다** | 자동으로 못 찾는다(`sourceRef` 는 조인 금지). 화면 겹침과 같은 업무인 것은 다르다 |
| 꾸러미 지문 | **필수다** | 8절과 규격 판 번호가 둘 다 여기 기댄다 |
| **「돌려받을 것」 칸** | **`manifest.json` 에 화면ID·모듈 목록 하나** (2026-08-24) | 역류가 as-is 재료를 실어 오므로, 수신 쪽에 「목록 밖 화면ID 거절」의 근거가 필요하다. **대조 없이 자리를 지키는 유일한 문 지킴이다** |
| 백엔드 스냅샷 | 근거·나온 요구사항·「변경 없음」·갈래 원값을 **살린다** | 열은 이미 있다. 스냅샷이 안 담아서 생긴 구멍이다 |
| 백엔드 판정 | **항목마다 「무엇으로 됐다고 하나」 한 줄** | 화면은 목업이 그 노릇을 한다. 백엔드는 그게 없으면 항목별 검수를 못 한다 |
| 백엔드 상세 설계 | **계약에 안 담는다** | 담으면 기획자가 API 요청/응답까지 정해야 하고 FRD 가 통째 넣어진다 |
| 도메인 앵커 | **경고**다 | `domains/` 가 실측으로 비어 있다. 필수로 잡으면 전송이 통째로 막힌다 |
| 검증 | 차단 + 경고 두 층. **검사기는 차단** | 못 쓰는 목업이 계약에 실려 나가는 것을 막는다 |
| 검사기 실행 자리 | **워크트리** | 레포 전집이 필요하다. 꾸러미 배치와 무관하다 |
| 실어보내는 방법 | **지금 안 정한다.** `DevHandoffGateway` 뒤 | `requests-to-dev.md` 의 답(주소·몸의 모양·상태코드표)이 안 왔다 |

`frd_screen_marker` · `_memo` · `_memo_comment` 를 화면별 `changes.md` 의 절 하나로 싣는다.
⭐ **마커는 `selector`·`elementLabel`·상대좌표를 갖고 있어** 「목업의 어느 지점인가」까지 적힌다 —
변경 목록만으로는 못 하는 말이다.

⛔ **「마커만 싣고 메모·생가는 버린다」로 줄이지 마라.** 마커 없이 생가로만 말한 지시가 사라진다.
⚠ 값: 이미 DB에 있는 것을 읽어 렌더하는 것이라 새 열이 0이다.

### 메뉴는 「그 화면이 어느 메뉴 아래 사는가」만 적는다

⛔ **IA 델타를 계약에 싣지 않는다 — 계산할 근거가 없다.** FRD 흐름은 **IA를 고치지도 읽지도 않는다**
(`ScreenPickWorker:66` 이 화면 짚기에서 `ia.md` 를 명시적으로 걷어냈다). `IaRevision` 이 있지만
**어느 FRD 때문에 바뀌었는지 안 묶여 있다.**

**대신 빌더 DB의 `IaScreenLink` 를 읽어 화면마다 메뉴 경로를 적는다.**
정본이 빌더 DB이므로 클론의 `ia.md`(확정 시점에 굳는 스냅샷)를 읽지 않는다.

⚠ **기획자가 IA에 아직 안 넣은 신규 화면은 빈다.** 그건 **검증 경고**로 잡는다 —
차단으로 올리면 IA를 나중에 정리하는 사업에서 전송이 통째로 막힌다.

### 앞 개발요청서는 후보를 대고 사람이 고른다

> ⭐ **2026-08-24 — 이 기계가 하나를 더 맡는다.** 같은 화면을 두 FRD 가 동시에 잡는 것을
> **편집 시점에는 막지 않기로 정했다**(→ `2026-08-07-dev-feedback-design`). 그러면 옛 화면 잠금이
> 막으려던 문제(「같은 화면을 시점만 달리해 둘이 그리면 개발이 어느 것이 맞는지 모른다」)가
> **전송 시점으로 옮겨온다.**
> ⛔ **그래서 후보에 「앞 DR」만 대지 말고 「지금 열려 있는 DR」도 댄다.**
> **막지는 않는다 — 보여 주고 사람이 확인한다.** 여기가 그 자리인 까닭은 **화면 겹침을 이미 세고 있기 때문**이다.

⛔ **자동으로 못 찾는다.** `Frd` 에 앞 FRD 연결이 없고 `sourceRef` 는 **조인 금지 글자 도장**이다
(2026-08-18 병주 확정). 그래서 열 하나로 끝나지 않는다.

**빌더가 `frd_screen.screen_id` 로 「같은 화면을 건드린 앞선 DR」을 후보로 대고, 전송 레이어에서
사람이 고른다.** 안 고를 수도 있다(첫 요청이면 없는 것이 정상이다).

⛔ **후보를 그대로 채워 넣지 마라.** 화면이 겹치는 것과 **같은 업무인 것은 다르다** —
겹치는 DR이 여럿일 수 있고, 틀린 것이 실리면 개발이 엉뚱한 앞 문서와 이어 읽는다.

### 꾸러미 지문은 필수로 굳었다

`manifest.json` 이 **8절을 낳고 규격 판 번호를 담는다** — 둘 다 여기 기대므로
「실을지」가 더 이상 선택이 아니다. 담는 것: DR번호 · 전송키 · 전송시각 · 기획레포 커밋SHA ·
앞 DR번호 · 자산을 어디서 떠 왔나 · **규격 판 번호** · **계약 파일**의 경로·크기·해시 ·
**자산 요약** · **「돌려받을 것」**(화면ID 목록 + 도메인 모듈 목록).

### ⛔ 자산을 낱개로 담지 않는다 — 병주 지시 2026-08-25 (실물 실측)

**실제로 나간 꾸러미를 받아 보고 고쳤다.** `DRK-0000002` 를 재니 이랬다.

| | |
|---|---|
| `files` 총 | **519** — 자산 **514** + 계약 **5** |
| `manifest.json` | **121,497 바이트** |
| **자산 항목을 빼면** | **1,589 바이트** |
| 자산이 차지한 비율 | **98.7%** — **76배** |

그리고 그 121KB 가 **이슈 본문과 함께 개발에게 갔다.**

⭐ **해시가 값을 하는 것은 계약 파일뿐이다.** 자산은 **추출기 원본을 한 글자도 안 고친 것**이라
개발이 낱개로 검증할 이유가 없다. 무결성은 **묶음 해시 하나**로 갚는다.

```
"files":  [ 계약 파일만 — 경로·설명·크기·sha256 ]
"assets": { "count": 514, "bytes": …, "sha256": "묶음 해시" }
```

⛔ **자산 파일 자체를 꾸러미에서 빼는 쪽으로 가지 마라.** 「목업은 혼자 선다」가 계약이고,
그 화면이 무엇을 부르는지 골라내면 **놓치는 순간 목업이 깨진다.**
**줄이는 것은 지문에 적는 줄 수이고 담는 파일은 그대로다.**

⛔ **`DevRequestPackage.entries` 와 꾸러미 지문(`fingerprint`)은 자산까지 셈한다.**
전송 이력이 그 지문으로 **「어느 판을 보냈나」**를 묶기 때문이다 —
자산을 거기서 빼면 **자산 변경이 이력에 안 잡힌다.** 가르는 것은 `manifest.json` 의 모양 하나다.

⚠ **자산을 가르는 기준은 `DevRequestPackage.isAsset` 하나다.** 8절이 세는 수와
`assets.count` 가 **같은 기준으로 세야** 사람이 읽는 수와 기계가 읽는 수가 안 갈린다.

### 「돌려받을 것」 칸 — 병주 확정 2026-08-24

**역류가 as-is 갱신 재료까지 실어 오기로 정해졌다**(정본 `2026-08-07-dev-feedback-design.md`).
그러면 수신 쪽에 **「이 화면ID 가 이 DR 의 대상인가」**를 판정할 근거가 필요하다 —
그것이 **내용을 대조하지 않고도 엉뚱한 화면을 덮는 사고를 막는** 유일한 문 지킴이다.

⛔ **개발요청서에 상세 사본을 만들지 마라.** DR별 사람용 대상과 회신 양식은 `expected-back.md`,
기계용 대상은 `manifest.expectedBack`이 같은 자료에서 나른다. `dev-request.md` 11절은 둘을 안내한다.
처리 규약과 수신 구현은 꾸러미 밖의 후속 단계다.

⭐ **8절과 갈리지 않는다** — 8절과 이 칸이 **같은 `manifest.json` 파일 목록에서 난다.**
⚠ 도메인 모듈은 8절(화면별)에 없으므로 **이 칸에만 있다** — 백엔드 항목의 `target` 에서 뽑는다

**목록이 아니라 표다.** 이름 하나만 담으면 수신 쪽이 판정을 못 한다.

| 칸 | 왜 필요한가 |
|---|---|
| **시스템 + 화면ID** | 놓을 경로에 시스템 마디가 필요하다. ⛔ **화면ID 하나로는 되찾을 수 없다** — 신규 화면은 색인에 아직 없다 |
| **필수 구성요소** (`pages`·`screen-md`·`index` 중 어느 것) | 「회신이 끝났다」를 셀 근거다. 없으면 **안 보낸 것과 안 바뀐 것이 같아 보인다** |
| **화면 md 를 받나** | `⚑ 보정됨`·`⬛ 네이티브` 화면은 **사람이 정의 블록을 손댔고** `--- 원본 글 ---` 은 검사기가 안을 안 본다. **우리가 아는 사실이니 미리 알려 준다** |
| **도메인 + 모듈** | 화면 축에 없는 것 |

⛔ **전송이 성공한 순간 이 표를 DB 로 굳힌다.** 수신 판정이 「지금 `manifest.json`」을 읽으면,
**꾸러미를 다시 구운 뒤에 이미 나간 계약의 범위가 바뀐다** — 꾸러미 빌더가 같은 출력 경로를 지우고 다시 만든다.

### as-is와 to-be 기준판을 개발요청서에 고정한다 (2026-08-25 교정)

FRD 작업 완료가 만든 개발요청서는 `workspace_base_sha`와 `workspace_head_sha`를 함께 저장한다.

- `as-is.html`·`as-is.md`: `workspace_base_sha`에서 `git show`로 직접 추출한다.
- `to-be.html`·자산: `workspace_head_sha`와 HEAD가 같은 깨끗한 FRD 워크트리에서 복사한다.
- `to-be.md`: AI 결과를 DB 진행 사본에만 두지 않고 전송 전에 같은 워크트리에 쓰고 커밋한다. 새 HEAD를 `workspace_head_sha`로 갱신한다.
- `manifest.json`의 기획 저장소 커밋도 현재 클론 HEAD가 아니라 이 `workspace_head_sha`다.

⛔ 신규 개발요청서 꾸러미를 만들 때 현재 클론이나 현재 DB의 화면 HTML을 다시 읽지 않는다.
화면 없는 간단 변경과 이 기능 도입 전 개발요청서만 기준 SHA가 없으므로 호환 경로를 사용한다.

⚠ **「확인했고 변경 없음」은 방향이 둘인 낱말이다.** 아래 「버리던 넷을 살린다」의 `required = false` 는
**우리가 개발에 「이건 안 바뀐다」고 말하는 것**이고, 역류의 `unchanged` 는
**개발이 우리에게 「확인했고 안 바뀌었다」고 말하는 것**이다. ⛔ **같은 칸으로 뭉치지 마라** — 방향이 반대다.

## 이 줄기가 기대는 전제

1. **워크트리가 전송이 끝날 때까지 남아 있다.** 꾸러미의 재료가 그것이다.
2. **클론의 `manifest.json` 이 `systems[].skins` 를 담고 있다.** 스킨을 고르는 정본이다.
3. **기획 레포 검사기가 워크트리에서 돈다.** 실측으로 순수 읽기라 동시에 돌려도 안 부딪힌다.
4. 개발 창구의 계약(주소·몸의 모양·상태코드표)이 오면 **`DevHandoffGateway` 구현 한 자리만** 고친다.
