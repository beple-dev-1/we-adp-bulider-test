# 기획이 끝난 것을 개발에 어떻게 넘기나 — 개발요청서

> ⚠ **2026-08-20 앞단 개정.** 받은 문서·요구사항·요구사항정의서·BRD를 거치는 설명은 폐기됐다.
> 개발 전달의 출발점은 FRD다. 아래 전달 원칙은 FRD 기준으로 다시 검증하기 전까지 이력으로 본다.
>
> ⚠ **2026-08-21 상태 이름 개정 (병주 확정).** 전달 상태 셋의 이름이 **「대기 · 전송중 · 전송완료」**로 바뀌었다.
> **값도 뜻도 그대로다** — 옛 이름 「안 보냄 · 보내는 중 · 보냄」과 하나씩 같고, 코드값
> (`NOT_SENT` · `SENDING` · `SENT`)은 안 바꿨다. 그래서 마이그레이션이 없다.
> **이 문서 본문은 새 이름으로 고쳤다.** `HANDOFF_HISTORY.md`·캡틴 원장 같은 이력 문서에는 옛 이름이
> 그대로 남아 있다 — 그것을 읽을 때 위 대응으로 읽는다.
> ⛔ **넷째 값을 만들지 마라.** 「거절됨」·「재전송 필요」는 이 셋 안에 이미 있다(명확한 거절은 「대기」,
> 모르면 「전송중」). 아래 갈래표 전체가 셋을 전제로 서 있다.

> **이 문서가 답하는 질문 하나: BRD 하나가 끝났을 때, 개발에 무엇을 어떻게 보내나.**
> BRD 안에서 목업을 고치는 일은 여기 없다(`planner-one-flow`).

```
받은 문서 → 요구사항 → 정의서 → BRD → 작업목업 → [ 개발요청서 ] → (개발)
                                                   └─ 이 문서 ─┘
```

---

## 방향이 반대다

앞 문서(④~⑧ 역류 수신)는 **개발 → 빌더**였다. 여기는 **빌더 → 개발**이다.
빌더가 개발이 제공하는 API 를 부른다.

⚠️ **이것은 g2c 를 아는 것과 다르다.**
빌더가 아는 것은 **「보낼 주소와 형식」**뿐이다. 운영 소스를 읽지 않는다.
개발 저장소를 들여다보거나 화면을 뽑아오기 시작하면 그때 선을 넘는 것이고, 여기서는 넘지 않는다.

---

## 완료의 단위 — BRD 하나

**BRD 하나가 닫히면 개발에 넘길 수 있다.**

| BRD 안에 있던 것 | 무엇이 끝나야 하나 |
|---|---|
| **고칠 화면** | 화면마다 목업이 되어 있어야 한다 |
| **메뉴 일** | 구조도가 고쳐져 있어야 한다 |
| **화면 없는 요건** | 만들 것이 없다. **BRD 에 적혀 있으면 끝난 것이다** |

**닫는 판정은 `planner-one-flow` 가 한다.** 여기는 닫힌 것을 받아 내보낸다.

**업무 단위로 나가는 이유**: 개발도 업무 단위로 받아 만든다.
회의록 하나분을 다 모아 보내면, 업무 셋 중 하나가 늦어서 **다 끝난 둘도 못 나간다.**

## 줄기 — 칸 넷

| | 칸 | 무슨 일이 일어나나 |
|---|---|---|
| 1 | **개발요청서가 만들어진다** | BRD 가 닫히면 **AI 가 자동으로** 쓴다. 재료는 이미 다 있다 — 정의서 여럿 · BRD · 화면별 목업 |
| 2 | **보고 코멘트를 쓴다** | 기획자가 통째로 본다. 본문은 안 고친다. **코멘트 칸에** 일정·우선순위·주의사항을 쓴다 |
| 3 | **넘기기** | 기획자가 **「개발에 넘기기」**를 누른다. 빌더가 **먼저 「전송중」을 남겨 확정하고** 개발 API 로 **개발요청서 한 장(`DR-` + 전송 키)**을 보낸다. **답에 따라 「전송완료」·「대기」·「전송중」 셋 중 하나로 옮긴다** — ⛔ **「4xx 면 대기」로 뭉치지 마라. 아래 「어느 답이 어느 상태로 가나」가 정본이다** |
| 4 | **닫힌다** | 개발요청서까지 **커밋**하고 기획 레포로 **푸시**한다. 워크트리를 지운다. 개발요청서가 **「전송완료」**로 남는다 — ⛔ **BRD 작업 상태는 「작업 완료」 그대로다.** 나갔느냐는 개발요청서가 진다(→ `brd`) |

## 본문은 다시 만들고, 코멘트는 사람 것이다

개발요청서는 **재생성물**이다.

| | 누가 | 고치는 법 |
|---|---|---|
| **본문** | AI | ⛔ **손으로 고치지 않는다.** 정의서나 목업을 고쳐 **다시 만든다** |
| **코멘트** | 사람 | 직접 쓴다. **재생성해도 지워지지 않는다** |

**갈라 두는 이유**가 있다. 본문을 손으로 고치면 원천(정의서·목업)과 어긋나고,
어느 쪽이 맞는지 아무도 모른다. 반대로 코멘트를 본문에 섞으면 **다시 만들 때 날아간다** —
일정·우선순위·주의사항은 사람만 아는 것이라 다시 쓸 수도 없다.

BRD 단위로 나가면서 그 방식이 없어졌다 — **개발이 받는 것은 이번 업무분이다.**

## 왜 사람이 누르나

앞 문서들은 **「닫으면 자동」**을 계속 골랐다. 여기서는 안 그런다.

지금까지의 자동은 전부 **안쪽 일**이었다 — 기획 레포에 커밋하고 밀어 넣는 것.
잘못돼도 안에서 고치면 된다.

**이것은 바깥으로 나간다.** 개발이 받아 가면 되돌리기 어렵다.

그리고 **「BRD 가 닫혔다」와 「이걸로 넘겨도 된다」는 다른 판단**이다.
앞엣것은 기계가 알지만 뒤엣것은 사람만 안다.

**그래서 코멘트 칸이 칸 2 에 있다.** 사람이 한 번은 봐야 하는 자리라서, 볼 때 쓸 것도 같이 받는다.

## 실패하면

**BRD 상태가 그대로 남는다.** 그리고 **어디까지 갔느냐에 따라 다시 누를 때 하는 일이 달라진다** —
아래 상태 셋 표가 그것을 정한다.

⛔ **「실패하면 다시 누른다」로 뭉치지 마라.** 그렇게 적으면 다음 사람이 **언제나 처음부터 다시 보낸다**로 읽고,
개발이 같은 개발요청서를 두 번 받는다. **다시 누르는 것이 무엇을 하는지는 남아 있는 상태가 정한다.**

⛔ **빌더가 몰래 재시도하지 않는다.** 두 번 갔는지 안 갔는지 아무도 모르게 된다.
⚠️ **이 문장은 정책이지 저절로 지켜지는 것이 아니다.** HTTP 클라이언트와 사내 프록시는 **연결 끊김·502 에
기본으로 다시 쏘는 것들이 있다.** 그것을 **꺼야** 이 문장이 참이 된다 — 끄라고 어디에도 안 적혀 있으면 안 꺼진다.

⚠️ **전송이 실패하면 커밋도 하지 않는다.** 칸 4 가 한 덩어리다 —
안 나갔는데 「전송완료」로 커밋되면 레포가 거짓을 말한다.

### 그런데 「다시 누른다」만으로는 두 번 간다

칸 3 이 끝나고 칸 4 에서 실패하는 자리가 있다. **개발은 이미 받았는데 기획 레포에는 안 들어간 상태**다.
여기서 그냥 다시 누르면 개발이 **같은 개발요청서를 두 번 받는다** — 위의 ⛔ 이 막겠다고 한 바로 그 일이
사람 손을 거쳐 일어난다.

그래서 **눌렀을 때 어디까지 갔는지를 빌더가 기록해 둔다.** 셋뿐이다.

| 남아 있는 것 | 무슨 뜻인가 | 다시 누르면 |
|---|---|---|
| **대기** | 아직 안 갔다. 보내기 전에 막혔거나 **개발이 명확히 거절했다** | 처음부터 — 보내고 커밋·푸시한다 |
| **전송중** | 보냈는데 **답을 못 받았다.** 갔는지 안 갔는지 우리가 모른다 | ⛔ **못 누른다.** 사람이 개발에 확인하고 손으로 갈라 준다 |
| **전송완료** | 개발이 받았다. 커밋·푸시만 못 했다 | **전송을 건너뛰고 커밋·푸시만** 한다 |

⛔ **「대기 → 전송중」은 한 요청만 성공해야 한다.** 이 하나가 없으면 위 표 전체가 헛것이다 —
두 탭이 거의 같은 때에 누르면 **둘 다 「대기」를 읽고 둘 다 보낸다.** 상태를 나중에 적는 것으로는 못 막는다.
**지금 값이 「대기」일 때만 바꾸는 조건부 갱신**으로 하고, **바뀐 줄이 0이면 그 요청은 보내지 않는다.**

⛔ **그 갱신이 「확정된 뒤에」 보낸다.** 갱신과 전송을 한 덩어리로 묶으면, **상대는 받았는데 우리 쪽이
되돌아가** 다시 「대기」가 된다. 그러면 다음 클릭이 또 보낸다 — 막으려던 바로 그 일이다.
**순서가 계약이다: 「전송중」을 확정한다 → 보낸다 → 답에 따라 「전송완료」나 「대기」로 옮긴다.**

### 「전송중」에서 나오는 길 — 사람이 고른다

「전송중」에 그대로 두면 그 BRD 는 **영영 못 나간다.** 그래서 나오는 문을 만든다.

**슈퍼계정이 관리 화면에서 개발에 확인한 결과를 고른다.**

| 고른 것 | 옮겨가는 곳 | 그다음 |
|---|---|---|
| **개발이 받았다더라** | **전송완료** | 다시 누르면 커밋·푸시만 한다 |
| **개발이 못 받았다더라** | **대기** | 다시 누르면 처음부터 보낸다 |

⛔ **기획자에게 이 버튼을 주지 않는다.** 「받았는지」는 개발에 물어봐야 아는 것이고,
모르는 채 「못 받았다」를 고르면 **두 번 간다.** 이 문 하나가 위의 모든 장치를 무르는 자리다.
⛔ **「그냥 초기화」 같은 버튼을 만들지 마라** — 그게 정확히 이 설계를 없애는 문이다.

### 「못 받았다」에는 시계를 걸어 둔다 — 아는 사람에게 줘도 시차는 안 없어진다

⚠️ **위험의 원인은 무지가 아니라 시차다.** 슈퍼계정이 아무리 성실해도 이렇게 된다.

```
T1  관리자가 개발에 묻는다      → 개발: "DR-003 없다"     ← 이때는 참이었다
T2  관리자가 「못 받았다」 고름  → 대기
T3  원 요청이 뒤늦게 착지       → 개발이 DR-003 을 받는다
T4  기획자가 다시 누른다        → 두 번째가 간다
```

T1 의 답은 **말할 때 참이었고 쓸 때 거짓**이 됐다.

**그래서 「전송중」에 들어간 시각으로부터 일정 시간이 지나기 전에는 「못 받았다」를 못 고르게 잠근다.**
(「받았다」는 언제든 고를 수 있다 — 그쪽은 두 번 갈 길이 없다.)

- 잠금 시간의 **기본은 24시간**이고 **설치 설정에서 바꾼다.** 개발 창구가 요청을 큐에 얼마나 물고 있는지
  물어서 알면 그 값으로 낮춘다
- 화면에는 남은 시간을 그대로 보여준다 — 「전송중에 들어간 지 3시간 20분 · 잠금 해제까지 20시간 40분」
- ⚠️ **24시간이 「안전해지는 경계」는 아니다.** 상대 큐의 상한을 모르는 한 위험이 0이 되지는 않는다.
  이 시계가 뜻하는 것은 **「이만큼 기다린 뒤에는 슈퍼계정이 남은 위험을 떠안고 다시 보낼 수 있다」**이다
- ⛔ **시계를 방아쇠로 쓰지 마라.** 「오래된 전송중을 자동으로 대기로 떨군다」는
  **위 반례를 기계가 대신 저지르는 것**이라 사람보다 나쁘다. **자물쇠로만 쓴다.**

⚠️ **답을 못 받은 것과 거절당한 것을 뭉치지 마라.** 시간 상한·연결 끊김은 **상대가 이미 받았을 수 있다** —
그건 「대기」가 아니라 **「전송중」**이다. 이 둘을 뭉치면 다시 누를 때 두 번 간다.

### 어느 답이 어느 상태로 가나 — 전수로 적는다

**기준 하나다: 「상대가 처리 안 했다」가 증명되는 것만 「대기」이고, 모르면 「전송중」이다.**

| 돌아온 것 | 어디로 | 왜 |
|---|---|---|
| **200·201** + 응답에 우리 전송 키가 되울려 옴 | **전송완료** | 받았다는 증거가 있다 |
| **202**, 또는 되울림 없는 2xx | **전송중** | ⚠️ **202 는 「접수했다」이지 「처리했다」가 아니다.** 그리고 사내 프록시·로그인 페이지도 200 을 준다 |
| **400 · 401 · 403 · 404 · 413 · 415 · 422** | **대기** | 요청 자체를 안 받아들였다 |
| **408 · 429** | **전송중** | 「지금 말고 나중에」다. 처리 여부가 안 갈린다 |
| **409** | **전송중** | ⚠️ **함정이다.** 「같은 것 이미 받았다」면 실은 **전송완료**이고, 일반 충돌이면 실패다. **상태코드만 보고 정하지 마라** — 개발에 뜻을 물어 정한 뒤 이 표를 고친다 |
| **5xx 전부** | **전송중** | 응답이 왔다는 것 말고는 시간 상한과 다를 게 없다. 502·504 는 **뒤에 넘겨 놓고 기다리다 포기한 것**이다 |
| **3xx 전부** | **전송중** + 관리자 경보 | ⚠️ 주소가 옮겨졌다는 신호이지 **처리를 안 했다는 증거가 아니다** — 서버가 저장한 뒤에 리다이렉트를 줄 수도 있다. 위 기준(모르면 「전송중」)을 그대로 따른다. 경보는 **주소를 고치라는 뜻**이다 |
| **시간 상한 · 응답 전 끊김** | **전송중** | 상대가 이미 받았을 수 있다 |
| **DNS 실패 · 연결 거부 · TLS 실패** | **대기** | 몸이 나가기도 전이다 |

⛔ **리다이렉트 자동 따라가기를 끈다.** POST 에 302 가 오면 많은 클라이언트가 **GET 으로 바꿔 따라가서
몸을 통째로 버리고** 최종 2xx 를 받는다. 그러면 빌더는 **아무것도 안 보내 놓고 「전송완료」로 확정**하고,
칸 4 가 한 덩어리라 **커밋·푸시까지 해서 레포가 「넘겼다」고 거짓말한다.** 두 번 가는 것보다 나쁘다 — 아무도 모른다.

⚠️ **이 표는 개발 창구의 계약이 와야 굳는다.** `requests-to-dev.md` 가 **2026-08-10 에 그 둘을 물었다** —
**상태코드표**(특히 202 를 쓰나 · 409 를 「이미 받았다」로 쓰나)와 **응답 몸에 전송 키를 되울려 주나**.
**답이 오면 202·409 두 줄이 확정되고, 그때 이 표를 고친다.**

### 무엇을 남기나 — 한 번 치가 아니라 시도마다

**상태 한 줄만 남기면 두 번째 시도가 첫 번째를 지운다.** 첫 시도가 「전송중」인 채로 두 번째가 성공하면
**둘 다 알아야 하는데 담을 자리가 없다.** 그래서 **시도마다 한 줄**을 남긴다.

| 남기는 것 | 왜 |
|---|---|
| **전송 키** | 이 시도를 가리키는 세상에 하나뿐인 값 (아래) |
| 보낸 시각 · 끝난 시각 | 격리 시계가 이걸 본다 |
| 돌아온 것 (상태코드 그대로) · 개발이 준 응답 식별자 | 나중에 갈래 표를 고칠 때 근거가 된다 |
| **보낸 몸의 지문** | ⚠️ 「받았다」가 **어느 판을 받은 것인지** 안 묶이면, 그 사이에 문서가 바뀌었을 때 무엇을 받았는지 모른다 |
| 누가 눌렀나 · 누가 언제 어느 문을 열었나 · 개발의 누가 뭐라 했다더라 | 「두 번 갔는지 아무도 모른다」는 **기록이 없어서** 생기는 상태다 |

⚠️ **이 기록은 기획 레포가 아니라 빌더 DB 에 산다** — 아래 이유 그대로다.

### 보내는 몸에 전송 키를 하나 싣는다 — 번호와 다른 것이다

**사람이 보는 것은 `DR-003` 그대로 두고, 개발에 보낼 때 세상에 하나뿐인 키를 하나 더 실어 보낸다.**
다시 보내면 **같은 키**다. 새 일이면 새 키다.

⚠️ **까닭은 오늘 정한 채번 규칙이다** — 번호는 **프로젝트마다 1번부터**라(`data-model` §4),
개발 쪽에서 보면 **서로 다른 사업의 `DR-001` 이 여럿**이 된다. 그쪽이 번호만 보고 거르면 **남의 것을 중복으로 집는다.**

⛔ **이것은 개발에 대한 요구가 아니라 고지다.** 「같은 전송 키가 두 번 오면 그건 재시도이지 새 요청이 아니다」
한 줄을 알린다. 그쪽이 아무것도 안 해도 우리는 손해가 없고, 우연히 그 키로 거르고 있으면 공짜로 중복이 막힌다.

⛔ **다시 보낼 때 새 번호를 뽑지 마라.** 앞것이 이미 갔으면 개발 손에 **번호만 다른 같은 문서 둘**이 남고,
역류가 우리가 버린 번호로 돌아온다.

⚠️ **이 기록은 기획 레포가 아니라 빌더 DB 에 산다.** 여기서 고치려는 실패가 **레포 푸시 실패**라서,
레포에 적어 두면 같은 실패에 같이 걸려 아무것도 못 막는다.

⛔ **개발에 「같은 것 두 번 오면 걸러 달라」고 요구하지 않는다.** 그건 옆 조직 일이 하나 느는 것이고,
언제 될지 우리가 못 정한다. **위 셋이면 우리 쪽 클릭은 닫힌다.**

### 무엇을 보장하고 무엇을 못 하나 — 갈라서 적는다

⛔ **「두 번 안 간다」를 통째로 보장이라 쓰지 마라.** 우리 벽 안과 밖이 다르다.

**보장이다 (우리 DB 안에서 증명된다)**

> **한 사람이 두 번 누르거나 두 탭이 거의 같은 때에 눌러도 발송은 한 번이다.**
> 「대기」일 때만 바꾸는 조건부 갱신 + 「그 갱신이 확정된 뒤에 보낸다」 둘이 이것을 만든다.

**위험 감소일 뿐이다 (우리 벽 밖이 걸려 있다)**

> **같은 개발요청서가 개발에 두 번 도착하지 않는다.** ← **0 이 아니다.**
> 살아 있는 길 셋 — ① 「전송중」의 문에서 나는 시차(격리 시계가 좁히지만 안 없앤다)
> ② 응답 갈래를 잘못 읽는 것(202·409 가 아직 안 굳었다) ③ 우리가 안 끈 클라이언트·프록시의 자동 재시도.

**실제 수준은 이렇게 부른다: 「기본은 한 번뿐이고, 다시 보내는 것은 사람이 위험을 떠안고 고른다.」**

⚠️ **이 문장을 개발에 보내는 문서에도 같은 세기로 적는다.** 우리가 「빌더가 중복을 막아준다」로 말하면
그쪽이 자기 방어를 안 넣는다 — **못 지킬 약속으로 상대의 방어를 면제해 주는 것**이 된다.

⚠️ **남는 구멍 하나를 정직하게 적는다.** 「전송중」은 자동으로 못 가른다 —
개발 API 에 **「이거 받았나」를 묻는 길이 없기 때문**이다. 사람이 개발에 확인해야 한다.
⛔ **여기서 남는 것을 「사람 손이 든다」로 적지 마라. 남는 것은 「사람이 틀리면 두 번 간다」이다.**
품이 드는 것은 감수하면 되지만 정확성은 감수의 문제가 아니다.

### 역류가 공짜 영수증이다

개발이 나중에 `DR-003` 으로 ④~⑧ 을 밀어 넣으면 **그건 DR-003 을 받았다는 증거**다.
그때 우리 상태가 「전송완료」가 아니면 **우리 기록이 틀렸다는 증거**이기도 하다.

**역류가 들어왔는데 그 개발요청서가 「전송완료」가 아니면 자동으로 「전송완료」로 고치고 관리자에게 알린다.**
이미 있는 수신 창구만 쓴다 — 개발에 요구할 것이 없다. 사고를 미리 못 막을 때 **늦게라도 알아채는 그물**이고,
아직 안 누른 두 번째 발송을 멈춘다.

## 자격

**개발이 빌더에게 키를 준다.**
역류 수신에서 빌더가 개발에게 프로젝트 키를 준 것과 대칭이다. 양쪽이 서로의 창구에 키를 하나씩 쥔다.

---

## 고리가 닫힌다

```
받은 문서 → 요구사항 → 정의서 → BRD → 작업목업
                                  │
                                  ▼
                          개발요청서 DR-003   ← 이 문서
                                  │
                               (개발)
                                  │
                                  ▼
                ④~⑧ 이 돌아온다  →  DR-003 에 붙는다
```

**나갈 때도 개발요청서 번호로 나가고 돌아올 때도 그 번호로 돌아온다.**

역류가 BRD 가 아니라 개발요청서에 붙는 이유: **BRD 는 우리 안쪽 이름**이고 개발은 그것을 알 이유가 없다.
개발이 손에 쥔 것은 `DR-003` 이다. 지금은 BRD 하나당 개발요청서 한 장이라 번호가 같이 움직이지만,
**붙이는 자리를 개발요청서로 못 박아야** 나중에 같은 업무를 두 번 넘길 때 어느 번 것인지 갈라진다.

---

## 넘긴 뒤에 그 업무가 또 바뀌면

2차 회의록이 **이미 넘긴 업무**를 고치자고 할 수 있다.

**그건 새 접수의 일이다.** 새 요구사항이 서고, 새 정의서가 나오고, **새 BRD** 가 선다.
그 BRD 가 목업을 새로 만들고 **새 개발요청서**를 낸다.

⛔ **같은 BRD 에서 2차·3차가 나가지 않는다.** 그렇게 두면 역류 문서가 어느 번 것인지 갈라지지 않는다.

⚠️ **대가가 있다.** 전체 문서를 매번 보내던 종전에는 「갱신분이 같이 간다」가 공짜였다.
지금은 개발이 **DR-003 과 DR-009 를 나란히 놓고** 뒤엣것이 앞엣것을 고치는 것임을 읽어야 한다.
그래서 개발요청서에 **「이 업무의 앞 개발요청서」**를 적어 준다 — 빌더가 이미 아는 것이라 거의 공짜다.

## 정한 것과 그 이유

| 무엇 | 정한 것 | 왜 |
|---|---|---|
| 방향 | **빌더가 개발 API 를 부른다** | 아는 것은 보낼 주소와 형식뿐이다. 운영 소스를 읽지 않으므로 g2c 경계를 안 넘는다 |
| 완료의 단위 | **BRD 하나** | 개발도 업무 단위로 받아 만든다. 회의록 단위면 늦은 업무 하나가 다 끝난 둘을 붙잡는다 |
| 보내는 것 | **개발요청서 한 장** | 개발이 받는 것은 이번 업무분이다. 전체 문서를 매번 보내는 방식은 없어졌다 |
| 실리는 것 | **정의서 · 화면별 목업 · 화면 없는 요건** | 요건 · 그림 · 목업 없는 것, 셋이 다 있어야 업무가 온전하다 |
| 본문 | **AI 재생성. 손으로 안 고친다** | 손으로 고치면 원천과 어긋나고 어느 쪽이 맞는지 모른다 |
| 코멘트 | **사람 칸. 재생성에도 남는다** | 일정·우선순위·주의사항은 사람만 안다. 본문에 섞으면 다시 만들 때 날아간다 |
| 만드는 때 | **BRD 가 닫히면 자동** | 안 누르면 낡는다. 사람이 눌러야 하는 자리는 보내는 것 하나로 충분하다 |
| 보내는 때 | **기획자가 누른다. 자동이 아니다** | 바깥으로 나가면 되돌리기 어렵다. 「닫혔다」와 「넘겨도 된다」는 다른 판단이다 |
| 실패 | **상태를 남기고 커밋은 안 한다. 「대기」일 때만 다시 누른다** | 몰래 재시도하면 두 번 갔는지 모른다. 안 나갔는데 커밋되면 레포가 거짓을 말한다. ⛔ 「전송중」이면 다시 누르는 것 자체가 막힌다 |
| 어디까지 갔나 | **셋으로 기록한다 — 대기 · 전송중 · 전송완료** | 「전송완료」인데 다시 누르면 개발이 같은 것을 두 번 받는다. 사람 손을 거쳤을 뿐 몰래 재시도와 결과가 같다 |
| 상태를 바꾸는 법 | **「대기」일 때만 바꾸는 조건부 갱신. 진 쪽은 안 보낸다** | 나중에 적으면 두 탭이 둘 다 「대기」를 읽고 둘 다 보낸다 |
| 갱신과 전송의 순서 | **「전송중」을 확정한 뒤에 보낸다. 한 덩어리로 묶지 않는다** | 묶으면 상대는 받았는데 우리 쪽이 되돌아가 「대기」가 되고 다음 클릭이 또 보낸다 |
| 「전송중」에서 나오는 문 | **슈퍼계정이 개발에 확인하고 「받았다 / 못 받았다」를 고른다** | 안 만들면 그 BRD 가 영영 못 나간다. 기획자에게 주면 모르는 채 골라 두 번 간다 |
| 답을 못 받았을 때 | **「전송중」이다. 「대기」가 아니다** | 시간 상한·연결 끊김은 상대가 이미 받았을 수 있다. 뭉치면 다시 누를 때 두 번 간다 |
| 그 기록이 사는 곳 | **빌더 DB. 기획 레포가 아니다** | 막으려는 실패가 레포 푸시 실패다. 레포에 두면 같은 실패에 같이 걸린다 |
| 중복 거르기 | **개발에 요구하지 않는다** | 옆 조직 일이 하나 늘고 그것이 언제 될지 우리가 못 정한다. 위 셋이면 우리 안에서 닫힌다 |
| 자격 | **개발이 준 키** | 역류 수신과 대칭이다. 양쪽이 서로의 창구에 키를 하나씩 쥔다 |
| 역류가 붙는 곳 | **개발요청서** | 개발이 쥔 종이가 그것이다. BRD 는 우리 안쪽 이름이다 |
| 또 바뀌면 | **새 BRD 가 새 개발요청서를 낸다** | 같은 BRD 에서 2차·3차가 나가면 역류가 어느 번 것인지 갈라지지 않는다 |
| 앞 개발요청서 | **적어 준다** | 전체를 안 보내니 개발이 앞것과 이어 읽어야 한다. 빌더가 이미 아는 것이라 거의 공짜다 |

---

## 이 줄기가 기대는 전제

1. **개발이 받는 API 를 제공한다.** 주소 · 형식 · 키.
2. 기획 레포에 **개발요청서의 규격**이 있다. AI 가 그 형식으로 쓴다.
3. 빌더가 **BRD 와 그 안 산출물의 연결**을 갖고 있다. 개발요청서를 만드는 재료가 이것이다.

## 여기서 끝난다 — 문 하나만 빼고

넘기면 끝이다. **워크트리가 사라지고 일은 회사 저장소에 있다.**

다음에 그 업무가 다시 보이는 것은 **④~⑧ 이 돌아올 때**이고, 그것은 다른 문서다.

### ⭐ 전송 철회 — 병주 지시 2026-08-25

**「끝이다」에 문 하나가 생겼다.** 다만 **되돌리기가 아니라 「무릅니다」를 알리는 것**이다.

⛔ **취소가 아니다.** 이미 나간 것은 없던 일로 못 만든다 — 개발에게 알림이 갔고 읽음이 남는다.

| 언제 되나 | ⭐ **이슈 라벨이 `intake` 일 때만** |
|---|---|
| 무엇을 하나 | 라벨에서 `intake` 를 빼고 `withdrawn` 을 붙이고 **이슈를 닫는다.** 까닭을 댓글로 남긴다 |
| 상태 | `SENT` → **`WITHDRAWN`**. ⛔ **`NOT_SENT` 로 되돌리지 않는다** — 이슈는 살아 있는데 「대기」면 다시 눌러 **두 번째 이슈가 열린다** |
| 다시 보내기 | ✅ 된다. 무르는 목적이 그것이다 |
| 누가 | **기획자.** 자기가 보낸 것을 무르는 것이고 라벨 검사가 안전장치다 |

⭐ **이 판정에 개발과 합의할 것이 없다.** `intake` 는 우리가 붙인 **「인수 전」** 표시이고,
개발이 집어가면 **그쪽 워크플로가 라벨을 바꾼다.** 그래서 **라벨이 그대로인지 보는 것만으로
「아직 아무도 손 안 댔다」가 판정된다** — 그쪽 시스템이 스스로 답을 준다.

⛔ **이슈를 못 찾으면 철회하지 않는다.** 「없으니 무른 셈 치자」가 가장 나쁜 결말이다 —
실은 열려 있는데 우리만 철회로 알고, 개발이 그것을 집어간다.

⛔ **창구가 철회를 못 했으면 DB 를 안 옮긴다.** 순서가 계약이다.

### ⚠ 딸린 것 둘 — 짓다가 드러난 자리다

**① 닫힌 이슈는 다시 보낼 때 재활용하지 않는다.** 전송 키가 **결정적**이라(`DRK-<요청ID>`)
철회 뒤 다시 보내면 같은 키로 **방금 닫은 그 이슈를 찾는다** — 재활용하면 **새 이슈가 영영 안 열려**
철회의 뜻이 사라진다. ⚠ **「다시 보내면 같은 키」 계약은 그대로 산다** — 열려 있는 동안은 여전히 두 번 안 연다.

**② 끝나지 않은 시도에 시간 상한을 뒀다(10분).** 서버가 죽어 `finished_at` 이 `null` 로 남으면
전송 잠금이 **영원히** 막아 그 개발요청서가 다시는 못 나간다(코드가 「서버가 죽었을 때 보냈는지
안 보냈는지 아무 기록이 없다」로 적어 둔 자리다). ⚠ **두 탭이 거의 같은 때 누르는 것은 몇 초라
그대로 막힌다** — 상한이 푸는 것은 버려진 시도뿐이다.
