# 한 화면이 상태에 따라 달리 보이는 것을 기획자가 만들고 보여 주려면

> **2026-08-27 · 병주 확정(저장 구조) + 캡틴 확정(나머지).** 결정과 못만 남긴다 — 구현은 저장소가 정본이다.
> 결정 근거의 실측(파일:줄)은 이 문서 안에 적었다 — 다른 문서를 가리키지 않는다.
> 구현 계획은 셋 — `plans/2026-08-27-plan-11-screen-scenarios.md` · `plan-12-demo-mode.md` · `plan-13-demo-scenario-links.md`.

## 이 문서가 답하는 질문 하나

**하나의 FRD 화면이 업무 조건에 따라 달리 보이는 것(계좌 미연결 · 잔액 0원 · 잔액 있음)을
기획자가 만들고, 눌러 보며 시연하고, 개발요청서로 전달하려면 Builder 를 어떻게 넓히나.**

세 기능이 이 질문 하나에 답한다. 그래서 설계는 하나고 계획은 셋이다 — 구현 위험이 다르다.

| | 기능 | 무엇이 생기나 | 계획 |
|---|---|---|---|
| ① | **상태 시안** | 화면 하나 아래 HTML 여러 벌 + 이름 + 노출 조건. 탭으로 하나씩 본다 | 계획 11 |
| ② | **데모 모드** | 미리보기에서 버튼을 누르면 연결된 다음 화면으로 넘어간다 | 계획 12 |
| ③ | **연결에 시안 지정** | 「이 버튼을 누르면 저 화면의 **어느 상태**로 가나」를 데모가 안다 | 계획 13 |

## 문제 — 지금 무엇이 틀리나

Builder 는 화면 하나에 HTML 하나만 관리한다. 상태별 화면을 만들려면 기획자는 오늘
**「새 화면으로 복제」**(`FrdScreenDuplicationService`) 를 쓰는데, 이것은 `tmp-*` **새 화면ID 를 발급**하고
IA 배치까지 만든다. 그래서 「계좌 홈 · 잔액 있음」이 개발요청서에 **신규 화면**으로 실려 나간다 —
개발자는 화면 세 장을 만들라는 줄 안다. 이 기능은 편의가 아니라 **잘못 나가는 산출물을 고치는 것**이다.

## 원칙 — 바꾸지 않는 것

- **시안마다 화면ID 를 만들지 않는다.** 화면ID 는 실제 화면 하나의 정체성이다.
- **기관별 `variants` 에 업무 상태를 넣지 않는다.** 그것은 익산·제주 같은 적용 구분이다.
- **솔루션 목업(추출된 as-is)은 읽기 전용이다.** 시안은 FRD 작업에 속한다.
- **추출기와 기획 저장소 규격을 빌더가 넓히지 않는다.** 화면 MD · `variantIndex` · `core/` 배치 · 검사기 전부.
- **시안 하나 = 한 시점의 제품 상태 하나.** 아코디언·탭처럼 사용자가 잠깐 바꾸는 것은 시안이 아니다.
- **시안 HTML 은 기획 검토 자료다.** 퍼블리셔의 최종 코드가 아니다 — 밖으로 나갈 때 그렇게 표시한다.
- **코드 식별자는 영문, 화면 문구와 설명은 한글**(`docs/coding-conventions.md`).

## 결정 1 — 시안은 별도 표에 산다 (병주 확정 · 2026-08-27)

```
adk_builder_frd_screen            ← 화면 하나. html = 대표 시안 (그대로)
└─ adk_builder_frd_screen_scenario ← 추가 시안. 0개면 지금과 같다
     id · frd_screen_id · scenario_name · display_condition · html
     · sort_order · version · created_at · updated_at
```

- **대표 시안은 행이 없다.** `FrdScreen.html` 이 그대로 대표다. 그래서 **기존 FRD 는 마이그레이션 없이**
  「시안 하나짜리 화면」으로 열린다.
- 시안 id 는 `IdSequence.Kind.FRD_SCREEN_SCENARIO` 로 채번하는 **일곱 자리 기본키**다 — `tmp-*` 처럼 화면ID 를 짓지 않는다.
- `scenario_name` 은 화면 안에서 유일하다(`unique (frd_screen_id, scenario_name)`). 사람이 읽는 한글 이름이다.
- `version` 은 직접 문구 수정의 **낙관적 잠금**이다 — 시안은 DB 에만 살아 파일 잠금이 없다.

### 왜 화면 행을 재사용하지 않나 — 버린 안

대화에서는 「`FrdScreen` 행 하나 = 시안 하나 + `scenario_of` 열」을 먼저 권했다. 자식 다섯(이력·대화·메모·마커·IA배치)이
전부 `frd_screen_id` 한 열로 매달려 있어 격리가 공짜라는 계산이었다. 실측이 뒤집었다.

- `adk_builder_frd_screen` 에 **`unique (frd_id, screen_id)`** 가 있다(`V17`). 같은 화면ID 행이 둘이면 이것을 부분 인덱스로 수술해야 한다.
- 화면 행은 **수명주기를 통째로 겪는다** — `resetByFrdId` · 제외/복원 · `recoverDiscoveredNewScreen`(화면ID 를 `tmp-*` 로 바꿈) ·
  AI 초안 · `Map<screenId, FrdScreen>` 을 짜는 코드 8곳. 시안 행이 그 전부를 상속하고, 걸러내는 필터를 빠뜨리면 조용히 깨진다
  (`excluded_at` 필터를 `FrdScreenHistoryMapper` 조인이 이미 빠뜨린 선례가 있다).
- 코덱스 반대: **「격리가 공짜」는 저장에서만 참이고 비용은 조회 경로와 수명주기 전체로 옮겨간다.**

별도 표는 비용이 **유한하다** — 시안별 격리가 필요한 자식 **셋**(이력 · 마커 · 메모)에 `scenario_id`(null 허용) 를 더하고,
그 mapper 에 `scenario_id is null / = #{scenarioId}` 를 넣는다. 빠뜨리면 「대표 화면에 시안 마커가 보인다」로 **눈에 띄게** 깨진다.
대화(AI 편집)와 IA 배치는 화면 공통이라 건드리지 않는다.

## 결정 2 — 시안 HTML 의 정본은 DB 다. 워크트리 파일에 쓰지 않는다 (1차)

지금 화면 HTML 의 정본은 둘이다 — `FrdScreen.html`(DB) 과 워크트리 `core/<시스템>/pages/<화면ID>.html`.
AI 편집(`FrdScreenChatWorker`)과 직접 문구 수정(`FrdScreenDirectEditService`)은 **파일을 읽고 파일에 쓴 뒤** DB·이력에 남긴다.
미리보기(`FrdController.preview`)는 **파일 우선 · DB 폴백**이다.

시안은 같은 화면ID 라 이 파일 한 자리를 나눠 쓸 수 없다. 1차는 이렇게 가른다.

| | 대표 시안 | 추가 시안 |
|---|---|---|
| HTML 정본 | 파일 + DB (지금 그대로) | **DB 만** |
| 미리보기 | 파일 우선 · DB 폴백 (그대로) | DB (`?scenario=<id>`) |
| 직접 문구 수정 | 파일에 쓰고 DB·이력 (그대로) | **DB 만** + `version` 검사 → 이력 |
| AI 화면 대화 | 그대로 | ⛔ **1차 제외** — 버튼을 잠근다 |
| 완료 커밋 · 개발요청서 `to-be.html` | 나간다 (그대로) | **안 나간다** |

⛳ **AI 편집을 2차로 미룬 것이 이 결정의 핵심이다.** AI 편집은 파일이 있어야 도는데, 시안 파일을 어디에 두나(DB 정본 + 실행 때만
`.builder/` 같은 미추적 임시 경로에 펼치기 등)는 **기획 저장소 배치에 손대는지를 병주가 확정해야 한다.** 1차 세 기능 중 어느 것도
이것에 기대지 않는다. → 이슈 #20.

## 결정 3 — 데모는 부모 문서가 미리보기 안을 직접 듣는다

미리보기 iframe 은 `sandbox="allow-same-origin"` 이고 서버가 `Content-Security-Policy: sandbox allow-same-origin` 을 얹는다 —
**안에서 스크립트가 안 돈다.** `allow-scripts` 를 더하는 것은 안쪽이 sandbox 를 스스로 걷어낼 수 있는 조합이라 금지돼 있다
(`SolutionPreviewController`). 그래서 스크립트 주입도 `postMessage` 도 **쓰지 않는다.**

대신 **부모 문서가 `#preview-frame.contentDocument` 에 `click`·`submit` 캡처 리스너를 단다.** 영역 선택과 직접 수정이 이미 이 길로
iframe 안에 들어가 있다(`frd.html`). 히스토리 미리보기가 「같은 iframe 을 읽기 전용 문서로 갈아끼우고 돌아오기」의 선례다.

데모 모드의 계약:

- **작업대의 `#preview-frame` 하나**로 한다. 별도 큰 iframe·모달을 만들지 않는다(리스너·마커·리사이즈가 그 하나에 묶여 있다). 확대는 기존 토글.
- 데모 중에는 **직접 수정 · 마커 · 메모 · 이력 복원 · AI 를 전부 잠근다.** 보이는 화면과 편집 대상(`currentLink()`)이 어긋나는 것을 막는다.
- 누른 요소의 앵커 = `data-element-id` 우선 → 상호작용 요소의 `id`. 선행 `#` 은 벗긴다. 관계 줄(`구분: 이동 / 앵커 / 이동`)에서 다음 화면을 찾아 `frame.src` 만 바꾼다.
- `click.preventDefault` 만으로는 못 막는다 — `submit` 도 캡처로 막고, 연결 안 된 `a[href]` 의 기본 이동도 막고, `meta http-equiv=refresh` 를 걷고,
  미리보기 응답에 `form-action 'none'` 을 더하고, `load` 마다 리스너를 다시 단다. 외부로 튀었으면 마지막 화면으로 되돌린다.
- **연결 없는 요소를 누르면 조용히 두지 않는다** — 그 요소에 잠깐 outline + `role=status` 문구 「이 요소는 연결된 화면이 없습니다」.
  연결된 요소는 진입 때 점선 outline 으로 **누를 수 있는 곳을 미리 보여 준다.**
- 데모 스택으로 「뒤로」를 지원한다. 종료하면 원래 화면·시안으로 돌아온다.

## 결정 3-나 — 화면 안 상호작용(탭·아코디언·모달 얹기)은 클론의 데모 호스트를 부모가 실행한다

결정 3 은 「화면 → 다음 화면」만 다뤘다. 병주가 짚은 걱정 — **웹뷰는 딤·모달·탭이 많은데 스크립트 없이 되나** — 를 실측으로 갈랐다.

**실측(웹뷰 목업 253장 · 2026-08-27)**

- 252장이 싣는 스크립트는 `demo-nav.js` **하나**다. 코어가 아니라 **추출기가 넣어 둔 데모 런타임**이고, 셸·모달·탭·아코디언 호스트 넷(`assets/js/demo-*-host.js`, 533줄)을 얹어 소스의 `UI.modal.show`·`UI.tab.init` 을 재현한다.
- 빌더 미리보기는 CSP 로 스크립트를 막으므로 **이 호스트 넷이 안 돈다** — 그래서 지금도 작업대 미리보기에서 탭은 첫 탭에, 아코디언은 접힌 채 굳어 있다. 데모가 만드는 문제가 아니라 있던 문제가 데모에서 눈에 띄는 것이다.
- 모달 127장(`wv-modal-*`)은 **별도 화면**이다. 화면 안에 숨은 오버레이가 아니다. 모달 연결은 MD 관계 줄(`이동modal` 0건)이 아니라 HTML 속성 **`data-nav-modal`**(87장)에 있다 — ⚠ 빌더 캔버스는 `data-nav-target` 만 읽는다(`FrdCanvasService:287`).
- 호스트 셋은 전역으로 **`document` 만** 쓴다(`document.querySelector`·`documentElement`·`readyState`·`addEventListener`). 그래서 부모가 `document` 를 iframe 문서로 바꿔 넘기면 그대로 돈다.

**스파이크(`docs/superpowers/spikes/2026-08-27-demo-host-binding.html` · 캡처 `.png`)** — `sandbox="allow-same-origin"` iframe(스크립트 차단) + 부모가 `new Function('document','window', src)(frame.contentDocument, frame.contentWindow)` 로 호스트 실행:

| 시험 | 결과 |
|---|---|
| 탭 호스트 — `wv-setting-autobuy-registration` | 초기화 `10`(첫 탭만 보임) → 부모가 둘째 버튼 클릭 → `01`. 실제 표시(`display`)도 따라 바뀜 ✔ |
| 모달 얹기 — `wv-store-main-home` 위에 `wv-modal-alarm` | 부모가 모달 화면 HTML 을 받아 `.ui-modal` 조각을 기본 문서에 꽂고 모달 호스트 실행 → `fixed · z-index 100 · opacity 1 · 375×720`, 기본 화면은 그대로 ✔ |
| 아코디언 호스트 | 에러 없이 붙음(전환은 미검증 — 계획 12 검증 항목) |
| 딤 | ✘ `.ui-modal-dim` 요소가 목업·호스트 어디에도 없다 → 운영 런타임이 만드는 것. **이슈 #24** |

**결정**

- 데모 모드는 화면을 띄운 뒤 **클론의 `demo-tab-host.js`·`demo-accordion-host.js`·`demo-modal-host.js` 를 부모에서 iframe 문서에 묶어 실행한다.** 빌더는 호스트가 무엇을 하는지(클래스 규약) 모른다 — 「데모 런타임 파일을 실행」만 한다. 그래서 추출기가 호스트를 고치면 빌더는 저절로 따라간다. **경계가 지켜지는 유일한 길이다** — 빌더가 직접 탭·모달을 구현하면 `ready open ps-bottom` 같은 g2c 규약을 코드가 쥐게 된다.
- `data-nav-modal` 은 데모 그래프에서 **`이동modal` 엣지**로 읽는다. 데모에서 그 엣지를 누르면 화면을 갈아끼우지 않고 **현재 문서 위에 모달 조각을 얹는다**(스파이크 방식). 모달의 닫기(`.ui-modal` 안의 닫기 버튼 · 「뒤로」)는 조각을 떼는 것이다.
- ⚠ **보안 트레이드오프를 숨기지 않는다** — 클론의 JS 를 빌더 페이지 권한으로 돌린다. 목업 HTML 은 sandbox 로 막아 두면서 호스트 JS 는 부모에서 돌리는 것은 신뢰 경계가 다르다. 허용 목록(그 세 파일만) 을 기본 완화로 두되 **병주 확인이 먼저다 — 이슈 #25. 확인 전에는 계획 12 Task 4 를 시작하지 않는다.**
- 이 세 호스트가 있는 것은 **웹뷰**다. 백오피스 화면은 호스트가 없으면 안 돌리면 된다 — 파일이 없으면 건너뛴다(에러 아님).

## 결정 4 — 「연결 → 도착 시안」은 빌더 DB 가 쥔다. 화면 MD 는 한 글자도 바꾸지 않는다 (1차)

화면 연결은 화면 MD 정의 영역의 관계 줄이 정본이다:

```
- 구분: 이동 / 앵커: btn-link / 이동: acct-home / 라벨: 계좌 연결하기 [/ 조건: 행 선택]
```

「도착 화면의 어느 시안으로 가나」를 여기에 적는 길을 셋 검토하고 **전부 1차에서 버렸다.**

| 안 | 왜 버렸나 |
|---|---|
| `시안: <행id>` 마디 | 완료 커밋이 MD 를 **통째로** 기획 저장소에 보낸다(`FrdWorkspace.commitChanges` → `git add -A`). 빌더 내부 키가 밖에 박힌다 |
| 기존 `조건:` 마디 재사용 | `조건:` 은 이미 **「이동이 일어나는 조건」**이고 개발요청서 `changes.md` 표로 흐른다. 「도착 상태」를 섞으면 뜻이 충돌한다 |
| 새 `도착상태: <업무키>` 마디 | 장기적으로 가장 나은 안이다 — 그러나 **기획 저장소 규격을 빌더가 넓히는 것**이라 병주 확인 + 추출기 사본 규격 대조가 먼저다. → 이슈 #21 |

1차는 **빌더 DB 표 하나**로 간다.

```
adk_builder_frd_demo_link
  frd_screen_id(원본 화면 행) · anchor · target_screen_id · target_scenario_id(null = 대표) · created_at
  unique (frd_screen_id, anchor, target_screen_id)
```

- MD 는 「관계가 있다」를, DB 는 「데모에서 어느 시안을 띄우나」를 안다. 대응표는 **빌더 안 데모 전용**이라 정본이 둘로 갈리는 것이 아니다.
- **어긋나면 대표 시안으로 떨어진다** — MD 복원·캔버스 AI 가 MD 를 통째로 덮어 관계가 사라졌거나, 시안이 지워졌으면 데모는 도착 화면의 대표를 띄운다. 이것을 계약으로 못 박는다.
- 시안을 지우면 `target_scenario_id` 는 `on delete set null` — 대응 줄은 남고 대표로 떨어진다.

⚠ **부수 결함 하나를 계획 13 에서 먼저 고친다** — `FrdCanvasRelationService.appendRelation` 이 관계 줄을 통째로 재조립해 여분 마디(`조건:` 포함)를
지운다. 이 기능과 무관하게 지금도 `조건:` 이 편집 한 번에 사라진다.

## 결정 5 — 개발요청서에는 이름과 조건만 싣는다. 꾸러미 배치는 그대로다 (1차)

개발요청서 꾸러미는 화면마다 `as-is/to-be/changes` 배치 · `specVersion=2` 다. **1차는 이것을 바꾸지 않는다.**

- 개발요청서 스냅샷(`DevelopmentRequestContent.Screen`)에 `scenarios: [{name, displayCondition}]` 를 더한다 — `content_json` 은 빌더 내부다.
- `changes.md` 에 절 하나 **「상태별 화면」**을 더한다 — `changes.md` 는 「목업이 말 못 하는 것」을 담는 자유 md 다.

```
## 상태별 화면

| # | 상태 | 노출 조건 |
|---|---|---|
| 대표 | 계좌 미연결 | 연결된 계좌가 없음 |
| 1 | 연결됨 · 잔액 0원 | 연결된 계좌가 있고 총 잔액이 0원 |
| 2 | 연결됨 · 잔액 있음 | 연결된 계좌가 있고 총 잔액이 0원보다 큼 |

> 상태별 시안 HTML 은 Builder 안 기획 검토용 참고 목업이며 최종 퍼블리싱 코드가 아닙니다. 이 꾸러미의 to-be.html 은 대표 상태입니다.
```

- **시안 HTML 을 꾸러미에 싣는 것은 2차다** — 「화면마다 넷」 배치를 바꾸므로 `specVersion` 을 올려야 하고 병주 확인이 먼저다. → 이슈 #22.
- 대표 시안에도 이름을 붙일 수 있게 한다(`FrdScreen` 에 `primary_scenario_name`·`primary_display_condition` 두 열). 없으면 표에서 「대표」만 적힌다.

## 화면 — 무엇이 어디에 붙나

⚠ **목업이 정본이다**(`docs/mockups/05a-frd-workbench.html` · `05q-frd-canvas.html`). **상태 시안 탭과 데모 버튼은 두 목업 어디에도 없다** —
병주가 목업에 먼저 그리고, 구현은 그 목업을 따른다. 아래는 설계가 제안하는 자리이고 목업이 이기면 목업을 따른다.

- **상태 시안 탭** — 작업대 무대 머리(`wm-stage-head`) 제목 아래 한 줄 `role="tablist"`:
  `[계좌 미연결] [연결됨 · 0원] [연결됨 · 잔액 있음] [+ 상태 시안]`. 좌측 화면 목록(`work-screen-list`)에는 넣지 않는다 — 그 목록은 「화면 = 파일」 단위다.
  현재 시안 이름은 색만이 아니라 글자로도 보인다(`#stage-screen-name` 옆).
- **시안 관리** — 탭의 「⋯」에서 이름 변경 · 노출 조건 변경 · 순서 변경 · 대표로 지정 · 삭제. **대표는 다른 시안을 대표로 지정하기 전에는 지울 수 없다.**
  「대표로 지정」은 `FrdScreen.html` 과 시안의 `html` 을 **맞바꾸는 것**이다(대표는 행이 없으니) — 그래서 대표 파일도 새 HTML 로 다시 쓴다. 이력에 한 줄 남긴다.
- **+ 상태 시안** — 이름 · 노출 조건 · 복제할 시안(기본 = 지금 보는 시안). 화면 전체를 복제한다. 영역만 복제하는 기능은 없다 — 복제 뒤 직접 수정으로 고친다.
- **데모 시작** — 「화면 보기」 그룹(줌 옆)의 토글. 켜면 얇은 바 「데모 중 · 현재: 화면명 / 시안명 · 뒤로 · 끝내기」. 미리보기 옆에 **시안 조작판**(그 화면의 시안 탭 + 노출 조건 문구) —
  흐름과 무관하게 「이 화면은 이런 상태도 있다」를 바로 바꿔 보여 준다.
- **연결에 시안 지정** — 캔버스의 연결 추가/수정 레이어에서 대상 화면을 고른 뒤 **「도착 상태」 선택 하나 더**(기본 = 대표). 이것이 `adk_builder_frd_demo_link` 에 앉는다.

## 완료 조건 (세 계획을 합쳐서)

- 같은 화면ID 아래 시안 둘 이상을 만들 수 있고, 지금 보는 시안을 복제해 만들 수 있다.
- 시안마다 이름과 노출 조건이 저장되고, 한 번에 하나만 미리보기 된다.
- 한 시안의 직접 수정이 다른 시안·대표의 HTML·이력·마커·메모를 바꾸지 않는다.
- 대표는 다른 시안을 대표로 지정하기 전에는 지울 수 없다.
- 기관별 `variants` 동작과 솔루션 목업 원본이 바뀌지 않는다.
- 기존 FRD 가 마이그레이션 없이 대표 시안 하나를 가진 것처럼 열린다.
- 개발요청서 `changes.md` 에서 화면별 상태와 노출 조건이 보이고, 꾸러미 배치·`specVersion` 은 그대로다.
- 데모 모드에서 연결된 요소를 누르면 지정한 도착 시안(없으면 대표)으로 넘어가고, 연결 없는 요소는 그 사실을 알려 준다. 데모 중 편집 도구가 전부 잠긴다.
- 미리보기 문서에서 `submit`·연결 없는 `a[href]`·`meta refresh` 가 실제 이동을 일으키지 않는다.
- 데모에서 웹뷰 화면의 탭이 눌러서 바뀌고, `data-nav-modal` 버튼을 누르면 모달이 현재 화면 위에 얹히고 닫힌다 — 빌더 코드에 g2c 클래스 이름이 없다.
