# 프로젝트가 어떻게 빌더에 생기나 — 등록과 클론

> **이 문서가 답하는 질문 하나: 빈 빌더에 기획 레포가 붙어 기획자가 열 수 있는 상태가 되기까지, 무엇이 일어나나.**
> 기획자 계정과 Claude 토큰은 여기 없다. 산출물을 어떻게 다루는지도 여기 없다.

앞의 여섯 문서가 모두 **「기획 레포가 이미 클론돼 있다」**에서 출발한다.
`push` 는 「빌더 공용 계정이 기획 레포에 쓸 수 있다」를 전제로 깔았고,
`planner-one-flow` 는 칸 1 을 「로그인하면 기획자 신원이 선다」로 시작했다.
**누가 언제 그렇게 만들었는지가 아무 데도 없었다.** 그 자리다.

이 문서는 그중 **프로젝트 쪽**만 세운다. 사람 쪽은 다음 문서다.

---

## 칸 다섯

| | 칸 | 무슨 일이 일어나나 |
|---|---|---|
| 0 | **슈퍼계정** | 빌더를 올릴 때 **설정에 아이디·비밀번호가 적혀 있다.** 빈 빌더가 밖에 열려 있는 순간이 없다. **최초 로그인에서 비밀번호를 바꾼다.** **아래 1~4 는 이 계정만 한다** |
| 1 | **프로젝트 등록** | 넷을 넣는다 — 이름 · 기획 레포 URL · 기본 브랜치 · **그 레포에만 닿는 토큰** |
| 2 | **확인** | `git ls-remote` 한 번. 넷이 다 맞아야 등록이 저장된다. **틀리면 그 자리에서 막힌다** |
| 3 | **받는 중** | 뒤에서 클론이 돈다. 목록에 「받는 중」으로 뜨고 **기획자에게는 아직 안 열린다**. 실패하면 「실패」와 다시 시도 |
| 4 | **준비됨** | 클론이 끝났다. 기획자가 로그인하면 이 프로젝트가 보인다. **여기서 이 문서는 끝난다** |

---

## 프로젝트 하나가 가진 것

```
프로젝트  「경비체계」
   ├─ 기획 레포 URL      https://gitlab.co/we/expense.git
   ├─ 기본 브랜치        main
   ├─ 토큰               이 레포에만 닿는다
   ├─ 서버 클론 하나     ← 워크트리의 뿌리
   └─ 상태               받는 중 · 준비됨 · 실패
```

**계층이 없다.** 프로젝트 1 = 기획 레포 1 = 서버 클론 1.
묶을 것이 없는데 그룹이라는 층을 세우면 「프로젝트 고르기에 뜨는 것이 그룹인가 레포인가」를 또 정해야 한다.

**계정 × 프로젝트 연결표도 없다.** 계정이 있으면 등록된 프로젝트가 전부 보인다.

---

## 확인은 즉시, 클론은 뒤에서

기획 레포에는 목업이 잔뜩 들어 있어 클론이 몇 분 걸릴 수 있다.
그렇다고 등록을 그냥 받아두면 **토큰이 틀린 것을 한참 뒤에야 안다.**

`git ls-remote` 는 파일을 하나도 안 받고 **URL · 토큰 · 기본 브랜치를 1초 안에 다 확인한다.**
그래서 둘을 나눴다.

```
[ 등록 ]
   │
   ├─ ls-remote ──▶ 틀림 →  등록이 저장되지 않는다. 무엇이 틀렸는지 그 자리에서 말한다
   │
   └─ 맞음 → 등록 저장 · 화면은 돌아온다
                └─ (뒤에서) clone ──▶ 준비됨
                                 └──▶ 실패 · 다시 시도
```

오타 난 등록이 저장되지도 않고, 개발자가 진행 막대를 보고 앉아 있지도 않는다.

---

## 클론은 뿌리이지 작업장이 아니다

```
서버 클론 (프로젝트당 하나)          ← 아무도 여기서 일하지 않는다
   └── BRD 열기 → git fetch origin
          └── 워크트리  BRD-003     ← 일은 여기서
          └── 워크트리  BRD-009
```

**BRD 를 열 때마다 fetch 한다.** 개발이 역류로 밀거나 다른 기획자가 밀어
회사 쪽이 앞서가도, 워크트리는 **항상 최신에서 딴다.**
기획자는 fetch 가 있었는지 모른다.

주기 실행으로 안 하는 이유 — **사람이 아무도 없어도 계속 돌고,
정작 「지금 반영해」를 못 밀어붙인다.** 필요한 순간은 BRD 를 여는 그때 하나다.

**fetch 가 실패하면 「실패」로 남고 다시 시도다.** 클론 실패와 같은 처리다 —
그 BRD 하나가 안 열릴 뿐이고, 등록도 클론도 성하다.

---

## 토큰은 프로젝트마다다

`push` 가 **미는 신원을 「빌더 공용 계정 하나」**로 정했다. 그 결정은 그대로 산다 —
계정이 하나인 것과 토큰이 하나인 것은 다른 말이다.

**계정은 공용 하나, 토큰은 레포마다 좁힌 것 N개.**
`push` 가 적어둔 「권한도 기획 레포로 좁힐 수 있다」를 실제로 실현하는 자리다.
하나가 새도 **한 프로젝트만 번진다.**

**이 토큰 하나가 넷에 다 쓰인다** — 등록 때 확인(`ls-remote`) · 클론 · BRD 열 때 fetch ·
`push` 가 말한 내보내기. 토큰을 용도별로 나누지 않는다.

값으로 치르는 것은 하나 — **프로젝트가 늘 때마다 토큰을 받아와야 한다.**
개발자가 프로젝트당 한 번 하는 일이라 감수한다.

**만료되면 슈퍼계정이 들어와 그 칸만 다시 넣는다.** 새로 받아 넣으면 끝이고,
등록 때와 같은 `ls-remote` 로 그 자리에서 확인한다. 이름 · URL · 브랜치는 건드리지 않는다.

다시 시도로 넘기지 않는 이유 — **다시 시도는 네트워크 끊김을 낫게 하지만 만료를 못 낫게 한다.**
넣을 자리가 없으면 몇 번을 눌러도 같은 자리에서 실패하고, **프로젝트가 선 채로 굳는다.**
그 토큰이 fetch 에도 쓰이니 그 프로젝트의 BRD 열기가 사람 전부에게 막힌다.

---

## 정한 것과 그 이유

| 무엇 | 정한 것 | 왜 |
|---|---|---|
| 계층 | **프로젝트 1 = 레포 1. 그룹 없음** | 묶을 것이 없는데 층을 세우면 「프로젝트 고르기에 뜨는 것이 그룹인가 레포인가」를 또 정해야 한다 |
| 토큰의 범위 | **프로젝트마다, 그 레포에만 닿는 것** | 계정은 공용 하나여도 토큰은 좁힌다. 하나가 새도 한 프로젝트만 번진다 |
| 등록 순간 | **확인은 즉시 · 클론은 뒤에서** | `ls-remote` 는 1초다. 오타 난 등록이 저장되지도, 개발자가 진행 막대를 보고 앉아 있지도 않는다 |
| 확인에 실패하면 | **등록이 저장되지 않는다** | 잘못된 등록이 남으면 기획자가 BRD 를 열다 막힌다. 그때는 원인이 안 보인다 |
| 클론에 실패하면 | **「실패」로 남고 다시 시도** | 네트워크는 다시 하면 되는 일이다. 등록까지 되물릴 이유가 없다 |
| fetch 에 실패하면 | **「실패」로 남고 다시 시도** | 클론 실패와 같다. 그 BRD 하나가 안 열릴 뿐이다 |
| 토큰이 만료되면 | **슈퍼계정이 그 칸만 다시 넣는다** | 다시 시도로는 안 낫는다. 넣을 자리가 없으면 프로젝트가 선 채로 굳는다 |
| 클론 갱신 | **BRD 를 열 때마다 fetch** | 주기 실행은 사람이 없어도 돌고 「지금 반영」을 못 밀어붙인다 |
| 클론의 자리 | **워크트리의 뿌리. 여기서 일하지 않는다** | 클론에서 직접 고치면 워크트리로 나눈 뜻이 사라진다 |
| 프로젝트 접근 | **등록된 것 전부** | BRD 목록과 같은 판단 — 안 겪은 문제에 장치를 먼저 세우지 않는다 |
| 슈퍼계정 | **설치 설정에 적어둔다. 최초 로그인에서 바꾼다** | 「첫 접속자가 관리자」는 빈 빌더가 밖에 열려 있는 창을 만든다. 다만 적어둔 값이 계속 살아 있으면 그 파일을 본 사람이 관리자가 된다 |
| 받는 중인 프로젝트 | **기획자에게 안 열린다** | 파일이 아직 반쯤 와 있다. 열리면 빈 BRD 목록이 뜬다 |

---

## 여기 없는 것

안 겪은 일이라 세우지 않았다. 겪으면 그때 이 문서를 고친다.

- 프로젝트 **삭제**, 이름 · URL · 브랜치 **수정** (토큰 다시 넣기는 위에 있다)
- 클론 **통째로 다시 받기**
- 등록 이력 · 누가 등록했나

---

## 이 줄기가 기대는 전제

빌더가 만들지 않는다. **없으면 이 줄기가 서지 않는다.**

1. 기획 레포가 **회사 GitLab** 에 있다.
2. **그 레포에만 닿는 토큰**을 개발자가 받아올 수 있다.
3. 기획 레포에 **③ 솔루션 목업 · 업무 목록 · 메뉴구조도(IA) · 검사기**가 이미 들어 있다.
   (③ 솔루션 목업은 `we-adk-builder-extractor` 산출물 — 사람이 올린다)

   ⛔ **2026-08-09 실측: 넷 중 셋이 아직 없다.** 갓 나온 기획 레포는 화면 0장이고,
   추출기는 IA 를 안 내며, 업무 목록의 자리도 안 정해졌다. 검사기만 실물로 들어 있다
   (→ `docs/extractor-measured-facts.md`). **클론은 되지만 볼 것이 없다.**

   ⚠️ **넷 중 둘이 새로 들어왔다 — 도메인 정보와 IA.**
   그 둘이 없으면 AI 가 정의서를 업무로 묶지 못하고 고칠 화면도 못 찾는다(→ `brd`).
   **클론은 되는데 일은 못 하는 프로젝트**가 서므로, 「준비됨」의 조건에 넣는다.

---

## 여기서 끝난다

프로젝트가 「준비됨」이 되면 끝이다. 서버에 클론이 하나 앉아 있고, 아직 아무 워크트리도 없다.

다른 문서로 가는 것들:

- **기획자 계정과 Claude 토큰** — 사람이 어떻게 빌더에서 AI 를 돌릴 자격을 갖나. 이 문서의 짝이다
- **접수** — 준비된 프로젝트에 받은 문서가 어떻게 요구사항정의서로 들어오나
- **기획자가 화면 하나를 고치는 한 줄기** — 이 문서가 만든 클론에서 워크트리를 딴다
