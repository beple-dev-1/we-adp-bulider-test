# 닫힌 일이 어떻게 기획 레포로 나가나 — 푸시

> ⚠ **2026-08-20 작업 단위 개정.** 아래의 BRD 기준은 폐기됐고 현재 작업 단위는 FRD다.
> 워크트리 생성·재사용·종료 계약은 `docs/frd-worktree-lifecycle-design.md`가 정본이다.

> **이 문서가 답하는 질문 하나: 서버 워크트리에 쌓인 커밋이 회사 GitLab 의 기획 레포로 나가기까지, 무엇이 일어나나.**

앞의 문서들이 모두 **「워크트리는 그대로 둔다 — 내보내고 지우는 것은 다른 문서다」**로 끝났다. 그 자리다.

---

## 한 길이다

앞단이든 BRD 든 같다. **찍으면 기본 브랜치로 바로 푸시하고, 워크트리를 지운다.**

| | 앞단 (요구사항 확정 · 정의서 승인) | BRD 작업 | ④~⑧ 수신 |
|---|---|---|---|
| 나가는 때 | 버튼을 **누른 순간** | **개발에 넘길 때** | 개발이 **밀어 넣은 순간** |
| 워크트리 | **그때 딴다.** 쓰고 바로 지운다 | 작업이 도는 내내 살아 있다. **푸시 직후 지운다** | **그때 딴다.** 쓰고 바로 지운다 |

워크트리가 사는 길이만 다르다 — `intake` 가 **「워크트리는 커밋을 담는 동안만 산다」**로
정했고, 앞단은 담을 커밋이 미는 순간에야 생긴다. **나가는 길은 하나다.**

**레포로 나가는 것이 세 번이 됐다**(→ `intake`). 그래도 이 문서에 새 장치가 없다 —
미는 자리가 둘에서 **다섯**으로 늘었을 뿐이고, 아래 「줄을 세운다」가 그것을 그대로 받는다.
⚠️ **2026-08-10 에 넷에서 다섯이 됐다** — 메뉴 일을 **닫을 때 미는 것**이 더해졌다(→ `menu-structure`).

브랜치를 따로 따지 않는다. **MR 을 열지 않는다.**

---

## MR 을 안 만드는 이유

MR 은 **검토받기 위한 자리**다. 그런데 **기획 레포의 MR 을 승인하는 사람이 없다.**

열어봤자 아무도 머지하지 않는다. 그러면 둘이 동시에 망가진다.

- 일이 기본 브랜치에 안 들어가서 **다른 기획자의 목록에 안 뜬다** — 이어지는 작업을 못 연다
- **「머지되면 지운다」가 영영 안 돌아** 서버에 워크트리가 계속 쌓인다

없는 절차를 흉내내면 **장치만 늘고 일은 안 나간다.**
승인하는 사람이 생기면 그때 이 문서를 고친다.

---

## 신원 — 공용 계정으로 밀고, 커밋에 사람을 적는다

git 에서 **쓴 사람(author)과 민 사람은 다른 것**이다.
커밋 author 는 GitLab 계정과 아무 상관이 없다 — 이름과 메일만 있으면 된다.

| | 누구 |
|---|---|
| **미는 것** | 빌더 공용 계정 하나 |
| **커밋 author** | 로그인한 기획자 (자동 수신은 빌더 수신) |

**기획자는 GitLab 계정이 없어도 된다.** 토큰을 맡기는 자리도 만들지 않는다.

개인 계정으로 밀지 않는 이유:

1. **기획자는 Git 을 모른다.** GitLab 토큰을 발급받아 오라고 시키는 것은
   「HTML 을 안 보게 한다」는 이 도구의 취지와 정면으로 어긋난다
2. **더 안전하다.** 서버가 개인 토큰 N개를 들고 있으면 서버가 뚫릴 때 N명이 털린다.
   하나면 하나고, 권한도 기획 레포로 좁힐 수 있다
3. **막히지 않는다.** 토큰 만료나 퇴사로 푸시가 멈추는 일이 없다
4. **잃는 것이 없다.** 누가 했는지는 커밋 author 에 그대로 남는다

첫 문서가 **「로그인한 기획자가 그대로 커밋 이름이 된다」**고 정해둔 것이 여기서 값을 한다.

## 추적

```
BRD-003
   └── 작업            = 워크트리 하나
          └── 커밋       메시지에 BRD-003 · author 는 그 기획자
                 └── 기획 레포 기본 브랜치
```

앞 문서가 세운 **BRD 1개 = 작업 1개 = 워크트리 1개**가 기획 레포까지 그대로 간다.

**앞단 커밋에는 무엇을 적나** — 요구사항 확정은 그 **접수**를, 정의서 승인은 그 **접수**를 적는다.
BRD 번호가 아직 없기 때문이다. 요구가 어느 BRD 로 갔는지는 **추적 매트릭스가 잇는다**.

⚠️ **커밋 메시지에 요구사항 번호를 줄줄이 적지 않는다.** BRD 하나가 정의서 열 건을 담으면
메시지가 번호 열 줄이 된다. 되짚는 일은 매트릭스가 하고, 커밋은 **어느 작업이 찍었나**만 말한다.

## 미는 것은 한 번에 하나다

두 기획자가 거의 같은 때에 눌러 동시에 밀 수 있다. **줄을 세운다.**

```
요구사항 확정  ─┐
정의서 승인    ─┤
개발에 넘기기  ─┼─▶ 줄에 넣는다 ─ 일꾼 하나가 집는다 ▶ 최신 받기 ▶ 얹기 ▶ 푸시
④~⑧ 수신     ─┤          └─▶ 「내보내는 중…」 ▶ 앞사람이 끝나면 이어서 돈다
메뉴 일 닫기   ─┘
```

`concurrent-edit` 의 짧은 잠금 자리 그대로다. **다섯 자리를 같은 줄에 세우면 된다.**
새 장치가 아니다 — 종전에는 둘이었고 다섯이 됐을 뿐이다.

⚠️ **「한 번에 하나」를 무엇이 지키나 — 일꾼이 하나다**(2026-08-10 병주 확정 · 계획 2 Task 7).
DB 잠금을 짧게 잡았다 놓는 것으로는 못 지킨다 — **놓은 뒤 git 이 도는 동안 남이 또 집는다.**
그렇다고 git 이 도는 내내 트랜잭션을 쥐면 **커넥션 풀이 마르고, 롤백이 나면 이미 나간 커밋의 기록이 사라진다.**
**서버가 한 대라는 전제**에서 일꾼 하나가 가장 싸고 정확하다. 그 전제가 깨지는 날 무엇을 고치는지는 계획 2 에 적어 뒀다.

**그래서 「밀다 거절당하면 몇 번까지 다시 미나」를 정할 일이 없다.** 밀 때 앞에 아무도 없다.
겹치는 것이 없으면 기획자는 줄을 섰는지도 모른다 — 「내보내는 중…」이 조금 길어질 뿐이다.

## 부딪히면 — 나중 사람이 다시 한다

줄을 세워도 **내용이 겹치는 것**은 못 막는다. 앞사람이 이미 민 파일을 나중 사람도 고쳤으면
얹을 수가 없다. `concurrent-edit` 이 **「먼저 닫은 쪽이 남고 나중 쪽이 다시 한다」**까지 정했다.
**여기가 그 「다시 한다」의 속이다.**

⚠️ **하나라도 부딪히면 통째로 다시 한다.** 작업이 파일 셋을 건드렸는데 하나만 부딪혀도 그렇다.
부딪힌 것만 남겨 봐야 **기획자가 풀 수 없는 화면**이 된다. 여기서 git 을 보이면 그 사람은 멈춘다.

### 먼저 — 무엇이 부딪힐 수 있나

**길이 둘이고 걸리는 범위가 서로 다르다. 뭉치지 마라.**

**① 빌더 안에서 둘이 같은 파일을 건드린다 — 여기 걸리는 것은 둘뿐이다.**
**요구사항·정의서**(상세의 「내용 수정」과 접수가 같은 파일을 잡는다) ·
**메뉴구조도**(시스템마다 한 장이다 — 2026-08-10 정정. **부딪히는 것은 같은 시스템 안에서다**).

**② 기획팀 사람이 GitLab 에서 직접 고친다 — ⚠ 여기는 파일 종류를 안 가린다.**
우리 줄 밖이라 **목업이든 개발요청서든 걸린다.** 드물지만 실재한다.

⛔ **「부딪힐 수 있는 것은 둘뿐이다」라고 전칭으로 쓰지 마라.** 그건 ①에 대해서만 참이다.
전칭으로 적어 두면 다음 사람이 **「목업은 부딪힐 리 없다」를 믿고 그 경로의 복구를 안 만든다.**

부딪히지 않는 것 셋을 세어 둔다(→ `concurrent-edit`) —

- **작업 목업**: 화면이 막히고 파일 경로에 BRD 번호가 들어간다
- **넘겨받은 BRD**: **같은 워크트리를 넘긴다.** 사본이 둘로 갈리지 않는다
- **개발요청서**: BRD 하나당 한 장이고 그 BRD 를 쥔 사람만 만든다

⚠️ **이걸 세어 적는 이유**: 부딪힌다고 적어 두면 **아무도 걸리지 않는 복구 절차**가 서고,
다음 사람이 그것을 보호로 믿는다. 아래 절 둘이 그 둘에 하나씩 대응한다.

### 메뉴구조도 — 지시를 들고 다시 한다

구조도는 손으로 그린 것이 아니라 **지시를 여러 번 보내 만든 것**이다.
그러니 되살릴 것은 파일이 아니라 **지시**다.

```
김철수의 작업대 (메뉴구조도)
┌────────────────────────────────────────────────────┐
│ ⚠ 구조도를 이영희가 먼저 저장했다 (8/7 16:20)       │
│   당신이 고친 것은 그 위에 다시 해야 한다.           │
│                                                    │
│   이 작업에서 당신이 보낸 지시                       │
│    1  인사관리 아래에 근태를 넣어라        [ 보내기 ] │
│    2  휴가신청을 그 아래로 옮겨라          [ 보내기 ] │
│                                                    │
│        [ 이영희 것을 받아 다시 시작한다 ]           │
└────────────────────────────────────────────────────┘
```

**빌더가 자동으로 다시 돌리지 않는다.** 사람이 보고 하나씩 보낸다 —
둘 중 하나는 이영희가 이미 해놨을 수 있고, **그건 사람만 안다.**

⛔ **그래서 지시를 쌓아둬야 한다.** `ai-run` 은 지금 **실패한 지시 한 건만** 살려둔다.
**일이 도는 내내 보낸 지시를 순서대로 보관하는 것**이 여기서 새로 는다. 텍스트라 싸다.

⚠️ **목업 지시도 같이 쌓는다. 이유는 다르다.**
목업은 부딪히지 않으니 **다시 할 일이 없다** — 쌓는 것은 **작업대에 「지난 지시」로 보여주기 위한 것**이다
(→ `planner-one-flow`). **화면마다 따로 쌓는다.** BRD 하나가 화면 셋을 고치므로 뭉쳐 두면 어느 화면 것인지 갈린다.

### 요구사항 · 정의서 — 다시 누르면 끝이다

앞단은 되살릴 것이 없다. **요구사항과 정의서가 DB 에 그대로 있다** —
워크트리는 몇 초 떴다 지워지는 것이라 잃을 것이 거기 없다.

다만 부딪혔다는 것은 **그 사이 누가 같은 것을 고쳤다**는 뜻이라, 그것을 보이고 다시 묻는다.

```
접수 8/6 — 내보내지 못했다
  REQ-007 을 이영희의 8/5 접수가 방금 고쳤다

  [ 겹침을 다시 본다 ]      [ 그대로 다시 찍는다 ]
```

## 막는 대신 무른다 — 「이 저장 취소」

main 으로 바로 나가므로 **잘못 들어갔을 때 기획자가 되돌릴 데가 없다.**
목업의 「되돌리기 한 칸」은 저장하기 전 얘기다.

**브랜치를 따도 이 불안은 안 사라진다** — 승인할 사람이 없어 결국 main 에 들어가야 하니까.
그래서 **막는 장치가 아니라 무르는 장치**를 둔다.

```
이력
  8/9 14:20  ② 정의서 승인 — RD-014 외 2건            [ 이 저장 취소 ]
  8/9 11:05  ① 요구사항 확정 — 8/9 회의록 · REQ-001 외 6건
```

누르면 빌더가 **되돌리는 커밋을 하나 더 얹어 민다.** 이력은 지워지지 않고
「8/9 에 넣었다가 8/9 에 뺐다」가 남는다. **기획자에게 git 을 보이지 않는다.**

- **되돌아가는 것도 밀기 줄에 선다.** 남이 그 위에 이미 뭘 얹었을 수 있다
- **DB 초안은 그대로 둔다.** 레포에서만 뺀다 — 다시 찍을 수 있어야 한다
- ⛔ **넘긴 개발요청서는 취소로 안 지워진다.** 개발이 이미 받아 갔다. 그건 새 BRD 의 일이다

**잦은 커밋 자체는 위험이 아니다.** git 은 덮어쓰지 않고, 커밋이 촘촘할수록 되돌릴 지점이 많다.
몰아 찍는 쪽이 되돌릴 때 통째로 날아간다.

## 정한 것과 그 이유

| 무엇 | 정한 것 | 왜 |
|---|---|---|
| 나가는 길 | **기본 브랜치로 바로. 브랜치도 MR 도 없다** | 승인하는 사람이 없다. 없는 절차를 흉내내면 일이 안 나가고 워크트리만 쌓인다 |
| 되돌리기 | **「이 저장 취소」 — 되돌리는 커밋을 얹는다** | main 직행이라 무를 데가 없다. 브랜치를 따도 승인할 사람이 없어 같은 데로 들어간다 |
| 취소의 범위 | **레포에서만 뺀다. DB 초안은 남는다** | 다시 찍을 수 있어야 한다. 넘긴 개발요청서는 개발이 이미 받아 갔으므로 취소로 안 지워진다 |
| 미는 신원 | **빌더 공용 계정 하나** | 기획자는 Git 을 모른다. 개인 토큰 N개를 서버가 들고 있는 쪽이 오히려 위험하다 |
| 커밋 author | **로그인한 기획자** | 누가 했는지는 여기 남는다. 공용 계정으로 밀어도 추적이 안 끊긴다 |
| 언제 나가나 | **버튼을 누를 때 자동** | 누른다는 것이 「이건 됐다」는 뜻이다. 내보내기 버튼을 또 두면 안 누르고 쌓인다 |
| 미는 자리 | **다섯 — 요구사항 확정 · 정의서 승인 · 개발에 넘기기 · ④~⑧ 수신 · 메뉴 일 닫기** | 레포로 나가는 것이 세 번이 됐다. 장치는 안 는다 — 같은 줄에 세운다. ⚠ 2026-08-10 에 넷에서 다섯이 됐다(메뉴 일. → `menu-structure`) |
| 워크트리 | **푸시 직후 지운다** | 일이 회사 저장소에 들어갔다. 서버에 남겨둘 이유가 없다 |
| 밀기 경합 | **줄을 세운다. 한 번에 하나 — 일꾼이 하나여서 그렇다** | 짧은 잠금이 이미 있다. 같은 줄에 세우면 「몇 번까지 다시 미나」를 안 정해도 된다. ⚠ 짧은 DB 잠금만으로는 안 지켜진다(놓은 뒤 git 이 도는 동안 남이 집는다) |
| 푸시 결과를 모를 때 | **「모름」으로 두고 사람이 본다** | git 도 시간 상한·연결 끊김·서버 재기동을 만난다. ⛔ 자동으로 다시 밀지 않는다 — 같은 커밋이 두 번 얹힌다 |
| 커밋 메시지 | **BRD 번호. 앞단은 접수** | BRD 하나가 정의서 열 건을 담으면 번호를 줄줄이 적게 된다. 되짚는 일은 추적 매트릭스가 한다 |
| 내용이 부딪히면 | **먼저 닫은 쪽이 남는다. 나중 쪽이 다시 한다** | 기획자에게 git 충돌 화면을 보일 수 없다. 「다시 한다」 하나로 끝낸다 |
| 부분 충돌 | **하나라도 부딪히면 통째로** | 부딪힌 것만 남겨 봐야 기획자가 못 푼다 |
| 부딪힐 수 있는 것 | **빌더 안에서 겹치는 것은 둘 — 요구사항·정의서 · 메뉴구조도** | 그 길에서는 목업·넘겨받은 BRD·개발요청서가 부딪힐 길이 없다. 세어 적지 않으면 아무도 걸리지 않는 복구 절차가 선다 |
| GitLab 에서 직접 고치면 | ⚠ **파일 종류를 안 가린다** | 우리 줄 밖이라 목업이든 개발요청서든 거절될 수 있다. **위 줄의 「둘」은 빌더 안에서 겹치는 것에만 해당한다** — 전칭으로 읽지 마라 |
| 구조도가 다시 할 때 드는 것 | **그 작업에서 보낸 지시 전부** | 구조도도 말로 고친 것이다. 파일만 버리면 기억으로 복원해야 한다 |
| 목업 지시도 쌓나 | **쌓는다. 이유가 다르다** | 다시 할 일이 없다 — **작업대에 「지난 지시」로 보여주기 위한 것**이다. 화면마다 따로 쌓는다 |
| 다시 돌리는 사람 | **빌더가 아니라 사람** | 앞사람이 이미 해놓은 것이 섞여 있다. 무엇이 아직 필요한지는 사람만 안다 |
| 앞단이 부딪히면 | **다시 누르면 끝** | 요구사항·정의서가 DB 에 있다. 겹친 것만 보이고 다시 묻는다 |

---

## 이 줄기가 기대는 전제

1. 기획 레포가 **회사 GitLab** 에 있고, 빌더가 클론해 두었다.
2. **빌더 공용 계정**이 기획 레포에 쓸 수 있다.
3. 밀어 넣는 곳은 기획 레포의 **기본 브랜치**다. 프로젝트마다 다르면 설정으로 바꾼다.
