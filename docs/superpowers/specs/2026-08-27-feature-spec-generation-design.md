# 기능명세서를 어떻게 자동으로 최신 공식 산출물로 유지하나

> **이 문서가 답하는 질문 하나: 화면 상세에 들어왔을 때 무엇을 근거로 기능명세서를 만들고, 어떻게 최신 공식 문서만 보여 주나.**
>
> 날짜 2026-08-27 · 사용자 확정: 생성 방식은 사용자에게 드러내지 않고 상세 진입 시 필요한 경우에만 자동으로 만든다.

## 1. 결정

기능명세서는 화면 `md`를 보여 주는 창이 아니다. 화면 `md`·현재 운영 화면 HTML·IA를 입력으로 삼아
Builder가 만드는 **화면별 공식 산출물**이다.

- 화면 하나에 현재 기능명세서 한 장이 있다.
- 사용자가 상세에 들어오면 Builder가 최신 여부를 판정한다.
- 현재 문서가 없거나 입력이 달라졌을 때만 뒤에서 새 문서를 만든다.
- 사용자는 AI·해시·프롬프트·추출 좌표를 보거나 조작하지 않는다.
- 정상 생성된 문서는 DB에 저장하며 같은 입력으로 다시 만들지 않는다.
- 새 문서가 실패해도 앞의 정상본은 지우지 않는다.
- 성공한 개정판은 불변으로 남기고 현재 개정판만 원자적으로 바꾼다.
- 별도의 사람 검토·발행 단계는 두지 않는다. 구조·근거 검증을 모두 통과한 성공판이 곧 현재 공식 문서다.

이 결정은 2026-08-25의 「기능명세서는 화면 md에 흡수한다」 결정을 폐기한다. 화면 `md`는 다시
기능명세서의 **입력 자료**가 되고 산출물 자체가 아니다.

## 2. 제품에서 보이는 것과 보이지 않는 것

### 사용자가 보는 것

- 문서명, 시스템, 화면명, 화면 ID, 문서 개정번호, 작성일
- 화면 개요
- 기능 명세
- 화면 항목 정의
- 업무 규칙
- 권한·오류·예외
- 화면 이동·외부 연계
- 변경 이력
- 인쇄·PDF 저장에 맞는 A4 문서

### 사용자에게 보이지 않는 것

- `AI로 생성`, `재생성` 버튼과 문구
- 화면 `md` 원문
- 추출 위치, HTML 좌표, 앵커
- 입력 지문과 생성기 버전
- 프롬프트와 모델 실행 기록
- 내부 근거 식별자와 실패 이유 코드
- 같은 부모를 둔 화면을 나열하는 `관련 화면` 탭

다른 화면은 실제 기능이 그 화면으로 이동하거나 연계할 때만 기능 행 안에 나타난다. 화면 탐색은 IA와
기능명세서 목록의 책임이고, 상세 상단에서 형제 화면을 나열하지 않는다.

## 3. 문서 규격

### 3.1 문서 머리

문서 머리는 AI가 쓰지 않고 Builder가 확정된 값으로 조립한다.

| 항목 | 값의 정본 |
|---|---|
| 문서명 | `기능명세서` |
| 시스템 | 프로젝트 `manifest.json`과 시스템 표시 이름 |
| 화면명·화면 ID | `SolutionScreen` |
| 메뉴 경로 | 현재 IA |
| 개정번호 | DB의 성공 개정 순번 |
| 작성일 | DB가 기록한 성공 시각 |
| 기준 입력 | 내부 개정판의 입력 지문. 화면에는 표시하지 않는다 |

### 3.2 화면 개요

- 화면 목적
- 적용 업무 범위
- 주요 사용자 또는 권한 주체 — 입력 자료에서 확인된 경우만
- 사전 조건 — 입력 자료에서 확인된 경우만

### 3.3 기능 명세

| 열 | 뜻 |
|---|---|
| 번호 | Builder가 문서 순서대로 `FN-001`부터 부여한다 |
| 기능명 | 사용자가 결과를 예상할 수 있는 `목적어 + 행동` |
| 실행 조건 | 버튼·선택·화면 진입 등 기능이 시작되는 조건 |
| 사전 조건 | 실행 전에 충족해야 하는 값·상태·권한 |
| 처리 내용 | 화면이 수행하는 일을 순서대로 정리한 내용 |
| 처리 결과 | 화면 갱신·저장·다운로드·이동 등 확인 가능한 결과 |
| 예외·제약 | 입력 제한, 결과 없음, 실행 불가, 중복 방지 등 |

기능 번호는 AI가 만들지 않는다. AI가 반환한 배열의 검증된 순서에 Builder가 결정적으로 붙인다.

### 3.4 화면 항목 정의

| 열 | 뜻 |
|---|---|
| 번호 | Builder가 `FD-001`부터 부여한다 |
| 항목명 | 화면에 표시되는 업무 이름 |
| 유형 | 입력, 선택, 날짜, 체크, 버튼, 표시, 표 열 등 표준 유형 |
| 필수 | `필수`, `선택`, `확인되지 않음` |
| 기본값 | 처음 표시되는 값. 확인할 수 없으면 비운다 |
| 입력·표시 규칙 | 허용 값, 길이, 읽기 전용, 마스킹, 날짜 범위 등 |
| 설명 | 업무에서 이 항목이 뜻하는 것 |

원본에서 확인되지 않은 필수 여부·기본값을 관행으로 채우지 않는다.

### 3.5 조건부 절

다음 절은 근거가 한 건 이상일 때만 그린다.

- 업무 규칙
- 권한 규칙
- 오류·안내 메시지
- 화면 이동
- 외부 인터페이스
- 상태 전이

빈 절과 `해당 없음`을 반복해 문서 분량을 부풀리지 않는다.

### 3.6 변경 이력

변경 이력은 AI가 작성하지 않는다. 저장된 성공 개정판의 번호·시각과 직전 구조화 문서의 결정적 차이로
Builder가 만든다. 첫 판은 `최초 작성`, 다음 판부터는 추가·변경·삭제된 기능과 항목의 개수를 표시한다.

## 4. 입력 자료와 Builder 경계

기능명세서 생성기는 다음 자료만 읽는다.

1. `core/<system>/pages/<screenId>.md`
2. 해당 화면의 현재 운영 HTML과 모든 실제 변형 HTML
3. `SolutionScreen`에서 얻은 화면명·메뉴 경로·부모·진입 화면·변형 정보
4. 같은 프로젝트·시스템의 화면 ID와 화면명 색인 — 이동 대상 검증에만 사용

Builder는 운영 소스, `g2c`, Thymeleaf 원본, `dino-*` 구조를 읽지 않는다. 추출기를 실행하지도 않는다.
필요한 자료가 기획 저장소에 없으면 문서를 지어내지 않고 준비 실패로 남긴다.

디자인가이드는 기능 사실의 근거가 아니므로 입력 지문에 넣지 않는다. 기관 스킨도 기능이 아니라 렌더
차이이므로, HTML 변형이 실제로 별도 파일일 때만 입력 자료가 된다.

## 5. 근거 목록

AI에게 원본만 던지고 자유롭게 인용하게 하지 않는다. Builder가 먼저 입력 자료를 읽어 다음과 같은 근거
목록을 만든다.

| 근거 ID 예 | 가리키는 것 |
|---|---|
| `MD:def:bo-card-list-e07` | 화면 md 정의 한 줄 |
| `HTML:screen.html#btnSearch` | HTML의 ID가 있는 요소 |
| `HTML:screen.html@name=cardStatus` | 이름으로 식별되는 입력 묶음 |
| `IA:bo-card-list` | 화면 색인의 한 화면 |

AI 출력의 모든 기능·항목·규칙·메시지·연계에는 한 개 이상의 `evidenceIds`가 있어야 한다. 저장 전
검사기는 그 ID가 이번 입력 스냅샷에 실제로 있는지 확인한다. 근거 목록과 짧은 근거 문장은 개정판에
보존하지만 사용자 문서에는 출력하지 않는다.

## 6. 입력 지문

`sourceFingerprint`는 SHA-256 소문자 64자리다. 다음 값을 순서가 바뀌지 않게 NUL 바이트로 나누어
계산한다.

1. 화면 `md` 전문
2. 파일 이름으로 정렬한 모든 화면 HTML의 `파일 이름 + 전문`
3. 키 순서가 고정된 화면·IA 문맥 JSON
4. ID로 정렬한 근거 목록 JSON

생성기 버전과 출력 스키마 버전은 입력 지문에 섞지 않고 별도 열로 저장한다. 현재성은 아래 셋이 모두
같을 때만 성립한다.

```text
현재 개정판.source_fingerprint == 방금 계산한 sourceFingerprint
현재 개정판.generator_version  == FeatureSpec.CURRENT_GENERATOR_VERSION
현재 개정판.schema_version     == FeatureSpecContent.CURRENT_SCHEMA_VERSION
```

이렇게 해야 원본 변경과 생성 규칙 변경을 구분해 설명하고 시험할 수 있다.

## 7. 상세 진입이 생성 계기다

목록 조회는 문서를 만들지 않는다. 한 프로젝트에 화면이 수백 장일 수 있으므로 목록 진입이 AI 실행
수백 개를 만드는 구조는 금지한다.

`GET /projects/{projectId}/artifacts/functional-specs/{systemCode}/{screenId}`의 순서는 다음과 같다.

1. 프로젝트 안의 정확한 시스템·화면을 찾는다.
2. 현재 입력 스냅샷과 지문을 계산한다.
3. DB의 현재 개정판과 생성 시도를 한 번 읽는다.
4. 현재성이 맞으면 저장된 구조화 문서를 즉시 표시한다.
5. 현재성이 다르면 DB에서 생성 시도를 원자적으로 선점한다.
6. 선점한 요청만 `aiExecutor`에 작업을 넣는다.
7. 화면은 현재 문서 유무에 따라 준비 상태 또는 앞 정상본을 표시한다.

사용자에게 생성 버튼은 없다. 새로고침과 중복 탭도 DB 선점에서 하나의 작업으로 합쳐진다.

### 파생 화면 상태

| 상태 | 화면 |
|---|---|
| `READY` | 현재 입력과 맞는 공식 문서를 표시하고 인쇄를 허용한다 |
| `PREPARING` | 정상본이 아직 없다. `기능명세서를 준비하고 있습니다.`를 표시한다 |
| `REFRESHING` | 앞 정상본은 읽게 하되 `최신 내용을 반영하고 있습니다.`를 표시하고 제출용 인쇄는 잠시 막는다 |
| `FAILED_EMPTY` | 정상본이 없다. `기능명세서를 준비하지 못했습니다. 잠시 후 다시 열어 주세요.`를 표시한다 |
| `FAILED_STALE` | 앞 정상본은 읽게 하되 최신 문서가 아님을 알리고 제출용 인쇄를 막는다 |

화면 문구에는 AI·모델·해시·프롬프트를 쓰지 않는다.

## 8. 비동기 작업과 역전 방지

생성 시도에는 UUID `generationId`와 `requestedFingerprint`가 있다.

- 같은 화면·같은 지문의 진행 중 작업은 둘째 요청을 받지 않는다.
- 진행 중 원본이 바뀌면 새 지문이 앞 작업을 대체할 수 있다. 앞 작업의 저장은 `generationId` 조건에서
  0행이 되어 버려진다.
- 서버가 멈춰 `RUNNING`이 남으면 `aiRunTimeout + 5분`이 지난 뒤 다음 상세 진입이 선점을 회복한다.
- AI 응답이 규격을 어기면 같은 입력으로 한 번만 바로잡아 다시 요청한다.
- 실패 뒤 자동 재시도는 `nextRetryAt` 이후의 상세 진입에서만 한다. 같은 오류의 연속 실패는
  1분 → 5분 → 30분으로 늦춘다.
- 입력 지문이 바뀌면 실패 횟수와 재시도 대기를 초기화한다.

생성 직후 저장하기 전에 입력 스냅샷을 다시 계산한다. 시작 지문과 다르면 결과를 저장하지 않고
`SOURCE_CHANGED`로 끝낸다. 다음 상세 진입이 새 입력으로 다시 만든다.

## 9. DB

### `adk_builder_feature_spec`

화면 하나의 현재 상태다. 기본키는 `(project_id, system_code, screen_id)`다.

| 열 | 책임 |
|---|---|
| `current_revision_id` | 현재 공식 개정판. 첫 성공 전에는 비어 있다 |
| `generation_state` | `RUNNING`, `DONE`, `FAILED` |
| `generation_id` | 현재 또는 가장 최근 생성 시도 UUID |
| `generation_started_at` | 멈춘 작업 회수 기준 |
| `requested_fingerprint` | 현재 시도가 만들기로 한 입력 지문 |
| `requested_generator_version` | 현재 시도가 사용하는 생성 규칙 버전 |
| `requested_schema_version` | 현재 시도가 만드는 구조 규격 버전 |
| `failed_reason` | 내부 실패 코드. 사용자에게 직접 보여 주지 않는다 |
| `failure_count` | 같은 입력의 연속 실패 횟수 |
| `next_retry_at` | 자동 재시도 허용 시각 |
| `updated_at` | 상태가 마지막으로 바뀐 DB 시각 |

`RUNNING`은 실패 이유가 없어야 하고, `FAILED`는 실패 이유가 있어야 한다. 현재 개정판은 생성 중이나
실패 중에도 보존할 수 있다. 중복 선점은 지문 하나가 아니라
`requested_fingerprint + requested_generator_version + requested_schema_version` 조합으로 판정한다.

### `adk_builder_feature_spec_revision`

성공 결과를 불변으로 보존한다.

| 열 | 책임 |
|---|---|
| `revision_id` | 개정판 UUID |
| `project_id`, `system_code`, `screen_id` | 소유 화면 |
| `revision_no` | 화면 안에서 1부터 증가하는 번호 |
| `source_fingerprint` | 이 판을 만든 입력 지문 |
| `generator_version` | 프롬프트·모델 선택·생성 규칙 버전 |
| `schema_version` | 구조화 문서 규격 버전 |
| `renderer_version` | 저장 HTML을 만든 렌더러 버전 |
| `content_json` | 검증된 구조화 기능명세서 정본 |
| `evidence_json` | 내부 근거 목록과 항목별 근거 연결 |
| `html` | Builder 렌더러가 만든 문서 본문 스냅샷 |
| `created_at` | DB가 기록한 성공 시각 |

`(project_id, system_code, screen_id, revision_no)`와
`(project_id, system_code, screen_id, source_fingerprint, generator_version, schema_version)`는 유일하다.

완료 트랜잭션은 현재 행을 잠그고 다음 개정번호를 배정한 뒤 개정판을 넣고, 그 개정판으로
`current_revision_id`를 바꾼다. 둘 가운데 하나만 커밋되는 상태는 없다.

## 10. 구조화 출력

AI는 HTML이나 Markdown을 만들지 않고 JSON 하나만 반환한다. 루트는 다음 책임을 가진다.

```text
FeatureSpecContent
├─ overview
├─ preconditions[]
├─ functions[]
├─ fields[]
├─ businessRules[]
├─ permissionRules[]
├─ messages[]
├─ transitions[]
└─ integrations[]
```

각 배열 항목은 사용자 문구와 `evidenceIds[]`를 가진다. 화면명·ID·시스템·문서번호·개정번호·작성일은
AI 출력에 두지 않는다. Builder가 DB와 화면 색인에서 붙인다.

표준 열거값은 코드가 소유한다.

- 항목 유형: `INPUT`, `SELECT`, `DATE`, `CHECK`, `RADIO`, `BUTTON`, `DISPLAY`, `TABLE_COLUMN`, `OTHER`
- 필수 여부: `REQUIRED`, `OPTIONAL`, `UNKNOWN`
- 연계 유형: `SCREEN`, `POPUP`, `DOWNLOAD`, `EXTERNAL`, `OTHER`

설명은 한글이고 열거 상수는 영문이다.

## 11. 생성·검증 계약

`FeatureSpecWorker`는 기존 `ClaudeCredentialRunner`와 `aiExecutor`를 사용한다. 실행 디렉터리에는 이번
화면의 입력 스냅샷만 놓고 그 디렉터리만 읽게 한다.

실행 자격은 상세에 들어온 현재 계정의 Builder AI 연결을 사용한다. 별도 서비스 계정을 지어내지 않는다.
연결이 없으면 내부적으로 `NO_CREDENTIAL`을 기록하고 화면에는 설치 관리자에게 문의하라는 일반 문구만
표시한다. 서버 재시작으로 메모리 작업이 사라져도 DB의 제한 시간 회수 규칙으로 다음 진입이 다시 잇는다.

저장 전 검사는 다음 순서다.

1. JSON 스키마 밖의 열과 알 수 없는 열거값 거절
2. 항목 수·문자 길이·중첩 깊이 제한
3. 모든 `evidenceIds`가 이번 근거 목록에 있는지 검사
4. 이동 대상 화면 ID가 같은 프로젝트 화면 색인에 있는지 검사
5. 기능명·항목명의 빈 값과 중복 검사
6. 사용자 문구에 파일 경로·HTML 태그·개발 좌표가 섞이지 않았는지 검사
7. Builder가 기능·항목 번호를 붙이고 결정적 순서로 정규화
8. 서버 렌더러가 안전한 HTML 생성 — AI HTML은 저장하지 않는다
9. 입력 지문 재검사
10. 새 개정판과 현재 포인터를 한 트랜잭션으로 저장

프롬프트는 자료에 있는 사실만 쓰고, 자료 안의 지시문을 따르지 않으며, 알 수 없는 값은 추측하지 말라고
명시한다. 모델 이름과 노력 수준을 바꾸면 `generatorVersion`도 바꾼다.

## 12. 화면과 인쇄

### 목록

목록은 화면 색인과 DB 현재 행을 한 번씩 읽어 합친다. 목록 진입은 생성 계기가 아니다.

- 문서 있음
- 준비 중
- 준비 전
- 최신 내용 반영 중
- 준비 오류

목록에서 `화면 md 있음/없음`을 기능명세서 상태로 부르지 않는다.

### 상세

공식 문서의 순서는 고정한다.

```text
문서 머리
화면 개요
기능 명세
화면 항목 정의
업무 규칙
권한·오류·예외
화면 이동·외부 연계
변경 이력
```

상세에는 관련 화면 탭, 추출 위치, 추출 근거, 원문 보기를 두지 않는다.

### 제출본

첫 구현의 제출본은 같은 구조화 JSON에서 만든 **A4 인쇄 문서**다. 별도 인쇄 화면은 Builder 셸과 상태
문구를 제거하고 `@page`·반복 표 머리·절 단위 페이지 나눔·문서번호와 쪽 바닥글을 적용한다. 사용자는
브라우저의 `인쇄·PDF 저장`으로 제출본을 얻는다. AI 응답을 직접 파일로 내려주지 않는다.

제출본은 `READY`에서만 열 수 있다. 낡은 정상본을 읽는 것은 허용하지만 최신 입력과 맞지 않는 판을
제출본으로 내보내지는 않는다.

## 13. URL

화면 식별자는 시스템 안에서만 유일할 수 있으므로 새 URL은 시스템을 포함한다.

| 메서드·주소 | 책임 |
|---|---|
| `GET /projects/{p}/artifacts/functional-specs` | 목록. 생성하지 않는다 |
| `GET /projects/{p}/artifacts/functional-specs/{system}/{screen}` | 상세. 최신 확인과 필요 시 생성 선점 |
| `GET /projects/{p}/artifacts/functional-specs/{system}/{screen}/status` | 준비 상태 폴링 |
| `GET /projects/{p}/artifacts/functional-specs/{system}/{screen}/print` | 현재 개정판의 제출용 인쇄 문서 |

기존 `/{screenId}` 주소는 프로젝트에서 화면 ID가 하나로만 풀릴 때 새 주소로 돌려보낸다. 같은 ID가 둘
이상이면 임의의 시스템을 고르지 않고 목록으로 보낸다.

생성용 POST와 수동 재생성 주소는 만들지 않는다.

## 14. 코드 책임

| 코드 | 책임 |
|---|---|
| `FeatureSpecMaterialService` | md·HTML·IA 스냅샷, 근거 목록, 입력 지문 |
| `FeatureSpecGenerationService` | 상세 진입의 현재성 판정과 DB 선점 |
| `FeatureSpecWorker` | 비동기 AI 실행, 재검증, 완료·실패 기록 |
| `FeatureSpecContentReader` | 엄격한 JSON 읽기와 구조 검증 |
| `FeatureSpecRenderer` | 화면 본문과 A4 인쇄 HTML 생성 |
| `FeatureSpecMapper` | 현재 행·개정판·CAS 완료 저장 |
| `FeatureSpecController` | 목록·상세·상태·인쇄 라우팅 |

현재 `FeatureSpecDocument`의 화면 md 파서와 `FeatureSpecPresentation`은 새 문서의 정본이 아니다. 전환이
끝나면 제거한다. 화면 자료 수집 로직은 사용자 매뉴얼과 입력 계약이 같으므로, 사용자 매뉴얼 구현이
안정된 뒤 `ScreenArtifactMaterialService`로 공통화한다. 진행 중인 사용자 매뉴얼 코드를 이번 구현의
선행 리팩터링 대상으로 삼지 않는다.

## 15. 실패 코드

실패 코드는 내부 운영과 시험에서만 사용한다.

- `MISSING_SCREEN`
- `MISSING_MD`
- `MISSING_HTML`
- `INVALID_CONTEXT`
- `NO_CREDENTIAL`
- `QUEUE_UNAVAILABLE`
- `AI_EXECUTION_FAILED`
- `INVALID_RESPONSE`
- `UNVERIFIED_EVIDENCE`
- `SOURCE_CHANGED`
- `INPUT_OUTPUT_FAILED`
- `UNEXPECTED`

오류 화면은 코드가 아니라 `무슨 일 + 다음 행동`만 말한다. 정상본이 있으면 실패가 그 본문을 지우지
않는다.

## 16. 시험 계약

### 입력과 현재성

- 같은 파일을 다른 순서로 읽어도 지문이 같다.
- md, HTML, IA 문맥, 근거 목록 중 하나가 바뀌면 지문이 바뀐다.
- 생성기나 스키마 버전만 바뀌어도 현재성이 풀리지만 원본 변경으로 기록하지 않는다.
- 목록 조회는 생성 작업을 시작하지 않는다.
- 최신 상세 조회는 AI 작업을 시작하지 않는다.

### 동시성과 복구

- 같은 화면을 여러 탭에서 열어도 작업 하나만 시작한다.
- 늦게 끝난 앞 `generationId`가 새 결과를 덮지 못한다.
- 멈춘 `RUNNING`은 제한 시간이 지난 뒤 회수된다.
- 생성 중 원본이 바뀌면 결과를 저장하지 않는다.
- 재생성 실패가 앞 정상본과 개정 이력을 지우지 않는다.

### 문서 품질

- 모든 기능·항목·규칙에 실제 근거 ID가 있다.
- 알 수 없는 화면 이동, 열거값, HTML, 파일 경로를 거절한다.
- 기능·항목 번호와 변경 이력이 결정적이다.
- 빈 조건부 절을 출력하지 않는다.
- 화면과 A4 문서에 AI·해시·추출 위치·원문이 나타나지 않는다.

### 화면

- 첫 진입은 준비 상태를 보이고 완료 뒤 자동으로 공식 문서로 바뀐다.
- 낡은 판은 읽을 수 있지만 제출용 인쇄는 막힌다.
- 375px에서는 기능·항목 표 컨테이너만 가로 이동한다.
- 인쇄 화면은 셸 없이 한 개의 `h1`, 반복 표 머리, 페이지 나눔을 가진다.

## 17. 구현 순서

1. 산출물 정본과 이 설계의 용어를 맞춘다.
2. 현재 행·불변 개정판 DB와 Mapper의 동시성 시험을 만든다.
3. 입력 스냅샷·근거 목록·지문을 만든다.
4. 구조화 출력 레코드·엄격한 Reader·서버 Renderer를 만든다.
5. 상세 진입 선점과 비동기 Worker를 연결한다.
6. 목록·상세·상태 폴링·인쇄 화면을 새 문서 계약으로 바꾼다.
7. 실제 긴 화면으로 데스크톱·375px·A4 인쇄를 검증한다.
8. 화면 md 직접 표시 코드와 화면 전용 CSS를 제거한다.

기능명세서 화면을 먼저 다시 꾸미지 않는다. 1~5가 서야 화면이 공식 산출물의 상태와 내용을 정확히
표현할 수 있다.
