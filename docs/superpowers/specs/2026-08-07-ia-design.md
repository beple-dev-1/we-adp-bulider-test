# 빌더에 화면이 몇이고 기획자가 어떻게 오가나 — 화면 지도

> **2026-08-27 — 요구사항 추적 매트릭스는 산출물에서 삭제됐다(병주).** 아래에 남은 매트릭스 언급은 이력이다.
> 그린존(기능명세서 · 화면설계서 · 단위테스트 · 통합테스트 · 사용자 매뉴얼)은 같은 날 열렸다 — 정본은 `CLAUDE.md`.

> **2026-08-20 메뉴 개정.** 현재 산출물은 10종이며 받은 문서·요구사항·요구사항정의서·BRD 화면은
> 제품 흐름과 왼쪽 메뉴에서 제거됐다. 아래에 남은 해당 화면 설명은 이력이다. 현재 산출물 정본은
> `docs/artifacts.md`다.

> **이 문서가 답하는 질문 하나: 빌더에 화면이 몇 개 있고, 사람이 그 사이를 어떻게 오가나.**
> 화면 생김새·색·글꼴은 여기 없다.
> **각 줄기가 왜 그렇게 도는지도 여기 없다** — 그 근거는 줄기 문서들이 갖는다.
> 뒤의 「기획자 여정」은 새 결정이 아니라 **줄기들을 화면 위에 겹쳐 그려 서로 안 어긋나는지 보는 것**이다.

줄기 문서들은 전부 **「무엇이 어떤 순서로 일어나나」**를 적었다.
이 문서는 그것들이 지나가는 **자리**를 한 장으로 세운다.

---

## 왜 줄기만으로는 안 되나

줄기를 그대로 화면으로 옮기면 **「일이 지나가는 자리」만 생기고 「물건이 사는 자리」가 안 생긴다.**

`docs/artifacts.md`의 현재 산출물 10종을 흐름에 대보면, 만들어지는 자리뿐 아니라 보관하고 다시 여는
자리도 필요하다. FRD 작업과 솔루션 목업이 대표적이다.

`artifacts.md`는 머리에서 **「빌더는 인증 + 그룹/프로젝트 등록이 아니다.
현재 산출물 10종의 생애를 관리하는 것이 본체다」**라고 한다.
생애는 만들어지고 · 읽히고 · 고쳐지고 · 나가는 것인데, 줄기 지도는 **만들어진다 하나만** 그린다.

그래서 **메뉴를 줄기로 짜지 않는다. 산출물로 짠다.**

---

## 메뉴는 산출물이다

14종이 **메뉴 열**이 된다. ④~⑧ 다섯은 한 메뉴로 접었다(14 − 5 + 1 = 10).
그 열을 다섯으로 묶었다.

```
┌ 경비체계 ────────────────────────── ● 2 · 이영희 ▾ ┐
│                                                      │
│   받은 문서            줄마다 접수 하나                │
│   요구사항             낱개 · 상태가 붙는다             │
│   요구사항정의서       요구에서 풀린 요건               │
│   ──────────────                                     │
│   BRD                  업무 하나 · 작업이 여기서 열린다  ← 기본 화면 │
│   FRD 작업             자체 채번 · 화면 0장도 있다      │
│   메뉴구조도           시스템마다 하나                │
│   개발요청서           출처 하나당 한 장               │
│   ──────────────                                     │
│   솔루션 목업          as-is · 읽기 전용               │
│   ──────────────                                     │
│   기타 산출물 ④~⑧     개발이 돌려준다                 │
│   ──────────────                                     │
│   추적 매트릭스        전체를 꿰어 본다                 │
└──────────────────────────────────────────────────────┘
```

묶는 기준은 **일의 어느 대목이냐**다.

| 묶음 | 무엇 | 언제 |
|---|---|---|
| 첫째 | 받은 문서 · 요구사항 · 요구사항정의서 | 요구가 들어와 요건이 될 때까지 |
| 둘째 | BRD · FRD 작업 · 메뉴구조도 · 개발요청서 | 요건에서 나오는 것 |
| 셋째 | 솔루션 목업 | 밖에서 이미 와 있는 as-is |
| 넷째 | ④~⑧ 다섯 | 개발이 끝나고 역류해 오는 것 |
| 다섯째 | 추적 매트릭스 | **어느 대목도 아니다. 전부를 세로로 꿴다** |

`artifacts.md` 는 14종을 **누가 만드느냐**로 갈랐고, 그 A절 안에 스스로 경고를 달아놨다 —
**「⚠️ 받은 문서와 ④~⑧ 은 성격이 다르다. 받은 문서는 일이 시작될 때 들어오고
④~⑧ 은 개발이 끝나고 역류한다. 같은 "받는다"로 묶었지만 시점이 반대다」**.

일의 대목으로 가르면 그 둘이 애초에 안 묶인다. 경고를 달 필요가 없어진다.

**추적 매트릭스만 대목이 없다.** 그것이 하는 일이 대목을 가로지르는 것이라서다.
다른 아홉과 같은 줄에 섞으면 「어느 대목의 물건인가」를 읽는 사람이 잘못 짚는다.

## 산출물 메뉴 열은 틀 셋을 나눠 쓴다

14종이 각자 화면을 가지면 열넷을 따로 설계하게 된다. 그러지 않는다.

```
                    로그인
                      │
       ┌──────────────┴──────────────┐
       첫 로그인                      그 밖
       │                              │
  1 비밀번호 바꾸기                   │
       ↓                              │
  2 Claude 연결                       │   ← 기획자와 슈퍼관리자 모두
       └──────────────┬───────────────┘     연결하거나 나중에 연결한다
                      ▼
             프로젝트 고르기
                      ▼
           ┌─── 산출물 목록 ───┐      메뉴 열이 이 틀 하나를 쓴다
           │                    │
           ▼                    │
      산출물 상세                │      무엇을 열든 이 틀 하나
           │                    │
           ▼                    ▼
     ┌──────── 작 업 대 ────────┐
     │  미리보기 자리만 바뀐다    │
     │  목업 · 메뉴 트리          │
     │  요구사항 · 정의서 · BRD 초안│
     └──────────────────────────┘
```

**화면은 아홉이고, 그중 틀 셋을 쓰는 것은 셋뿐이다.**

| | 화면 | 틀 |
|---|---|---|
| 1 | 로그인 | 틀 밖 |
| 2 | 비밀번호 바꾸기 | 틀 밖 |
| 3 | Claude 연결 | 틀 밖 |
| 4 | 프로젝트 고르기 | 틀 밖 |
| 5 | **산출물 목록** | **틀** — 메뉴 열이 이것 하나를 쓴다 |
| 6 | **산출물 상세** | **틀** — 무엇을 열든 이것 하나 |
| 7 | **작업대** | **틀** — 미리보기 자리만 바뀐다 |
| 8 | 프로젝트 관리 | 틀 밖 |
| 9 | 사용자 관리 | 틀 밖 |

**틀 셋은 산출물에만 적용된다.** 로그인 계열 넷과 관리 둘은 산출물을 다루지 않으니 이 규칙 밖이다.

### 아홉에 **등록 화면**이 딸린다 — 메뉴는 안 는다

**입력 항목이 많아 목록 위 작은 레이어에 안 들어가는 것들**이다. 목록에서 넘어가고,
왼쪽 메뉴의 현재 위치는 **부모 목록 그대로**다. 그래서 메뉴가 늘지 않는다.

| 어느 목록에서 | 등록 화면 |
|---|---|
| 프로젝트 관리 | 프로젝트 등록 |
| 사용자 관리 | 사용자 등록 |

**관리 둘은 상세도 갖는다** — 프로젝트 상세(정상 · 실패) · 사용자 상세. 복구 같은 행동을
목록 열에 섞지 않고 상세로 보내기 위해서다 (→ `project-management-menu`).

⛔ **등록은 틀이 아니라 화면이다.** 프로젝트와 사용자 등록은 각각 다른 폼이다.
공통으로 뽑을 것이 「목록에서 넘어간다 · 부모 메뉴가 그대로 켜져 있다」 둘뿐이라 틀로 세울 값이 없다.

**추적 매트릭스는 목록 틀을 쓴다.** 표 한 장이라 상세도 작업대도 없다 —
칸을 누르면 그 산출물의 상세로 건너간다.

**Claude 자격 만료는 흐름도에 없다.** 화면을 옮기는 것이 아니라, **「BRD 열기」·「접수 열기」·
「내용 수정」을 누른 그 자리에서** 연결 화면이 끼어들었다가 원래 하려던 일로 이어지기 때문이다.

화면이 아닌 것 둘 —

- **머리**는 모든 화면에 붙는다: 프로젝트 이름 · 알림 · 사람 이름 · (슈퍼계정에게만) 관리.
  **로그인 전에는 사람 이름이, 프로젝트를 고르기 전에는 프로젝트 이름이 아직 없다** — 그 자리는 비어 있다.
- **창구 둘**: ④~⑧ 역류 수신 API · 개발로 나가는 개발요청서 전송.

## 작업대는 틀 하나다 — 다만 메뉴구조도는 빠졌다

줄기 문서들이 이미 같은 말을 하고 있었다.

- `intake` — 「기계는 다른 문서와 같다 — AI 실행 · 진행 표시와 완료 알림 · 되돌리기 한 칸 ·
  검사기 · 저장. **재료만 다르다**」

그래서 **AI 로 고치는 것들의** 작업대는 여럿이 아니라 하나다. 바뀌는 것은 **미리보기 자리와 버튼** 둘뿐이다.

⛔ **메뉴구조도는 2026-08-12 에 이 틀에서 빠졌다.** 편집 수단이 AI 대화가 아니라 **사람의 표 편집**이라
지시 칸도 되돌리기도 없다. `menu-structure` 의 「줄기는 같다」 중 편집 UI 에 걸리던 대목이 그때 폐기됐다.

⛔ **동그라미 번호는 산출물에만 쓴다.** ①·③·④~⑧ 은 `artifacts.md` 가 정한 산출물 번호다.
순서를 세는 자리(마당 · 걸음 · 칸)에는 보통 숫자를 쓴다.
안 그러면 **한 번호가 산출물 하나와 순서 하나를 같이 가리켜** 읽는 사람이 어느 쪽인지 알 수 없게 된다.

| 미리보기 자리 | 어느 줄기 | 지시로 고치는 것 |
|---|---|---|
| 요구사항 초안 | 접수 · 칸 3 | 요구사항 |
| 정의서 초안 | 접수 · 칸 7 | 요구사항정의서 |
| BRD 초안 | `brd` · 확인 | BRD (화면 판단 · 거친 그림) |
| 목업 | BRD 안 화면 일 | ① FRD 작업 |
| 요구사항 · 정의서 | 상세의 **`[ 내용 수정 ]`** | 그 산출물 하나 |

⛔ **메뉴구조도는 이 표에 없다.** 2026-08-12 결정으로 **사람이 표를 직접 편집**하게 되어
지시로 고치는 자리가 아니다. 아래 「메뉴구조도를 작업대에 두는 근거」가 그것을 적는다.

**개발요청서는 작업대에 안 온다.** 본문을 말로 고치지 않기 때문이다(재생성물).
보고 코멘트를 쓰는 자리는 **상세**다.

### 틀은 하나, 버튼은 재료가 정한다

| 미리보기 자리 | 버튼 | 왜 |
|---|---|---|
| 요구사항 초안 | `[ 확정 ]` | **커밋이다.** 받은 문서와 요구사항 전부가 나간다 |
| 정의서 초안 | `[ 승인 ]` | **커밋이다.** 정의서가 나간다 |
| BRD 초안 | `[ 이대로 시작 ]` | **커밋이 아니다.** 워크트리를 따고 목업을 만든다 |
| 목업 | `[ 목업 저장 ]` `[ BRD 작업 완료 ]` | 저장은 여러 번 찍는다. 끝내는 것이 따로 있다 |
| 메뉴 트리 (표 편집) | `[ 변경 저장 ]` `[ 목록으로 ]` | 구조도는 몇 분만 잡는다. 지시 칸이 없어 되돌리기도 없다 |
| 요구사항 · 정의서 (상세에서 바로) | `[ 변경 내용 저장 ]` | 저장이 곧 커밋이고 그 자리에서 푸시까지 간다 |

⚠️ **종전과 반대가 된 자리가 하나 있다.** 종전에는 접수 작업대의 `[ 승인 ]` 이
**커밋이 아니었다** — 「접수가 도는 내내 레포에 아무것도 안 나간다」가 규칙이었다.
지금은 **확정과 승인이 각각 커밋을 만든다**(→ `intake`).
그래서 이 버튼들은 **누르면 나간다**는 것이 사람에게 보여야 한다.

**BRD 초안의 `[ 이대로 시작 ]` 만 커밋이 아니다.** 거꾸로 이것은 **잠금을 만든다** —
누르는 순간 그 BRD 의 화면들이 남에게 닫힌다. 그 사실도 버튼 옆에 보인다.

### `[ BRD 작업 완료 ]` 는 목업 작업대에만 있다

**작업을 끝내는 문은 하나다** (2026-08-13 결정). BRD 상세가 아니라 **FRD 작업 상세**에 둔다 —
화면을 다 고친 사람이 그 자리에서 끝내는 것이 자연스럽고, 두 자리에 두면 하나를 고칠 때 다른 하나를 빼먹는다.

⚠️ **BRD 단위 행동이라 화면 머리에 붙는다.** 미리보기 헤더의 `[ 목업 저장 ]` 은 **지금 고른 화면 하나**의 일이고,
`[ BRD 작업 완료 ]` 는 **BRD 전체**의 일이다. 같은 줄에 두면 무엇을 끝내는 것인지 안 보인다.

⛔ **미완료 화면이 남아 있으면 누를 때 물어본다.** `handoff-to-dev` 가 「고칠 화면마다 목업이 되어 있어야 한다」를
개발요청서의 전제로 걸어 놨다 — 그 전제를 여기서 지키지 않으면 빈 목업이 개발까지 간다.

```
┌──────────────────────────────────────────────────────────┐
│  BRD-003  전자결재 — 임시저장                             │
│  경비체계          ● 2          이영희 ▾                 │  ← 머리는 여기도 붙는다
├───────────────────────────────┬──────────────────────────┤
│                               │  지시                    │
│      미리보기 자리             │  ┌────────────────────┐  │
│      (여섯 종 중 하나)         │  │                    │  │
│                               │  └────────────────────┘  │
│                               │  ─ 지난 지시 ─           │
│                               │    ↩ 되돌리기 (한 칸)     │
├───────────────────────────────┴──────────────────────────┤
│                             [ 목업 저장 ]  [ BRD 작업 완료 ] │
└──────────────────────────────────────────────────────────┘
        ↑ 버튼은 재료가 정한다 — 위 표대로 바뀐다
```

## 일은 목록의 줄 상태로 산다

**접수와 작업은 메뉴 이름이 아니다.** 물건이 아니라 물건에 걸린 일이기 때문이다.
메뉴로 세우면 같은 물건이 두 군데 살게 된다.

```
받은 문서                          요구사항                                  BRD
 8/5 기획회의록  정의서 검토        REQ-001 임시저장  확정 완료 · 요청 완료     BRD-003 전자결재  ██ 작업중 · 나
 8/6 과업요청서  요구사항 검토       REQ-002 자동추천  확정 완료 · 요청 전       BRD-009 근태       작업 대기
 8/7 2차 회의록  요구사항 추출       REQ-003 권한 정책 생성 완료 · 요청 전       BRD-011 경비       작업 완료
        ↑ 현재 단계                       ↑ 검토 상태 · 정의서 생성 요청          ↑ 작업 상태
```

**접수 1건 = 받은 문서 1건**이다. 그러니 「받은 문서」 메뉴가 곧 접수 목록이다. 목록을 둘 만들지 않는다.

**등록 화면은 목록과 분리하되 메뉴는 늘리지 않는다.** 받은 문서 목록의 `문서 등록`에서 하위 화면으로 이동하고,
문서명과 종류(회의록·과업요청서·제안서·기타)를 입력하고, 첨부파일 또는 직접 입력 중 하나 이상을 제공한다. 첨부파일은 선택이다. 등록 화면에서도 왼쪽 메뉴의 현재 위치는
`받은 문서`다. 상세 화면은 별도 후속 화면이며, 등록 폼을 목록이나 상세 안에 섞지 않는다.

**요구사항 목록에는 정의서 생성 요청 전인 항목도 그대로 남는다.** 목록에서 사라지면
추적 매트릭스의 빈 줄과 어긋난다 — 한쪽에는 있고 한쪽에는 없는 상태가 된다.

### 접수를 닫은 뒤에도 고칠 수 있다 — 상세가 곧 작업대다

요구사항과 정의서는 접수 작업대에서 태어난다. 그런데 **워크트리는 커밋을 담고 바로 지워진다**(`intake`).
그러면 오타 하나를 고칠 자리가 없어진다 — 접수를 다시 여는 길은 만들지 않기로 했다.

**상세에서 바로 고친다** (2026-08-13 결정). 별도 작업대로 나가지 않는다 —
`[ 내용 수정 ]` 을 누르면 그 자리에서 본문이 편집 가능해지고, AI 대화는 **본문 위 오버레이**로 뜬다.

⚠️ **종전에는 「고치기」라는 이름으로 하나짜리 작업대를 열게 되어 있었다.** 그 이름은 폐기됐다.
요구사항·정의서는 **읽는 글 한 덩어리**라 미리보기 자리를 따로 쓸 것이 없고, 상세에 이미 있는
출처 근거·관련 화면 후보·낳은 산출물을 **보면서** 고치는 것이 낫다.

**보이지 않는 쪽은 그대로다.** 화면만 줄었지 규칙은 안 바뀌었다.

| | 상세에서 고치기 | BRD 작업 |
|---|---|---|
| `[ 내용 수정 ]` 을 누르면 | fetch · 워크트리 하나 · **「누가 보고 있나」 표시** | fetch · 워크트리 하나 · 화면 잠금 |
| 저장 | 워크트리에 커밋 · author 는 그 사람 · **푸시 · 워크트리 지우기 · 표시 지우기** | 커밋은 같다. 푸시·워크트리 지우기는 **BRD 작업 완료 때** |

#### 워크트리가 이미 있으면 `[ 내용 수정 ]` 이 안 뜬다

⛔ **이것은 워크트리를 새로 따는 길이다. 이미 있으면 거기서 고친다.**
안 그러면 한 사람이 같은 파일을 두 워크트리로 잡고 **자기 자신과 부딪힌다.**

| 그 산출물이 지금 | 어디서 고치나 |
|---|---|
| **접수가 도는 중** | 접수 작업대에서 「말로」 — `intake` 의 칸 5·9 다 |
| **그 정의서를 담은 BRD 가 열려 있다** | **그 작업대에서 바로.** 워크트리가 이미 거기 있다 |
| **아무것도 안 열려 있다** | **상세의 `[ 내용 수정 ]`** — 그때만 워크트리를 딴다 |

그래서 **BRD 작업대에 「이 정의서 고치기」 자리가 하나 붙는다.**
미리보기는 목업 그대로이고 정의서 본문을 여는 곳만 는다. **작업대를 둘 띄우는 것보다 싸다.**

⛔ **요구가 바뀐 것은 「내용 수정」이 아니다.** 여기서 고치는 것은 **적힌 것이 틀렸을 때**다 —
오타 · 빠뜨린 말 · 잘못 푼 요건. 요구 자체가 달라졌으면 `intake` 가 정한 대로
**새 요구사항이 서고 새 BRD 가 다룬다.** 회의에서 나온 말은 받은 문서로 남아야 하는데,
「내용 수정」으로 밀어 넣으면 **받은 문서 없는 요구**가 생겨 추적이 그 자리에서 끊긴다.

#### 정의서를 고쳤는데 그 BRD 가 닫혀 있으면

**작업이 끝난 BRD 는 「재작업 필요」로 되돌린다.** 옛 요건으로 만든 목업이 그대로 개발에 가는 것을 막는다.
사람에게 안 묻는다 — 「정의서가 바뀌었다」와 「BRD 가 닫혔다」는 기계가 다 아는 사실이다.

⛔ **다만 이미 넘긴 BRD 는 되살리지 않는다.** `handoff-to-dev` 가 「넘기면 끝」으로 정했다.
그 경우는 **새 BRD** 가 다루고 새 개발요청서를 낸다.

### 솔루션 목업은 복사 버튼을 갖지 않는다

복사는 **BRD 가 화면을 열 때 자동으로, 매번** 일어난다 — BRD 가 대상 화면을 판단하므로
어느 것을 복사할지 기계가 안다.

상세에 「이걸로 목업 시작」 버튼을 두지 않는다. 두면 **BRD 없이 목업이 생겨서**
그 목업이 어느 요구에서 나왔는지 아무도 모르게 된다.
대신 상세는 **「이 화면을 다룬 BRD」** 목록을 보여준다. 짝이 없으면 목록이 빈다.

### 목업 상세는 판본을 보여준다

목업은 **BRD 마다 사본**으로 남는다(`brd`). 그래서 같은 화면에 판본이 여러 개 있다.

```
① FRD 작업 — 전자결재 상신
   BRD-011  8/12  이영희   ← 지금 것
   BRD-003  8/5   김철수
   ③ 솔루션 목업 (운영 as-is)
```

**「지금 화면이 이렇다」고 말하지 않는다.** 진짜 현재는 운영 시스템이고, 여기 있는 것은
시점마다의 그림이다. 목록이 그것을 그대로 보여준다.

### 메뉴구조도를 독립 작업대에 두는 근거

**2026-08-12 에 뒤집혔다.** 종전에는 「미리보기 자리에 트리가 뜰 뿐 다른 산출물과 같은 작업대」였는데,
지금은 **사람이 IA 표를 직접 편집한다.** 화면 ID · 사용자 유형 · 메뉴 구분 · 화면 유형 · Depth · Path 를
**한 행에서 대조**해야 해서 목업 작업대의 AI 대화로는 안 된다.

그래서 **작업대 틀을 공유하지 않는다** — 지시 칸도 되돌리기도 없고, 표와 트리 두 판이 나란히 선다.
`menu-structure` 가 「줄기는 같다」고 못 박은 것 중 **살아남는 것은 나머지 셋**(잠금 · 출발점 · 판본 없음)이고,
그 셋은 UI 가 아니라 규칙이라 편집 수단이 바뀌어도 그대로다.

**막는 것은 셋인데 근거가 둘로 갈린다.** `concurrent-edit` 이 「**한 장이라서** 막는 자리는
둘 — 메뉴구조도 · ④~⑧ 수신」으로 정했고, 거기에 **판본이 갈리면 안 되므로 막는 화면 잠금**이 따로 있다.
사람이 여는 것은 메뉴구조도와 BRD 둘이다. 그래서 메뉴구조도 상세는 **「지금 누가 잡고 있나」**를
먼저 보여주고, 잡은 사람이 있으면 여는 버튼이 아예 없다.

**BRD 도 같다** — 품은 화면 중 하나라도 남이 물고 있으면 여는 버튼이 없다.

⚠️ **표시가 두 가지다. 뭉치면 결론이 틀린다.**

| 어떤 표시 | 무엇을 알리나 | 어디에 붙나 |
|---|---|---|
| **동시편집 표시** | 지금 남이 잡고 있다 | **막히지 않고 표시만 뜨는 것은 요구사항·정의서 둘뿐이다.** 목업 · 추적 매트릭스 · 개발요청서에는 안 붙는다(→ `concurrent-edit`) |
| **구조도 표시** | 이 BRD 초안이 본 메뉴구조도가 그새 바뀌었다 | **BRD 상세에 붙는다**(초안일 때). 동시편집과 무관하다 (→ `brd`) |

⛔ **「표시가 뜨는 것은 요구사항·정의서 둘뿐이다」로 뭉쳐 적지 마라.** 그건 **동시편집 표시에 대해서만** 참이고,
BRD 에는 구조도 표시가 따로 붙는다. 뭉쳐 적어 두면 다음 사람이 **BRD 상세에 표시 자리를 안 만든다.**

그래서 **`depth7` 을 더했다**(`V41`) — ⛔ 현재 화면을 생략하거나 마디를 합치거나 자르지 않는다.

**빠지는 것 둘은 까닭을 남긴다** (`Tree.skipped`) — ① 색인에 경로가 없고 조상에서도 못 물려받은 화면
② **공용 화면**(`iaShared`). ⛔ 공용 화면을 한 자리에 못 박지 마라 — 여러 자리에서 열리므로
한 곳을 고르면 「모른다」가 아니라 **틀린 정보**가 된다. 화면은 그것을 따로 목록으로 보여 준다.

#### ⛔ 다시 가져오는 길은 두지 않는다 (2026-08-21 병주 확정)

**IA 는 최초 한 번만 색인에서 잡는다. 그 뒤로는 기획자가 잇는다.**

> 병주: 「IA는 최초 한번만 잡아주는게 맞지 않어? 이후 IA작업은 화면이 새로 생기면 기획자가 연결하는게 맞는게 아닌지?」

**그 길이 이미 있다** — `IaService.workbench()` 는 작업대를 열 때마다 **클론 색인을 새로 읽어**
트리에 안 걸린 화면을 「미연결 화면」으로 낸다. 그래서 저장소 업데이트로 화면이 늘면
**다음에 작업대를 열 때 그 화면이 저절로 그 목록에 뜨고**, 기획자가 메뉴에 연결한다.

⛔ **저장소 업데이트마다 다시 세우지 마라.** 사람이 고친 IA 를 조용히 덮는다 —
DB 를 정본으로 둔 뜻이 사라진다.

⛔ **「다시 가져오기」 버튼을 상주시키지 마라.** 2026-08-21 에 관리자 화면에 한 번 만들었다가
**같은 날 걷었다**(`991ea99` → 되돌림). 확인도 편집 흔적 보호도 없는 버튼이 상주하면
기획자가 며칠 손본 트리를 관리자가 한 번 눌러 날린다.
⚠ **재료가 또 바뀌어 이미 들어온 트리를 갈아 끼워야 하는 날은 코드가 바뀌는 날이다** —
그때 일회성 도구를 내면 된다. 오늘 쓴 것이 `991ea99` 에 있다.

#### 표에는 메뉴 행만 오른다 — 이게 잠금 근거를 살렸다

**행에 오르는 것은 `종류: 화면` 이고 `상위화면` 이 없는 것뿐**이다. 상세·등록·팝업의 소속은
**파생**된다 — 그래서 **메뉴를 옮길 때 고치는 것은 행 하나**고 하위가 따라온다.

⛔ **2026-08-15 에 팝업·모달의 파생이 바뀌었다 — 「사슬」이라고만 읽으면 틀린다.**

| 종류 | 소속이 어디서 오나 |
|---|---|
| 화면형 | `상위화면` 사슬을 따라 처음 만나는 「행에 오른 화면」의 `경로` |
| **팝업·모달** | **그 화면을 같은 시스템에서 `이동`·`이동modal` 로 지목한 화면들의 소속.** ⛔ **`상위화면` 을 적으면 red 다**(IA-1 · 전에는 「없으면 red」였다) |

**팝업·모달의 결과는 셋이다** — 지목한 화면들이 닿는 **자리**가 ① 한 곳이면 그 자리를 받고
② **두 곳 이상이면 공용**(트리에 못 매단다 · `iaShared`) ③ **지목이 0장이면 red**(IA-9).

⚠️ **작업대가 이것에 걸린다** — **공용 팝업은 어느 메뉴에도 안 걸리므로 트리만 그리면 화면에서 사라진다.**
「낡은 IA」보다 나쁜 **「보이지 않는 IA」**가 된다. **트리 밖에 `iaShared` 자리를 따로 둬야 한다.**
그리고 **팝업의 자리를 옮기는 길은 이 작업대에 없다** — 그것은 **여는 화면의 이동 줄**이 정한다.

⭐ **「시스템마다 한 장」이 실물로 참이 됐다.** 전에 걱정한 「표를 저장하는 것이 실제로는
화면 md 수십 장을 고치는 일」이 **아니게 됐다** — 메뉴 일이 여는 파일은 `ia.md` **한 장**이다.
**`menu-structure` 의 통째 잠금과 `concurrent-edit` 의 「한 장이라서 막는다」가 그대로 산다.**

⚠️ **첫 판 정리는 이 작업대로 하지 않는다.** 92행에 순서를 넣고 계층을 운영과 대조하는 일은
「몇 분」이 아니다 — 그동안 아무도 구조도를 못 열고, 저장할 때마다 판번호가 올라
**BRD 초안들에 헛표시가 쏟아진다.** **첫 판은 기획 레포에서 한 번에 잡고**,
이 작업대는 그 뒤의 **몇 분짜리 유지보수**를 맡는다.

#### 빌더가 읽는 것 — `index.json`

```json
"schema": "we-adk-index/3",
"screens": {
  "bo-usag-list":          { "ia": { "경로": "customer/usag", "종류": "화면" } },
  "bo-bizcard-detail-pop": { "ia": { "경로": "bizcard/bizcard", "종류": "팝업",
                                     "여는화면": ["bo-bizcard-detail"] } }
},
"iaIndex":  { "backoffice/customer/usag": ["bo-usag-list"] },
"iaShared": { "backoffice": ["bo-front-lnkgpop"] },
"counts":   { "iaScreens": 256, "iaShared": 2 }
```

⛔ **`{대분류, 업무}` 로 읽지 마라** — 2026-08-14 에 `{경로}` 로 바뀌었다.
파생물이라 **손으로 고치면 A-6 red** 다. 정본은 `ia.md` 다.

⛔ **`/2` 로 읽지 마라 — 2026-08-15 에 `/3` 이 됐고 `ia` 의 칸이 종류에 따라 갈린다.**
**화면형 `{경로, 종류, 상위화면?}` · 팝업·모달 `{경로?, 종류, 여는화면[], 여는곳?}`.**
한 모양으로 파싱하면 팝업에서 깨진다.

| 읽을 때 | |
|---|---|
| ⛔ **`경로` 없음이 두 가지다** | **`iaShared` 등재 여부로 가른다** — 등재됐으면 **공용(정상)**, 안 됐으면 **자리를 못 얻었다(red)**. 뭉치면 **정상인 공용 팝업과 결함을 같은 것으로 그린다** |
| `iaIndex` 는 **파티션** | 한 화면은 최대 한 자리. 「이 메뉴 아래 몇 장」을 셀 때 공용이 부풀지 않는다 |
| 검산 | **`iaScreens = Σ iaIndex + Σ iaShared + (자리 못 얻은 것)`** |

**실측 전문과 규격 인용은 `docs/requests-to-extractor.md` 8번에 있다.**

## 기획자 여정은 딴 문서로 뺐다

줄기들을 **한 사람의 하루로 이어 그려** 이음매가 어긋나지 않는지 보는 것은
이 문서의 질문이 아니다. `planner-journey` 가 그것만 답한다.

여기서 정한 화면 아홉과 틀 셋이 그 여정의 자리를 대는 것이고, **그쪽에서 새로 정하는 것은 없다.**

## 슈퍼계정은 어디까지 보나

**문은 하나다.** 로그인 화면이 하나고, 통과하면 슈퍼계정에게만 머리에 「관리」가 더 보인다.

**슈퍼계정도 산출물을 다 보고 AI 기능을 사용할 수 있다.**
관리 권한과 Claude 자격은 별개이며, 슈퍼계정도 본인 자격을 연결한다.

「다 본다」는 여기서 새로 정한 것이다. 화면을 역할마다 다르게 그리면 목록·상세 두 틀이
각각 두 벌이 되는데, 늘어나는 일에 비해 감추는 값이 없다. 그리고 클론이 「받는 중」인지
「실패」인지를 실제로 쓰는 사람이 개발자다.

⚠️ `dev-feedback` 은 **「기획자용 도구에 개발자가 들어오지 않는다」**고 적었다. 그 말은
**개발팀이 빌더 계정을 만들 필요가 없다**는 뜻이고(그래서 프로젝트 키로 밀게 했다),
빌더를 설치한 개발자 한 사람을 막자는 뜻이 아니다. 그 문장과 부딪히지 않는다.

## 정한 것과 그 이유

| 무엇 | 정한 것 | 왜 |
|---|---|---|
| 메뉴의 뼈대 | **현재 산출물 10종** | 빌더의 본체가 산출물의 생애다. 흐름만 따라가면 다시 여는 자리가 사라진다 |
| 메뉴 개수 | **10종을 모두 표시한다** | 제거된 앞단 네 종은 숨은 메뉴로도 되살리지 않는다 |
| 추적 매트릭스의 자리 | **독립 메뉴로 둔다** | FRD부터 개발 결과까지 가로지르는 계산물이기 때문이다 |
| 화면 틀 | **목록 · 상세 · 작업대** | 산출물의 성격에 맞는 틀을 선택한다 |
| 작업대 | **하나. 미리보기 자리와 버튼만 바뀐다** | 줄기 문서들이 이미 「기계는 같다. 재료만 다르다」고 적어놨다 |
| 개발요청서 | **작업대에 안 온다. 상세에서 본다** | 본문을 말로 고치지 않는 재생성물이다. 코멘트만 사람 칸이다 |
| 작업대 버튼 | **재료가 정한다** | FRD의 `FRD 작업하기`는 워크트리를 만들고, 다른 확정 행동과 결과가 다르다 |
| 확정·승인이 커밋인 것을 보여주나 | **보여준다** | 종전에는 승인이 커밋이 아니었다. 규칙이 반대로 바뀐 자리라 안 알리면 사람이 옛 규칙으로 누른다 |
| 동그라미 번호 | **산출물에만. 순서에는 보통 숫자** | 순서에도 쓰면 한 번호가 산출물과 순서를 같이 가리킨다 |
| 일의 자리 | **메뉴가 아니라 목록의 줄 상태** | 접수와 작업은 물건이 아니라 물건에 걸린 일이다 |
| 접수 목록 | **받은 문서 메뉴가 곧 그것이다** | 접수 1건 = 받은 문서 1건이다 |
| 정의서 생성 요청 전 | **목록에 그대로 남는다** | 사라지면 추적 매트릭스의 빈 줄과 어긋난다 |
| 기본 화면 | **BRD** | 작업이 열리는 자리가 「지금 내 할 일」이다. 메뉴 열이 무게가 같으면 그것이 묻힌다 |
| ④~⑧ 목록 | **개발요청서별로 가른다** | `dev-feedback` 이 그 자리를 비워뒀으므로 IA 가 채운다. 종류별로 가르면 DR-003 에 뭐가 붙었나를 다섯 목록에서 맞춰야 한다 |
| 접수를 닫은 뒤 고치기 | **요구사항·정의서 상세에서 바로** — 별도 작업대를 안 연다 | 워크트리가 지워졌는데 접수를 되살리면 「닫혔다」가 무슨 뜻인지 흐려진다. 읽는 글 한 덩어리라 미리보기 자리를 따로 쓸 것이 없다 |
| `[ 내용 수정 ]` 이 뜨는 때 | **워크트리가 없을 때만** | 있는데 또 따면 한 사람이 같은 파일을 두 워크트리로 잡고 자기 자신과 부딪힌다 |
| 정의서를 고쳤는데 BRD 작업이 끝나 있으면 | **자동으로 「재작업 필요」** | 옛 요건으로 만든 목업이 개발에 간다. 둘 다 기계가 아는 사실이라 묻지 않는다 |
| 이미 넘긴 BRD | **되살리지 않는다. 새 BRD 가 다룬다** | `handoff-to-dev` 가 「넘기면 끝」으로 정했다 |
| 솔루션 목업 복사 | **버튼을 안 둔다. 화면을 열 때 자동** | 버튼을 두면 BRD 없이 목업이 생겨 어느 요구에서 나왔는지 끊긴다. ⛔ **2026-08-24 에 예외 하나가 생겼다** — **이미 열린 작업의 as-is 를 다시 복사하는 것은 사람이 누를 때만** 한다(→ `dev-feedback-design` 의 「부딪히는 자리」 3번). 까닭이 반대다: **첫 복사**는 자동이어야 추적이 안 끊기고, **재복사**는 자동이면 기획자가 며칠 그린 to-be 를 조용히 되돌린다 |
| 목업 상세 | **판본 목록을 보여준다** | BRD 마다 사본이 남는다. 「지금 화면이 이렇다」고 말하면 거짓이다 — 진짜 현재는 운영이다 |
| 메뉴구조도 | **독립 작업대에 둔다. 잠금은 구조도 통째** | 화면 ID·Depth·Path를 사람이 표에서 직접 관리한다. 목업 작업대의 AI 대화와는 편집 수단이 다르다 |
| 여는 버튼이 없어지는 것 | **메뉴구조도 · BRD 둘** | **사람이 여는 것 중** 막히는 것이 그 둘이다. ④~⑧ 수신도 막히지만 그건 사람이 여는 것이 아니다. 나머지는 다 열리고, **동시편집 표시만 뜨는 것은 요구사항·정의서 둘뿐**이다 |
| BRD 의 구조도 표시 | **동시편집 표시와 별개로 둘이 더 붙는다** | 「옛 구조도로 만들어졌다」(만든 판) · 「바뀐 뒤 아직 안 봤다」(확인한 판). 위 줄의 「둘뿐」은 **동시편집 표시**에 대한 말이다 — 뭉쳐 읽으면 BRD 상세에 표시 자리를 안 만들게 된다 (→ `brd`) |
| 메뉴 일을 닫으면 | **밀고 · 워크트리를 지우고 · 잠금을 푼다** | 판번호가 그때 오른다. 판 12 의 내용이 한 사람 기계에만 있으면 남이 그 판을 못 읽는다 (→ `menu-structure`) |
| 알림 | **머리에 하나. 어느 화면에서든** | AI 가 몇 분 도는 동안 사람이 다른 산출물을 볼 수 있어야 한다 |
| 어긋남 표시 | **알림과 별도로 산출물에 남는다** | 알림은 읽으면 사라지고, 흔적은 남아야 한다 |
| Claude 만료 | **열기를 누른 그 자리. 연결 뒤 이어서 열린다** | 돌아와 다시 누르게 하면 하려던 일을 두 번 시킨다 |
| 로그인 문 | **하나. 슈퍼계정에게 「관리」가 더 보인다** | 주소를 둘로 가르면 세션도 둘이 된다 |
| 슈퍼계정 첫 로그인 | **비밀번호를 바꾸고 Claude 연결 또는 나중에 연결을 고른다** | 역할과 관계없이 최초 설정 흐름을 같게 유지한다 |
| 슈퍼계정 | **다 보고 AI 기능도 사용할 수 있다** | 관리 권한과 개인 Claude 자격은 별개다 |
| 「작업바닥」이라는 말 | **버린다** | 여러 문서에서 두 화면을 한 이름으로 불렀다. 산출물 이름을 쓰면 어긋날 자리가 없다 |

「생애」는 넷이다 — 만들어지고 · 읽히고 · 고쳐지고 · 나간다.

| 산출물 | 만든다 | 읽는다 | 고친다 | 나간다 |
|---|---|---|---|---|
| 받은 문서 | 접수 열기 | 받은 문서 메뉴·상세 | — 보존이 정답 | 확정할 때 커밋 ① |
| 요구사항 | 작업대(요구사항 초안) | 요구사항 메뉴·상세 | 상세의 「내용 수정」 | 확정할 때 커밋 ① |
| 요구사항정의서 | 작업대(정의서 초안) | 정의서 메뉴·상세 | 상세의 「내용 수정」 · **폐기**(파일은 남고 표시가 붙는다) | 승인할 때 커밋 ② |
| BRD | 작업대(BRD 초안) | BRD 메뉴·상세 | 작업대에서 말로 | 커밋 ③ |
| ① FRD 작업 | 작업대(목업) | 목업 메뉴·상세 · 판본 목록 | 작업대(목업) | 커밋 ③ |
| 메뉴구조도 | 독립 작업대(표 편집) | 구조도 메뉴·상세 | 독립 작업대(표 편집) | 커밋 ③ |
| 개발요청서 | BRD 닫히면 자동 · 상세의 버튼 | 개발요청서 메뉴·상세 | — 재생성물(코멘트는 사람 칸) | 개발에 넘기기 · 커밋 ③ |
| ③ 솔루션 목업 | — 밖에서 온다 | 목업 메뉴·상세 | **보정 워크트리**(「내용 수정」 관용구 그대로) | 커밋 ③ |
| ④~⑧ 다섯 | — 개발이 만든다 | 기타 산출물 메뉴·상세 | — 개발이 책임진다 | — 여기가 종점이다 |
| 추적 매트릭스 | — 늘 계산된다 | 매트릭스 메뉴 | — 원천을 고친다 | — ⛔ 커밋하지 않는다 |

> ⚠️ **③ 의 「⛔ 고치지 않는다」는 2026-08-14 에 뒤집혔다** (병주 확정 ·
> `specs/2026-08-14-solution-mockup-correction-design.md`). 이름은 **「보정」**이다 — 「수정」이 아니고,
> **to-be 를 as-is 에 미는 것은 여전히 금지**다. 기계는 요구사항·정의서의 **「내용 수정」 관용구 그대로**이고
> (워크트리 하나 → 고친다 → 저장이 곧 커밋 → 푸시 → 워크트리 지우기) **③ 에는 잠금이 없다** —
> BRD 는 ① 사본을 쥐므로 겹칠 사람이 없다.
> ⛔ **보정을 ① 작업대에 두지 않는다** — as-is 보정이 BRD 커밋에 딸려 들어간다.
> ⚠️ **2026-08-16 현재 실제로 도는 것은 「실물과 다름」뿐이다**(계획 7). 보정·캡처는 자리만 있고 잠겼다.

**빈 칸은 「빠뜨렸다」가 아니라 「그게 정답이다」인 것만 남았다.** 받은 문서는 보존이 정답이고,
재생성물은 손으로 안 고치는 것이 정답이고, as-is 와 개발 산출물은 빌더가 만들 물건이 아니다.
