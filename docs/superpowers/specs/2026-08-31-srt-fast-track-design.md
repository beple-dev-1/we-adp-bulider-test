# SRT를 어떻게 단순하게 만들 것인가

## 결론

SRT는 직접 입력하거나 플로우에서 가져온 요청을 개발요청서로 보내는 짧은 경로다.

```text
직접 요청 입력 ─┐
                ├ 요청 내용 정리 → 개발요청서 생성
플로우 업무 등록 ┘
```

사용자는 요청을 직접 입력하거나 플로우 업무번호·주소를 등록한다. 어느 방식으로 시작해도 반드시 개발요청서를 생성하며 FRD 작업으로 전환하지 않는다. AI 분석은 별도 단계로 보여 주지 않고 처리 결과만 남긴다.

## 화면 구성

### SRT 목록

- SRT 번호, 요청 제목, 플로우 업무번호, 처리 결과, 작성자, 연결된 작업을 확인한다.
- 주요 행동은 `SRT 등록` 하나다.
- 기존 개발요청서 목록과 같은 표·필터·페이지 이동 패턴을 사용한다.
- 등록과 상세는 목록 위에 레이어로 연다.

### SRT 등록

- 목록 위에 중앙 레이어로 연다.
- `직접 입력`에서는 제목과 개발 요청을 적고 `등록`을 누른다.
- `플로우 등록`에서는 업무번호 또는 주소를 입력하고 `등록`을 누른다.
- 플로우 등록 시 AI가 본문, 첨부파일, 댓글을 함께 읽는다.
- 사용자가 개발요청서 입력 항목을 다시 작성하거나 처리 경로를 고르지 않는다.
- 등록한 모든 SRT는 개발요청서 생성으로 이어진다.

### SRT 상세

- Builder 공통 `dialog--layer` 스타일의 상세 레이어로 연다.
- 별도의 `처리 결과` 영역을 두지 않는다.
- SRT 번호는 레이어 헤더의 작은 번호로 표시하고, 등록 방식·작성자·등록일시는 제목 아래 설명 한 줄에 표시한다. 본문에는 별도 메타 영역을 두지 않는다.
- 플로우 등록은 제목 아래에 API로 수집한 본문, 첨부파일, 댓글을 모두 보여 준다. 원문을 보기 위해 플로우로 다시 이동시키지 않는다.
- 직접 입력 등록은 같은 자리에 사용자가 입력한 제목과 요청 원문을 보여 준다.
- AI가 정리한 상세 개발 내용은 연결된 개발요청서에서 확인한다.
- 등록 단계에서는 개발팀에 전송하지 않는다.
- 사용자가 상세 화면에서 내용을 확인한 뒤 `개발요청 보내기`를 누른다.
- 전송 전에 개발 완료일, 배포일, 전달사항, 첨부파일을 선택해서 추가할 수 있다.
- 전송 확인은 새 팝업을 띄우지 않고 같은 상세 레이어 안의 다음 단계로 전환한다.

## 최소 상태

| 상태 | 의미 |
|---|---|
| 개발요청서 생성 중 | 등록한 내용을 개발요청서로 정리하는 중이다. |
| 개발요청서 생성 | 개발요청서가 만들어졌다. |
| 처리 오류 | 원문을 가져오거나 분석하지 못해 다시 시도해야 한다. |

## 구현 원칙

- SRT는 FRD, 워크트리, 화면 작업대를 만들지 않는다.
- 직접 입력 내용이나 플로우 원문과 생성된 개발요청서 내용은 나눠 보존한다.
- 브라우저가 아닌 Builder 서버가 플로우 API를 호출한다.
- 같은 플로우 업무로 SRT가 중복 생성되지 않게 한다.
- 개발요청서는 출처가 FRD인지 SRT인지 구분해서 연결한다.
- 메뉴는 `FRD 작업`과 `개발요청서` 사이에 둔다.

## 구현 순서

1. SRT 메뉴와 목록·등록·상세 화면을 만든다.
2. 플로우 원문 가져오기와 오류 처리를 연결한다.
3. AI가 개발요청서 입력값을 채우게 한다.
4. SRT에서 개발요청서를 생성하고 서로 연결한다.
5. SRT 상세에서 개발요청 전송을 연결한다.
6. 중복 생성, 원문 오류, 사용자 수정 보존과 중복 전송을 검증한다.

## 이번 목업 범위

- `_srt-list.html`: 목록, 등록 레이어, 직접 입력·플로우 상세 레이어, 전송 단계를 함께 확인하는 목업
- 공통 메뉴 계약과 실제 서버 동작은 시안 확정 뒤 구현한다.
