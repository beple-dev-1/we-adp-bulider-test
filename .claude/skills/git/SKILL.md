# /git {서브커맨드}

형상관리 작업을 정해진 순서로만 처리한다. 이 스킬의 목적은 **되돌리기 어려운 작업 앞에 절차를 두는 것**이다.

---

## 0단계: 프로파일·VCS 확인

```bash
bash .claude/scripts/check-profile.sh --quiet
```

- 미연동이면 멈추고 사용자에게 알린다.
- `config/stack.yaml` 의 `vcs` 를 읽는다. 아래 표로 이 프로젝트의 성격을 판정한다.
- **커밋할 준비가 됐는지 먼저 본다.** 읽기만 하고 넘어가면 마지막에 죽는다.
  아래는 **`vcs.kind: git` 일 때만** 한다. `svn` 은 자격 증명이 서버·캐시에 달려 있어 여기서 판정하지 않고,
  `none` 은 커밋 자체를 하지 않는다.

  ```bash
  # vcs.kind: git 인 경우에만
  git rev-parse --git-dir >/dev/null 2>&1 || echo "저장소 아님 — git init 이 먼저다"
  [ -n "$(git config user.email)" ] && [ -n "$(git config user.name)" ] \
    && echo "identity OK" || echo "identity 없음"
  ```

  - `git config` 는 **저장소 밖에서도 전역값을 반환한다.** 그래서 `rev-parse` 로 저장소 여부를
    먼저 본다 — 안 보면 `git init` 안 한 폴더에서 통과를 내고 커밋에서 `not a git repository` 로 죽는다.
  - identity 가 없으면 **브랜치를 만들기 전에** 사용자에게 아래를 실행하게 한다.
    스테이징·메시지 승인까지 다 끝낸 뒤 실패하면 그 작업이 전부 헛돈다
    (2026-09-01 실측 — 정확히 그 순서로 막혔다).

  ```bash
  git config user.name  "내 이름"
  git config user.email "내 메일주소"
  ```

  (모든 프로젝트에 적용하려면 `--global` 을 붙인다. 이 저장소만이면 그대로 둔다.)
  `bash .claude/scripts/check-profile.sh --verify-commands` 의 **커밋 작성자 검사**가 같은 것을 본다
  (검사 이름은 `vcs-identity`. 그 검사도 `vcs.kind` 로 분기해 `svn`·`none` 은 SKIP 한다).

| `vcs.kind` | `commitDeploys` | 성격 |
|---|---|---|
| git | false | 브랜치·PR 사용. 커밋과 배포가 분리됨 |
| git | true | 커밋(또는 푸시)이 곧 배포. 되돌리기 비용 큼 |
| svn | true | 브랜치 없음. 커밋 즉시 반영 |
| none | — | 형상관리 없음. 커밋 관련 서브커맨드 사용 불가 |

- `vcs.kind: none` 이면 `status`·`diff` 만 안내하고 커밋 요청은 거절한다.

## 사용법

```
/git {서브커맨드} [{대상}]
```

| 서브커맨드 | 하는 일 |
|---|---|
| `status` | 변경 파일 목록 |
| `diff` | 변경 내용 |
| `log` | 커밋 이력 |
| `add` | 추적 추가 (경로를 명시하고, 스테이징 결과를 확인) |
| `commit` | 커밋 |
| `push` | 원격 반영 (git 전용) |
| `pr` | PR/MR 생성 (git 전용) |

- `add` 는 **경로를 명시**한다. `add .` · `add -A` 는 쓰지 않는다 — 로컬 전용 파일이나 산출물이 섞여 들어간다.
- 파일이 많으면 **디렉터리 단위로 지정해도 된다.** 하나씩 적는 것이 목적이 아니라
  **이 커밋 범위 밖 파일이 안 들어가는 것**이 목적이다 (연동 커밋은 수십~수백 파일이 정상이다).
- **다만 스테이징 뒤에 반드시 결과를 확인한다.** 이것이 규칙의 실체다.

  ```bash
  git diff --cached --name-only        # 무엇이 담겼는지
  git diff --cached --name-only | wc -l
  ```

  담긴 목록을 보고 **다른 과업 파일·산출물·로컬 전용 파일이 없는지** 확인한 뒤 커밋한다.
  확인 없이 커밋하지 않는다.

## 커밋 절차

0. **지금 어느 브랜치인지 먼저 확인한다** — `git branch --show-current`.
   - `vcs.kind: git` **이고** `commitDeploys: false` **이고** 현재 브랜치가 `vcs.defaultBranch` 면
     **커밋 전에 분기한다.** 기본 브랜치에 직접 쌓지 않는다.
   - `commitDeploys: true` 이거나 `vcs.kind: svn` 이면 분기하지 않는다 — 그 환경은 직접 커밋이 정상이다.
   - 이미 피처 브랜치에 있으면 그대로 진행한다.
   - 이 확인을 절차의 **맨 앞**에 두는 이유 — 뒤에 두면 커밋한 뒤에야 알게 되고,
     그때는 되돌리는 비용이 든다. 브랜치 절에 명령만 적어 두는 것으로는 지켜지지 않았다
     (2026-08-31 실측 — 3회차 내내 기본 브랜치에 직접 커밋됐고 아무 게이트도 잡지 않았다).
1. `status` 로 변경 파일을 확인한다.
2. `diff` 로 내용을 확인한다.
3. **`/code-review` 를 실행했는지 확인한다.** 안 했으면 먼저 하도록 안내한다.
4. 신규 파일이 있으면 하나씩 추적 추가한다.
5. 커밋 메시지를 작성해 **사용자에게 보여주고 승인을 받는다.**
6. 커밋한다.
7. 커밋 후 브랜치를 어떻게 할지 정한다 — 원격 유무로 갈린다.
   - **원격이 있으면** `push -u origin {브랜치}` → PR/MR → 스쿼시 머지 (아래 브랜치 절).
   - **원격이 없으면**(로컬 전용 저장소) push·PR 단계가 성립하지 않는다.
     과업이 끝난 시점에 기본 브랜치로 `--no-ff` 병합하고 브랜치는 남긴다.
     분기했다는 사실이 이력에 남고 기본 브랜치가 최신이 되어 다음 세션이 이어받는다.
   - 어느 쪽인지는 `git remote -v` 로 확인한다. 임의로 정하지 말고 결과를 따른다.

- 커밋 메시지 형식은 `references/commit-convention.md` 를 따른다.
- 한 커밋은 한 과업 단위로 묶는다. 과업번호를 메시지에 포함한다.
- **연동·설정 변경과 과업 구현을 한 커밋에 섞지 않는다.** 하네스 연동, 의존성 추가,
  린터 설정 같은 준비 작업은 과업 착수 **전에** 따로 커밋한다.
  이미 섞였으면 사용자에게 알리고 분리할지 묻는다 (과업 단위 되돌리기가 불가능해진다).
- `vcs.commitDeploys: true` 인 프로젝트에서는 3번을 건너뛰지 않는다.

## 브랜치 (git · `commitDeploys: false`)

```bash
git switch -c {브랜치명}          # 기본 브랜치에서 분기
git add {파일}
git commit -m "{메시지}"
git push -u origin {브랜치명}
```

- 기본 브랜치(`vcs.defaultBranch`)에 직접 커밋하지 않는다. 분기부터 한다.
- PR/MR 생성·머지 명령은 호스트별로 다르다. GitHub 은 `gh`, GitLab 은 `glab` 을 쓴다.
- 스쿼시 머지를 기본으로 한다.

---

## 하네스 파일을 따로 관리하는 경우

`vcs.separateHarnessRepo: true` 면 `.claude/**` 와 소스가 다른 레포로 간다.

- 소스 파일을 하네스 레포에, 하네스 파일을 소스 레포에 넣지 않는다.
- 커밋 전 변경 파일이 어느 쪽인지 먼저 가른다. 섞인 채로 커밋하지 않는다.

## 금지

- `push --force` · `push -f` · `push --force-with-lease`
- `reset --hard` · `clean -fd`
- 대화형 rebase (`rebase -i`)
- 사용자 승인 없는 커밋·푸시·PR 생성

되돌릴 수 없는 요청을 받으면 무엇이 사라지는지 먼저 알리고 사용자 확인을 받는다.
