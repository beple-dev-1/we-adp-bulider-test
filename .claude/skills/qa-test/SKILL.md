# /qa-test {과업번호}

테스트 계획서대로 실행하고 결과를 한 파일에 모은다.

> **이 스킬은 골격만 제공한다.** 무엇을 어떤 명령으로 돌리는지는 `config/stack.yaml` 의
> `test` · `runtime` 설정에서 읽는다. 하네스는 특정 테스트 프레임워크를 전제하지 않는다.

---

## 0단계: 프로파일 확인

```bash
bash .claude/scripts/check-profile.sh
```

미연동이면 멈추고 출력 내용을 사용자에게 전달한다.

---

## 트랙 구분

테스트는 두 트랙이다. 경계는 **커밋 시점이 아니라 검증 수단**이다.

| 트랙 | 무엇으로 검증 | 담당 |
|---|---|---|
| 트랙1 | 테스트 러너 (`stack.test.runCommand`) | `qa-tester` 에이전트 |
| 트랙2 | 실행 환경 — 실제 요청·화면 (`stack.runtime`) | 메인 Claude |

- 트랙1 의 범위는 `stack.test.scopeNote` 가 정한다. 프레임워크 제약이 있으면 거기에 적혀 있다.
- `stack.vcs.commitDeploys: true` 면 트랙2 는 **커밋 후**에만 가능하다. 그 경우 순서는
  트랙1 → `/code-review` → 커밋 → 트랙2 다.
- `commitDeploys: false` 면 트랙2 를 커밋 전에 로컬에서 돌린다.

---

## 절차

### 1단계: 계획서 로드

- `{outputDir}/plans/{과업번호}/{과업번호}_test_plan.md` 를 읽는다.
- 없으면 `/dev-plan {과업번호}` 를 먼저 하도록 안내한다.

### 2단계: 트랙1 — 러너 실행

- `stack.test.enabled: false` 면 이 단계를 건너뛰고 **건너뛴 사실을 결과서에 남긴다.**
- `stack.test.suites` 가 비어 있지 않으면 **각 suite 를 따로 실행하고 결과를 분리해 적는다.**
  (한 명령에 `&&` 로 묶으면 어느 러너가 실패했는지 결과서에서 사라진다)
- 명령 실행 전 `config/stack.yaml` 의 `env` 를 내보내고 `toolPaths` 를 PATH 앞에 붙인다
  (env·toolPaths 를 무시하면 PC 마다 다른 실패가 난다).
- `qa-tester` 에이전트에 계획서와 과업번호를 전달한다.
- 에이전트는 `stack.test.runCommand` 의 `{target}` 을 대상 이름으로 치환해 실행한다.

> **명령 결과는 파이프 없이 종료 코드로 판정한다.** `명령 | tail` 처럼 파이프를 걸면
> 종료 코드가 마지막 단계의 것으로 바뀌어 **실패가 성공으로 보인다.**
> 로그가 필요하면 파일로 리다이렉트한 뒤 읽는다 — `명령 > 로그 2>&1; echo $?`.

### 2.5단계: 트랙1 — 정적 검사

- `stack.lint.enabled: false` 면 건너뛰고 **건너뛴 사실을 결과서에 남긴다.**
- 켜져 있으면 `stack.lint.command` 를 실행한다. **파이프 없이 종료 코드로 판정**한다.
- `testing.md` DoD 트랙1 이 "러너·**정적 검사**" 를 요구한다. 러너만 돌리고 트랙1 완료로 보지 않는다.
- `lint.securityCommand`(보안 스캐너)는 `/code-review` 4단계가 돌린다. 여기서 중복 실행하지 않는다.

### 3단계: 결과 저장 (트랙1)

- `{outputDir}/test-reports/{과업번호}_test_result.md` 에 저장한다.
- 전체 통과면 GREEN, 하나라도 실패면 RED 로 판정을 명시한다.
- 실패는 요약하지 않고 **출력 원문을 함께 남긴다.**

### 4단계: 트랙2 — 실행 환경 검증

> **진입 조건을 먼저 본다. `commitDeploys` 값이 이 단계의 위치를 바꾼다.**
>
> | `stack.vcs.commitDeploys` | 지금 할 일 |
> |---|---|
> | `false` | **여기서 트랙2 를 돈다.** 끝나면 `/code-review` → 커밋 |
> | `true` | **여기서 멈춘다.** 3단계 결과서를 트랙1 판정으로 닫고, 요약줄에 `- 트랙2: 0/{전체} — 커밋 후 예정` 을 적는다. `/code-review` → 커밋 뒤에 **이 단계로 돌아온다** |
>
> 정본은 `rules/testing.md` 「트랙2 는 언제 하는가」다. 이 표는 그 정본을 절차 안으로 옮긴 것이다.
> 설명 절에만 두면 번호를 따라가는 실행자가 그대로 지나친다(2026-09-01 실측).

- `stack.runtime.enabled: false` 면 건너뛰고 그 사실을 남긴다.
- 기동이 필요하면 `stack.runtime.startCommand` 로 띄운다.
  백그라운드로 띄울 때는 `env`·`toolPaths` 를 명령줄에 직접 붙인다 —
  `export` 한 값은 서브셸로 안 넘어가 기동이 조용히 실패한다.
- **끝나면 반드시 내린다.** `stack.runtime.stopCommand` 가 **실제 명령**이면 그것을 쓰고,
  `none` 이거나 비어 있으면 **명령을 실행하지 않고** 프로세스를 직접 찾아 내린다
  (`none` 은 "안 쓴다" 는 뜻이다 — 실행하면 `command not found` 가 난다).
  어느 쪽이든 마지막에 **포트가 실제로 닫혔는지 확인**한다.
  빌드 도구가 자식 프로세스를 분리 실행해 **부모만 죽으면 자식이 orphan 으로 남는다**
  (`testing.md` 실행 환경 검증 절 참조). 안 내리면 다음 단계가 파일DB 락으로 막힌다.
- 요청은 `stack.runtime.baseUrl` 로만 보낸다. **운영 주소로는 보내지 않는다.**
- 화면은 `runtime.frontendUrl`(비어 있으면 `baseUrl`)로 접속한다.
  `runtime.browser: true` 인데 브라우저 도구가 이 세션에 없으면, 확인 못 했다고 결과서에 적는다.
- 화면을 바꿨으면 값 검사만으로 통과 판정하지 않는다 — 실제 렌더를 눈으로 확인한다.
  (값은 정상인데 화면만 깨지는 경우가 있다)
- 🔴 **`runtime.frontendUrl` 이 비어 있으면(= 백엔드가 화면을 함께 서빙하면) 딥링크를 반드시 확인한다.**
  **화면 라우트가 곧 서버의 미매핑 경로**라, 서버가 그것을 처리하지 않으면
  **직접 열기·새로고침·링크 공유가 전부 죽는다.** 목록에서 클릭해 들어가는 경로만
  확인하면 안 걸린다 — 그건 브라우저 안에서만 일어나기 때문이다.

  라우트 목록의 각 경로에 **직접 요청**을 보내 HTTP 코드를 본다. 브라우저 도구가 없어도 된다.

  ```bash
  for p in / /posts/new /posts/1 /없는경로; do
    echo "$p -> $(curl -s -o /dev/null --max-time 3 -w "%{http_code}" {baseUrl}$p)"
  done
  ```

  (2026-09-01 실측 — 러너 50건 GREEN 인 상태에서 `/posts/34` 가 500 이었다.
  트랙2 를 안 돌렸으면 화면이 죽은 채로 나갔다.)
- **화면 진입 경로 3종을 다 본다** — 최초 진입 / 인플레이스 갱신 / **닫고 재진입(새로고침·직접 열기)**.
  마지막 것이 가장 잘 빠지고 가장 자주 깨진다.
- 결과를 3단계와 같은 파일에 합산한다.

### 5단계: 실패 처리

- 실패가 있으면 수정 → `/code-review` → 돌아간다. **어디로 돌아가는지가 `commitDeploys` 로 갈린다.**

  | `commitDeploys` | 실패 시 |
  |---|---|
  | `false` | 아직 커밋 전이다. 수정 → 리뷰 → **재검증** 후 커밋 |
  | `true` | 이미 커밋(=배포)됐다. 수정 → 리뷰 → **재커밋** → 트랙2 재실행 |

- 트랙2 가 끝나기 전에는 과업을 완료로 보지 않는다.

### 6단계: 종결 상태 (검증 수단이 없을 때)

**정본은 `rules/testing.md` DoD 의 「예외 — 검증 수단이 아예 없을 때」 절이다.**
이 단계는 그 정본을 절차 안으로 옮긴 것이고, 예외를 여기서 새로 만들지 않는다.
스킬이 정본에 없는 예외를 선언하면 규칙이 두 곳에서 갈린다(2026-09-02 실측 — 그렇게 갈려 있었다).

**"못 했다" 를 표현할 자리가 없으면 규칙이 무시된다.** 아래만 조건부 완료로 닫는다.

- `runtime.browser: true` 인데 이 세션에 브라우저 도구가 없다 → **렌더 확인 불가.**
  값 검사·`curl` 상태코드로 갈 수 있는 데까지 가고, **못 한 것을 결과서에 그대로 적는다.**
- 이때 판정은 `GREEN(조건부)` 로 쓰고, 요약에 한 줄을 넣는다 —
  `- 미검증: 화면 렌더 (브라우저 도구 없음) → 별도 검증 항목으로 등록`
- **이 표기가 있으면 `/pack` 에 들어가도 된다** — `testing.md` DoD 의 예외 절이 그렇게 정했다.
- 남은 검증 항목은 `HANDOFF.md` 의 다음 단계에 옮겨 적는다. 거기서 사라지면 안 한 것이 된다.

## 결과서 형식

```markdown
# {과업번호} 테스트 결과서

## 요약
- 판정: GREEN | RED
- 트랙1: {통과}/{전체}  (건너뜀 시 사유)
- 트랙2: {통과}/{전체}  (건너뜀 시 사유)

## 트랙1 — 러너
| TC | 대상 | 결과 | 비고 |

## 트랙2 — 실행 환경
| TC | 방법 | 기대 | 실제 | 결과 |

## 실패 상세
(출력 원문)
```
