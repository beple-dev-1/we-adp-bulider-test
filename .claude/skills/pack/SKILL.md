# /pack 스킬

세션 종료 전 작업 상태와 이력을 기록하여 다음 세션 또는 다른 작업자가 이어받을 수 있도록 한다.

> `HANDOFF.md`·`HANDOFF_HISTORY.md` 는 **로컬 전용** 이다 — 어느 레포에도 커밋하지 않는다 (`base-rule`).

## 사용법
```
/pack
```

## 절차

### 1단계: 작업 범위 감지
- 현재 `/develop` 스코프와 과업번호를 확인한다.
- **소스 변경**: `config/stack.yaml` 의 `vcs` 에 맞는 상태 명령으로 변경 파일 목록을 확인한다.
- **하네스 변경 (Git)**: `git status`와 `git log --oneline -5`로 하네스 파일 변경을 확인한다.

### 2단계: HANDOFF.md 갱신
`HANDOFF.md` (루트)를 **`templates/handoff-template.md` 형식**으로 갱신한다.

- 진행 중인 작업(과업번호·스코프·브랜치·현재 단계) / 작업 요약 / 변경 파일 / 다음 단계 / 미결 사항 / 보안 자가점검 구조.
- `브랜치` 는 브랜치를 쓰는 경우에만 기록한다 (`vcs.kind: svn` 이면 생략).

### 3단계: HANDOFF_HISTORY.md 누적
완료된 작업을 **`templates/history-format.md` 형식**으로 `HANDOFF_HISTORY.md` 상단에 prepend 한다.
완료 작업은 HANDOFF.md에서 HISTORY로 이동한다. 완료 작업이 0건이면 entry 를 추가하지 않고 HANDOFF.md 만 갱신한다.

**🔴 이 파일은 전문을 Read 하지 않는다.** 누적 파일이라 계속 커진다(수천 줄 · 수만 토큰까지 자란다). Read 도구 기본 상한이 2,000줄이라 전문 Read 는 **잘려 읽힌다.** 잘린 내용을
Write 로 되쓰면 뒤쪽 entry 가 조용히 사라진다 — 로컬 전용 파일이라 어느 레포에도 백업이 없다.

prepend 는 아래 순서로 한다 (워크스페이스 루트 기준).

0. 파일이 없으면 골격부터 만든다 — `# HANDOFF HISTORY` · 빈 줄 · `---` · 빈 줄 (4줄).
1. **새 entry 를 Write 도구로 임시파일에 쓴다** (`{{config.tempDir}}/` 등 로컬 전용 경로).
   `## {날짜} — {제목}` 으로 시작하고 **빈 줄 · `---` · 빈 줄** 로 끝낸다 (entry 간 구분 형식).
2. 셸로 합친다 — 기존 파일은 읽지 않고 통과시킨다.
   ```
   { head -n 4 HANDOFF_HISTORY.md; cat {임시파일}; tail -n +5 HANDOFF_HISTORY.md; } \
     > {임시결과} && mv {임시결과} HANDOFF_HISTORY.md
   ```
   `head -n 4` 는 파일 골격(`# HANDOFF HISTORY` · 빈 줄 · `---` · 빈 줄)이다. 줄 수를 줄이면
   `---` 뒤 빈 줄이 사라져 entry 구분 형식이 어긋난다.
3. 검증은 카운트로만 한다 — `wc -l` 과 `grep -c '^## '` 가 각각 늘었는지 확인.
4. 임시파일을 지운다.

- **entry 본문을 셸 명령 문자열에 직접 넣지 않는다** (heredoc · `echo` 포함).
  시크릿 파일 접근 차단은 `config/scope.yaml` 의 `protectedPaths` 로 판단한다 —
  파일을 열지 않고 **이름만 언급해도** 막힌다. HISTORY 본문에는 그 파일명이 실제로 등장한다
  . 1번에서 Write 도구를 쓰는 이유다 — 파일 경로만 지정하면 내용이 셸 명령에 노출되지 않는다.
- Edit 도구로 상단만 고치면 골격은 지켜지지만, Edit 은 같은 대화에서 선행 Read 를 요구하므로
  위 비용을 그대로 낸다. **셸 방식을 표준으로 한다.**
- 이 절차는 3단계 전용이다. **2단계 `HANDOFF.md` 는 작은 파일이므로 종전대로 Read/Write 한다.**

### 4단계: 보안 자가점검
- 시크릿 정보가 코드에 포함되었는지 확인한다.
- 운영 설정 파일이 변경되지 않았는지 확인한다.

### 5단계: 세션 회고 — 절차 이탈 자가 기록

이번 세션에서 **명문화된 절차의 이탈**이 있었는지 회고하고, 해당 시
`.claude/harness-friction.jsonl`(로컬 전용)에 `process-deviation` type 으로 1줄 append 한다.
이 기록은 `/harness-review` 2단계 집계의 입력 신호가 된다.

- **기록 기준 (좁게 — 노이즈 방지)**: `base-rule`·`CLAUDE.md`·스킬 정의에 **문서로 존재하는
  게이트·필수 절차**를 생략했거나 순서를 위반한 경우만 기록한다. 스타일·판단 차이,
  사용자가 명시적으로 스킵을 지시한 항목은 기록하지 않는다.
- **기록 형식**: `{"ts":"<ISO8601>","type":"process-deviation","rule":"<위반 절차의 출처(파일·조항)>","detail":"<무엇을 생략/위반했고 어떻게 발견되었는가>"}`
- append 시 JSONL 유효성을 보장한다 — `detail`·`rule` 에 따옴표 등 특수문자가 있으면
  JSON 이스케이프 후 기록한다(깨진 줄은 2단계 집계 자체를 오염시킨다).
- 기록한 이탈은 `HANDOFF.md` **미결 사항**에도 1줄 기재한다(다음 세션 인지용).
- ⚠️ **LLM 자가 판정이다 — 기록은 신호일 뿐 확정이 아니다.** 이탈 여부의 최종 판단은
  `/harness-review` 집계를 본 사람이 한다(신뢰 위계 `테스트 필요`).
  무기록이 "이탈 없음"의 보증도 아니다.
- 마찰 로그 append 는 로컬 파일 기록이므로 leaf 스킬 원칙(외부 스킬 미호출)에 위배되지 않는다.

### 6단계: (선택) 하네스 자가검증 위임 — `/harness-review`

하네스(`.claude/`) 변경이 있었거나 사이클 종료 시 하네스 점검을 원하면 **선택적으로** `/harness-review` 를
위임 호출한다. **강제 자동 실행이 아니다** — 사용자가 원할 때만 수행하며, pack 자체는 이 호출 없이도 정상 종료한다.

- 호출: `Skill(harness-review)`. (pack 은 본래 외부 스킬을 호출하지 않는 leaf 스킬이므로 이는 신규 외부 위임이다.)
- 상세 절차·신뢰 위계(결정론 게이트 / 사람 항목별 컨펌 / 커밋 `/git` 위임)는 **`/harness-review` 스킬 정의를 따른다** — 여기서 재서술하지 않는다(중복·드리프트 방지).
- **정합성**: pack 이 만드는 `HANDOFF.md`·`HANDOFF_HISTORY.md` 와 마찰 로그는 로컬 전용으로 어느 레포에도
  커밋하지 않는다. `/harness-review` 가 만드는 **`.claude/` 개선분만** 하네스 레포에 커밋된다(`base-rule`·decision #1 일치).

## 완료 후
HANDOFF.md 갱신 완료를 안내하고 세션을 종료할 준비가 되었음을 알린다.
하네스 변경이 있었다면 `/harness-review` 실행 여부를 사용자에게 **선택적으로** 제안한다(강제 아님).
(위 6단계와 같은 것이다 — 단계 번호를 여기서 다시 매기지 않는다.)
