# 기본 규칙

이 파일은 모든 세션에 자동 적용된다.

---

## 프로파일 우선

- 이 하네스는 프로젝트 정보를 `.claude/config/` 에서만 읽는다. 코드에서 추측하지 않는다.
- 설정이 채워지지 않았으면(`__FILL__` 잔존) 스킬은 작업을 시작하지 않고 사용자에게 알린다.
- 검사: `bash .claude/scripts/check-profile.sh`

## 작업 범위

- `/develop {스코프}` 로 정한 범위 밖 파일은 수정하지 않는다. 필요하면 멈추고 사용자에게 묻는다.
- `config/scope.yaml` 의 `protectedPaths` 는 읽지도 않는다.
- 커밋 전 `/code-review` 를 거친다.
- `config/stack.yaml` 의 `vcs.commitDeploys: true` 면 **커밋이 곧 배포**다. 이 경우 리뷰 생략은 없다.
- 한 커밋은 한 과업 단위로 묶고, 과업번호를 메시지에 넣는다.

### 경미 변경 예외

아래를 **모두** 만족하면 `/code-review` 스킬 대신 인라인 검토(diff 확인 + 자가 판정)로 갈음할 수 있다.
갈음했으면 커밋 보고에 그 근거를 한 줄 남긴다.

1. 금액·권한·상태 전이 로직과 무관하다
2. 변경 성격이 스타일·상수값·주석·문서 중 하나다
3. 빌드·컴파일이 통과한다

하나라도 벗어나면 스킬을 거친다.

## 서브에이전트 사용

- 스킬이 디스패치 지점을 정의한 곳에서는 서브에이전트를 쓰는 것이 기본이다.
- 에이전트를 쓸 수 없는 상황이면 **임의로 대행하지 않고 사용자에게 먼저 묻는다.**
- 사용자가 메인 대행을 택했으면 두 가지를 지킨다.
  1. 그 에이전트가 맡던 교차검증을 별도 단계로 세운다 (관점이 다르면 놓치는 것도 다르다)
  2. 대행했다는 사실과 보강 내역을 산출물에 한 줄 남긴다
- 잡다한 단발 조회까지 서브에이전트로 돌리라는 뜻은 아니다. 기동 비용이 있다.

## 과업 진행 게이트

원인 규명형 과업(장애 대응·로그 분석)은 정규 워크플로를 생략할 수 있다. 단 경계를 지킨다.

- **읽기 구간(자율)** — 코드 추적·로그 분석·재현은 자율로 진행하되, 발견 시점마다 중간 보고한다.
- **쓰기 게이트(필수)** — 첫 소스 수정 전에 수정 대상·수정안·영향 범위를 보고하고 승인을 받는다.
- 수정 이후는 정규 절차와 같다: `/code-review` → 커밋 승인 → 커밋.

### 정규 워크플로로 올려야 하는 경우

아래 중 하나라도 해당하면 `/develop` 으로 전환한다.

1. 수정이 여러 파일로 퍼질 때 (스코프가 둘이면 `/develop {A}+{B}` 로 둘 다 명시한다)
2. 스키마 변경·데이터 정비가 필요할 때
3. 외부 연동 규격이 바뀔 때
4. 금액·권한 등 되돌리기 어려운 흐름을 수정할 때
5. 원인 복구가 아닌 기능 추가로 성격이 바뀔 때

## 보안

- 비밀번호·API 키·접속 정보·암호화 키는 코드·문서·주석·커밋 메시지에 넣지 않는다.
- `protectedPaths` 의 파일은 읽기·수정·복호화 금지. 값이 필요하면 사용자에게 요청한다.
- 개인정보가 든 실제 데이터를 코드·문서에 넣지 않는다.
- MCP 도구 호출 파라미터에 시크릿을 넣지 않는다 — 호출과 응답 모두 외부를 경유한다.
- DB 를 쓰는 경우, `stack.yaml` 의 `db.metaOnly: true` 면 업무 데이터를 직접 조회하지 않는다(구조 조회만).

## 산출물 위치

`config/project.yaml` 의 `outputDir` 기준이다.

| 산출물 | 경로 |
|---|---|
| 개발 브리프 | `{outputDir}/works/{과업번호}_dev_brief.md` |
| 개발·테스트 계획서 | `{outputDir}/plans/{과업번호}/` |
| 테스트 결과서 | `{outputDir}/test-reports/{과업번호}_test_result.md` |
| 세션 인수인계 | `HANDOFF.md` · `HANDOFF_HISTORY.md` |

- 산출물과 인수인계 파일은 **로컬 전용**으로 두는 것을 권고한다. `.gitignore` 에 추가한다.
- `.claude/harness-friction.jsonl`(마찰 로그)도 로컬 전용이다. 파일 경로가 그대로 들어가므로 올리지 않는다.

## 하네스 파일 수정

**먼저 소유를 가른다.** 코어와 프로젝트 소유는 처분이 다르다.

| 소유 | 대상 | 처분 |
|---|---|---|
| **코어** | `skills/` · `agents/` · `scripts/` · `hooks/` · `semgrep-rules/` · `docs/agents/` · `docs/examples/` · `docs/profile/` · `config/presets/` · `VERSION` · `.gitattributes` · `INSTALL.md` | **고치지 않는다.** 갱신 때 덮여 사라진다 — 고칠 것이 있으면 **하네스 관리자에게 전달**한다 |
| 프로젝트 | `config/*.yaml` · `rules/` · `docs/guideline/` · `docs/anti-patterns.md` · `settings.json` · `skills/code-review/references/project-rules.md` · 루트 `CLAUDE.md` | 아래 절차대로 확인받고 고친다 |

- 하네스는 **zip 으로 배포되고 편집은 관리자만 한다.** 코어를 고쳐도 다음 갱신에 사라지므로
  고쳐 주는 것이 오히려 손해다 — 고쳤다는 사실만 남고 결과는 안 남는다.
- **관리자 세션은 예외다.** 골자 저장소에서 작업하는 경우 코어가 곧 편집 대상이고,
  그때도 아래 절차(대상·전후·영향)를 그대로 지킨다.


`.claude/` 하위 파일과 `CLAUDE.md` 를 수정할 때는 **사용자가 직접 지시한 경우라도** 먼저 셋을 제시하고
확인을 받은 뒤 진행한다.

1. 어떤 파일을 수정하는지
2. 변경 전/후 핵심 차이
3. 그 변경이 미치는 영향

메커니즘(설정 슬롯·검사 스크립트)을 바꿀 때는 **그 슬롯을 읽는 쪽도 같이** 바꾼다.
읽는 곳 없는 설정은 곧 죽은 설정이 된다.

## 책임

- AI 가 쓴 코드도 커밋 전 담당자가 검토한다.
- 스코프 밖 수정은 명시적 승인 없이 진행하지 않는다.
