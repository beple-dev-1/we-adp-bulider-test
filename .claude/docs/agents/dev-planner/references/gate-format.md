# Gate Format — 4.5단계 페이즈 분할 검토

> 4.5단계 전용. playbook-phases.md의 R1~R10 규칙을 먼저 숙지한 후 사용.
>
> **제시 주체 = 메인(/dev-plan 스킬).** dev-planner 는 비대화형 서브에이전트라 사용자에게 직접 제시할 수 없다. dev-planner(split)는 본 포맷의 분할안을 **메인에 반환**하고, 메인이 사용자에게 제시·승인받는다. 아래 "사용자에게 제시/확인" 문구는 모두 **메인의 행위**로 읽는다.

---

## 페이즈 목록 테이블 컬럼 형식

### R9 적용 시 — 포함 화면 컬럼 추가

R9 적용 프로젝트는 페이즈 목록 테이블에 **포함 화면** 컬럼을 추가한다:

```
| N| 페이즈명| slug| 포함 §11 단계| 포함 화면| 예상 기간| 의존 페이즈| 독립 배포|
|---|---------|------|------------|---------|----------|-----------|---------|
| 1| 인프라 & 공통 & 보안| infra| 1,2,3| (없음 — 횡단)| 3d| —| Y|
| 2| 로그인| auth| 4,5| login.html, otp-modal| 1.5d| 1| Y|
| 3| 도메인 A 관리| domain-a| 6,10| domain-a/list, domain-a/detail| 2d| 1| Y|
| 4| 도메인 B v1| domain-b-v1| 7,11| domain-b/v1/step1~3| 2.5d| 2| Y|
| 5| 도메인 B v2| domain-b-v2| 8| domain-b/v2/step1~3| 2d| 4| Y|
| 6| 외부 시스템 연계| external-link| 9| external/link| 1.5d| 2| Y|
| 7| 도메인 C (신규) + 마무리| domain-c| 12,13,14,15| domain-c/*| 3d| 3,5,6| Y|
```

R9 미적용 프로젝트는 **포함 화면** 컬럼을 생략하거나 `해당 없음 — 화면 없는 프로젝트`로 단일 행 처리한다.

### R10 적용 시 — 영역(BE/FE) 컬럼 추가

R10 적용 프로젝트는 페이즈 목록 테이블에 **영역(BE/FE)** 컬럼을 추가한다:

```
| N| 페이즈명| 영역| slug| 포함 §11 단계| 포함 화면| 예상 기간| 의존 페이즈| 독립 배포|
|---|---------|------|------|------------|---------|----------|-----------|---------|
| 1| BE 인프라 & API & 공통| BE| be| 1,2,3,4,5,8,9,10| (없음 — BE 영역)| 2d| —| (가능하나 화면 없어 사용자 가치 없음)|
| 2| FE 단일 화면| FE| fe-{화면}| 6,7,13,14| {화면}.html| 1.5d| 1| Y|
```

R10 미적용 프로젝트는 **영역** 컬럼을 생략한다 (R9 가이드 표 형식 그대로).

## 4.5단계: 페이즈 분할 검토 (사용자 게이트)

메인은 dev-planner(split)가 반환한 페이즈 목록을 **사용자에게 텍스트로 제시하고 확인 받는다.** 5단계 코드 탐색 진입 전에 분할 자체를 검증하는 단계. 페이즈 분할은 develop·qa-test가 묶이는 가장 큰 의사결정이므로, 잘못된 분할로 5~7단계가 모두 낭비되는 것을 차단한다.

**선결 검토 — 도메인 ≥ 2개 묶임 케이스 (필수):**

브리프 §3-4 영향 도메인 또는 §11 단계 분포에서 **도메인 ≥ 2개**가 한 과업에 묶여 있고 BE 다단계 분할 후보가 도메인 축으로 향하는 경우, 페이즈 테이블 출력 직전에 사용자에게 **과업 분리 가능 여부**를 먼저 확인한다.

```
️ 선결 검토: 도메인 ≥ 2개 묶임 감지

이 과업에는 도메인 N개가 묶여 있습니다: {도메인 A}, {도메인 B}, ...
운영 표준은 **도메인별 과업 분리**입니다 — 분리 가능하면 각 과업당 도메인 1개로 처리하는 것이 표준 흐름입니다.

선택:
- "분리 가능" — 과업을 도메인별로 분리하시겠습니까? (dev-interview 재요청 권유)
- "분리 불가" — 도메인 축 (`be-infra` + `be-{도메인}` × N) 으로 분할 진행 (예외 케이스 안전망)
- 사유 없이 "진행" — 사용자 의사 확인 1회 더 요청
```

**사용자 응답 분기:**
- "분리 가능" / "분리하겠다" → dev-planner 종료 권유 + dev-interview 재요청 안내. 사용자가 분리 후 신규 과업으로 dev-plan 재호출.
- "분리 불가" / "묶어서 진행" → 도메인 축 분할 진행 + 페이즈 테이블 출력 (아래 R9+R10 포맷)
- 도메인 1개 케이스이거나 BE가 단일 BE / 레이어 축으로 자연 결정되는 경우 → 선결 검토 자동 생략 후 페이즈 테이블로 진입

**제시 포맷은 R9·R10 적용 여부에 따라 분기한다.**

**제시 포맷 (R9 + R10 적용 케이스 — 화면이 있는 서버 서비스):**

```
## 페이즈 분할 결과 (BE/FE 영역 분리 + 화면 단위 — R9·R10 동시 적용)

| N| 페이즈명| 영역| slug| 포함 §11| 포함 화면| 예상 기간| 의존 페이즈| 독립 배포|
|---|---------|------|------|---------|---------|----------|-----------|---------|
| 1| BE 인프라 & API & 공통| BE| be| 1,2,3,4,5,8,9,10| (없음 — BE 영역)| 2d| —| (가능하나 화면 없음)|
| 2| FE 도메인 A 화면| FE| fe-domain-a| 6,7| domain-a/edit.html| 1.5d| 1| Y|
| 3| FE 도메인 B 화면| FE| fe-domain-b| 11,12,13,14| domain-b/list, domain-b/detail| 1d| 1| Y|
| ...

**분할 근거 (R 규칙 적용 내역):**
- R10 (BE/FE 영역 분리): Phase 1은 BE 통합, Phase 2~N은 FE 화면별
- R1 (스캐폴딩+공통+보안 통합): §11 1,2,3,4,5,8,9,10 → Phase 1 (BE)
- R9 (화면 단위 우선 — FE만): Phase 2~N을 FE 화면 흐름 중심
- R5 (테스트 영역 분리): 페이즈 §DoD·§검증 방법 모두 미생성. 테스트·검증·회귀·커버리지는 qa-plan 전담. 페이즈 종료 신호는 BE = 러너 GREEN(`stack.yaml` 의 `test.scopeNote` 범위) 또는 개발서버 수동 검증 완료, FE = sub-agent 코드 생성 완료 보고 (DoD 폐기)
- R8 슬러그 컨벤션: 단일 BE = `be`, FE 화면별 = `fe-{화면}`
- ...

**총계:**
- 페이즈 수: N개 (R7 범위, BE 1~2 + FE 화면 N개 자연)
- 예상 기간: Nd (브리프 §1 제안 개발 기간 대비 ±M%)
- 독립 배포 가능: BE 페이즈는 통합 배포 권장, FE 페이즈는

---

이 분할로 상세 문서를 생성할까요?
- "OK" / "진행" / "저장" — 5단계 진입
- 분할 수정 (예: "BE를 be-infra/be-service 2단계로", "fe-domain-a/fe-domain-b 합치기") → 재분할
```

**제시 포맷 (R9·R10 미적용 케이스 — REST API / Batch / Daemon / Proxy / Library / 단일 서비스):**

```
## 페이즈 분할 결과 (R9·R10 미적용 — 비풀스택 프로젝트)

| N| 페이즈명| slug| 포함 §11| 예상 기간| 의존 페이즈| 독립 배포|
|---|---------|------|---------|----------|-----------|---------|
| 1| DTO·Repository·Service| core| 1,2| 1d| —| Y|
| 2| Controller + API| api| 3| 0.5d| 1| Y|
| 3| 배포 준비| release| 4| 0.5d| 2| Y|

**R9·R10 미적용 사유**: REST API 마이크로서비스 — 화면 없음, 풀스택 아님. R1·R4·R5(테스트 페이즈 폐지)만 적용.

**분할 근거 (R 규칙 적용 내역):**
- R1 (공통 인프라 통합): DTO·Repository·Service → Phase 1
- R4 (0.5d 흡수 검토): Controller는 0.5d지만 API 스펙 결정 책임 있어 별도 페이즈 유지
- R5 (테스트 영역 분리): 페이즈 §DoD·§검증 방법 모두 미생성. 테스트·검증·회귀·커버리지는 qa-plan 전담. 페이즈 종료 신호는 BE = 러너 GREEN(`stack.yaml` 의 `test.scopeNote` 범위) 또는 개발서버 수동 검증 완료, FE = sub-agent 코드 생성 완료 보고 (DoD 폐기)

**총계:**
- 페이즈 수: N개 (R7 권장 4~7 범위)
- 예상 기간: Nd
- 독립 배포 가능: N개

---

이 분할로 진행할까요?
- "OK" / "진행" / "저장" — 5단계 진입
- 수정 사항 알려주시면 재분할 후 다시 제시
```

**사용자 응답 처리:**
- "OK" / "진행" / "저장" → 5단계 진입
- 수정 요청 (예: "Phase 4와 5를 합쳐줘", "도메인 C를 Phase 6으로 옮겨줘") → 분할 재계산 후 다시 4.5단계 제시
- 수정 라운드 3회 도달 시 → "수정 라운드가 누적되고 있습니다. 현재 분할로 진행 후 페이즈 문서 단계에서 세부 조정하시겠습니까?" 제안

**스킵 조건:**
- 브리프 §11이 **3단계 이하**인 초소형 과업 + R7 적용 결과 페이즈 2~3개로 자명한 경우 → 4.5단계 생략하고 5단계 직접 진입 (단, 9단계 결과 반환 시 "분할 자명 — 검토 게이트 생략" 명시)
- §11이 4~5단계인 경계 케이스는 페이즈가 2~3개여도 게이트를 거친다 (R7 명시 허용 범위 밖이므로 사용자 확인 권장)

**스킵보다 우선하는 조건 (아래에 하나라도 걸리면 §11 단계 수와 무관하게 게이트를 거친다):**

1. 금액·정산·잔액·한도를 다룬다
2. 권한·역할·인가 판정이 바뀐다
3. 되돌리기 어려운 **상태 전이**가 있다 (주문 확정·환불 완료·발송 등)
4. 스키마 변경 또는 데이터 정비가 있다
5. 외부 연동 규격이 바뀐다

> 기준은 `.claude/rules/base-rule.md` §정규 워크플로로 올려야 하는 경우와 같다.
> **§11 단계 수는 브리프 작성자가 임의로 쪼갠 결과일 뿐이다.** 같은 과업을 3줄로 쓰면
> 게이트가 사라진다 — 위험도가 아니라 서술 길이가 게이트를 정하게 두면 안 된다.
> 위 다섯은 잘못 나누면 되돌리는 비용이 크므로 분할 자체를 사람이 한 번 본다.
