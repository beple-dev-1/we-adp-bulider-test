# 개발 계획서 페이즈 문서 형식

`{{config.outputDir}}/plans/{과업번호}/phases/phase_{N}.md` 파일의 **8섹션** 형식이다 (§1~§7 + §8 인계).

> **DoD 폐기** — §DoD·§검증 방법 섹션은 만들지 않는다. 테스트·검증·회귀·커버리지·통과 기준은 qa-plan 전담.
> 페이즈 종료 신호: BE = 러너 GREEN(`stack.yaml` 의 `test.scopeNote` 범위) 또는 개발서버 수동 검증 완료 / FE = sub-agent 코드 생성 완료 보고.

```markdown
# 페이즈 {N}: {제목}

| 항목 | 내용 |
|------|------|
| 페이즈 번호 | {N} |
| 영역 | BE / FE |
| 목표 | {이 페이즈에서 달성할 것} |
| 의존 페이즈 | {선행 페이즈 번호, 없으면 없음} |

## 1. 페이즈 개요
{이 페이즈의 범위와 목적}

## 2. 선행 조건 / 입력
{시작 전 필요한 산출물·의존 페이즈 결과·전제}

## 3. 구현 대상 파일
{메인 Claude·sub-agent 가 이 표로 작업 대상을 식별한다.}

| 파일 경로 | 작업 유형 | 설명 |
|---------|---------|------|
| {소스 경로}/{모듈}/{파일} | 신규 생성 | {책임} |
| {화면 경로}/{화면 파일} | 수정 | {변경 내용} |

## 4. 파일별 구현 상세
시그니처·책임·의존까지만 기술한다. **메서드 본문/SQL 본문/JS 함수 본문은 작성하지 않는다** (`/develop` 영역).

### {파일명}
{구현 방향, 메서드 시그니처, 주의사항}

- **BE 페이즈**: Request/Response DTO 필드 표 (필드명·타입·필수·검증·의미) — 루트 §6-3 과 동일 계약
- **FE 페이즈**: 화면 input 필드 표 — input name 은 BE Request DTO 필드명과 동일,
  검증 강도는 **FE ≤ BE** (FE 가 BE 보다 약한 것은 OK, 강한 것은 금지 — BE 가 최종 게이트다).
  FE 가 더 좁은 정규식·길이 제한을 가지면 BE 가 받아들이는 합법 입력이 화면에서 막힌다.

## 5. 데이터 계약 참조
{루트 §6-3 DTO 명세를 참조. 페이즈 자기완결을 위해 이 페이즈가 쓰는 필드만 발췌해도 됨.}

## 6. 위험·주의
{이 페이즈 고유 위험. 글로벌 위험은 루트 §8 참조.}

## 7. 산출물 목록
{이 페이즈에서 생성·수정되는 파일}

## 8. 다음 페이즈 인계
{다음 페이즈(N+1)가 이 페이즈 산출물을 어떻게 사용하는지}
```
