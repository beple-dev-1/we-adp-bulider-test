# 테스트 계획서 루트 문서 형식

`{{config.outputDir}}/plans/{과업번호}/{과업번호}_test_plan.md` 파일의 형식이다.

```markdown
# 테스트 계획서

| 항목 | 내용 |
|------|------|
| 과업번호 | {N} |
| 제목 | {과업 제목} 테스트 계획 |
| 작성일 | {YYYY-MM-DD} |
| 대응 개발 계획서 | {N}_dev_plan.md |

## 1. 테스트 범위
{테스트 대상 기능 목록}

## 2. 테스트 방법
| 유형 | 도구 | 범위 |
|------|------|------|
| 단위 테스트 | `stack.yaml` 의 `test.framework` | `test.scopeNote` 가 정한 범위 |
| 실행 환경 검증 | 실제 요청·화면 확인 (`config/stack.yaml` 의 `runtime`) | 서버 로직, E2E 흐름 |

> **러너 범위**: 테스트 러너로 어디까지 검증되는지는 프레임워크마다 다르다.
> `config/stack.yaml` 의 `test.scopeNote` 가 그 경계를 정의한다. 그 밖은 실행 환경 검증으로 넘긴다.

## 3. 테스트 환경
- 검증 환경: `config/stack.yaml` 의 `runtime.baseUrl`
- DB: `config/stack.yaml` 의 `db` 설정 (쓰지 않으면 해당 없음)
- 엔드포인트 규칙: 프로젝트 규약에 따름 (프로파일에 적는다)

## 4. 테스트케이스 목록
> TC 번호 규칙은 qa-planner 절차 §3 참조 (`TC-{과업번호}-{도메인코드}-{순번3자리}`).
> 도메인 코드는 `.claude/config/scope.yaml` 의 `scopes[].id` 대문자다 — 목록을 여기 두지 않는다.

| TC 번호 | 제목 | 유형 | 우선순위 | 완료 |
|--------|------|------|---------|------|
| TC-{과업번호}-{스코프ID대문자}-001 | ... | 단위/개발서버 | 높음 | [ ] |

## 5. 완료 기준 (DoD)
- [ ] 전체 TC GREEN
- [ ] CRITICAL 항목 0건
- [ ] 경계값 케이스 포함 확인
- [ ] 중복 처리 방지 케이스 포함 확인
- [ ] 오류 응답 구조가 이 프로젝트의 오류 계약(브리프 §5)과 일치하는지 확인
```
